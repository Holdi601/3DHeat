# 메모리, 예산과 적합성 검사

컴퓨터의 메모리는 한정되어 있습니다. 3DHeat은 파일이 필요로 하는 것을 합산해서, **불러오기** 전에 그것이 들어가는지 알려 줍니다.

!["들어가지 않음" 상태의 메모리 추정. "[N]행마다 불러오기"가 미리 채워져 있고, 불러오기 버튼에는 "너무 큼 - 줄이거나 솎기"라고 표시됨](../assets/img/en/memory-and-budgets-wont-fit.webp)

*이 컴퓨터에는 너무 큰가요? 3DHeat은 대신 N번째마다 행을 불러오라고 제안합니다.*

불러오기 도중 메모리가 바닥나는 브라우저 탭은 충돌하고 몇 분 동안의 작업을 잃습니다. 가진 것보다 많은 것을 요구받은 GPU는 컨텍스트를 잃거나 기어가듯 느려집니다. 그래서 불러오기가 시작되기 전에 소스 패널이 필요한 메모리를 말하고, 그것을 이 기계에서 감지한 예산과 비교하며, 들어가지 않을 때는 탈출구와 함께 거부합니다. 모델은 [`src/data/memory.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/data/memory.ts)에 있습니다.

## 메모리 추정 {#the-memory-estimate}

행을 세고 나면 **불러오기** 버튼 위에 나타납니다.

| 줄 | 뜻 |
|---|---|
| **메모리 추정** - *들어감* / *빠듯함* / *들어가지 않음* | 판정. 녹색, 주황색 또는 빨간색. |
| `N rows · B B/row` | 불러올 행 수(간격을 적용한 뒤)와 행당 고정 바이트. |
| `RAM X resident, Y peak while loading` | 불러온 뒤 붙잡고 있는 메모리, 그리고 불러오는 동안의 최고치. |
| `GPU Z · est. load T` | 행을 위한 GPU 메모리, 그리고 초당 120만 행으로 추정한 시간. |
| GPU 이름 | 드라이버가 알려 주면 렌더러의 이름. |
| 메시지 | 들어가지 않는 이유, 또는 빠듯한 이유와 할 일. |
| **[N]행마다 불러오기** | 솎기 간격(아래 참고). |
| `Budget: X RAM, Y GPU. Adjust under Performance → Resource budgets.` | 검사에 쓴 예산. |

### 행당 바이트 {#bytes-per-row}

| 열 | 고정 (RAM) | 메모 |
|---|---|---|
| 위치 | 12 | 32비트 부동소수점 셋. 항상 (평평한 축도 배열임) |
| 시간 | 4 | 대응될 때 |
| 수명 | 4 | 시간과 사람이 대응될 때 |
| 사람 | 4 | 대응될 때 |
| 그룹 | 2 | 대응될 때 |
| 세션 | 4 | 대응될 때 |
| `Source file` | 4 | 파일을 둘 이상 불러올 때 |
| 필터 열 각각 | 4 | 체크한 *필터링용으로 유지* 열마다 |

**최고치**는 불러오기가 잠깐만 필요로 하는 것을 더합니다. 병합하는 동안의 64비트 시간 8바이트, 정렬 키와 인덱스 12바이트, 순열 임시 공간 4바이트(시간이 대응될 때는 셋 다), 그리고 그룹 열이 아직 32비트일 때 4바이트. 그리고 합계에 **2.0**을 곱합니다. 이 계수는 측정했습니다(실제 여러 파일 불러오기가 항목별 배열의 1.9배에서 최고치에 도달했습니다. Parquet 디코더의 작업 집합, 각 열을 길이에 맞게 자르는 복사본, 그리고 해제되었지만 아직 돌려주지 않은 메모리 때문입니다). 그리고 올림했습니다. 과소 추정은 탭이 충돌하는 비용이 들고, 과대 추정은 불필요한 간격 비용만 들기 때문입니다.

**GPU**에서는 행마다 8바이트(위치와 그룹, 각 16비트)가 들고, 시간과 수명이 모두 대응될 때는 4바이트(시간과 수명, 각 16비트)가 더 듭니다. [GPU 메모리 상주](gpu-memory.md)를 보세요. 필터 텍스처(활성 필터마다 행당 4바이트)와 선 히트의 세그먼트 시작(선 모드가 켜져 있을 때 행당 8바이트)은 이 추정에 들어가지 않습니다.

## 적합성 검사 {#the-fit-check}

세 가지 제약을 비교합니다([`checkFit`](https://github.com/Holdi601/3DHeat/blob/main/src/data/memory.ts)).

- 최고 RAM과 **RAM 예산**,
- GPU 바이트와 **GPU 예산**,
- 시간 열이 대응될 때 행 수와 400,000,000행의 **정렬 상한**.

세 비율 중 가장 나쁜 것이 판정합니다. 70%까지는 *들어감*, 100%까지는 *빠듯함*(불러와야 하지만 느릴 것으로 예상), 그 위는 *들어가지 않음*입니다. 들어가지 않으면 패널은 가장 크게 제약하는 것을 이름으로 말하고 다음을 제안합니다.

- *N*번째마다 행을 불러오기. *N* = ⌈행 수 / 들어가는 행 수⌉이며, 간격 상자에 미리 채워집니다.
- 필터 열을 빼기, 시간 열의 대응을 풀기(정렬과 그 상한을 없애는 대신 타임라인을 잃음), 또는 예산을 올리기.

예산 자체가 하드웨어에 대한 사실이 아닐 때(브라우저가 RAM 수치를 제한했거나, 기본값이 지금 비어 있는 양에 눌려 있거나, GPU 수치가 추측일 때), 메시지는 그것을 말해서 필요 없는 간격을 쓰지 않도록 합니다.

### 솎기 {#decimation}

**[N]행마다 불러오기**는 *N*행마다 한 행만 남기며, 파일별로 셉니다. 히트는 평균이므로, N번째마다 행은 같은 분포를 더 많은 잡음으로 줍니다. 렌더러가 매 프레임 이미 하는 것과 같은 거래입니다. 상자는 1(*행 (전부)*)에서 시작합니다. 선택이 들어가지 않을 때는, 직접 입력하지 않았다면 제안된 간격으로 미리 채워집니다. 그러면 불러오기 버튼은 *파일 N개 불러오기 (K개 중 1개)*로 읽히고, 데이터셋 이름에 `every Kth row`가 기록됩니다.

### 정렬 상한 {#the-sort-ceiling}

렌더러는 행을 시간 오름차순으로 필요로 하므로, 대응된 시간 열은 모든 행을 정렬한다는 뜻입니다. 32비트 키 위의 기수 정렬([`sort.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/data/sort.ts))입니다. **4억** 행을 넘으면 탭에서 시도하지 않고 거부합니다. 이것은 불러오기 전에 검사하므로, 한도를 넘은 선택은 끝까지 읽고 마지막 단계에서 실패하는 대신 간격 제안과 함께 거부됩니다. 한도 가까이(*빠듯함*)에서는 패널이 정렬이 자체 진행 표시 없이 오래 걸리는 과정이라고 경고합니다. 시간 열이 없으면 정렬이 일어나지 않으며 상한도 적용되지 않습니다.

## 리소스 예산 {#resource-budgets}

**성능 → 리소스 예산**(성능 패널 맨 아래의 접을 수 있는 줄. `Resource budgets - RAM, GPU, cores`라고 읽힙니다). 예산은 감지되며, 감지된 수치가 기본값입니다. 슬라이더는 **상한**보다 높이 가지 않습니다. 상한은 감지된 수치이고, 감지가 측정이 아님을 아는 경우는 예외입니다.

| 조작 | 범위 | 뜻 |
|---|---|---|
| **행 데이터용 RAM** | 256 MiB부터 RAM 상한까지, 로그 | 적합성 검사의 RAM 예산. 감지된 기본값을 넘으면 *(감지값보다 높음)*, 상한에서는 *(최대)*로 표시. |
| **행 데이터용 GPU** | 128 MiB부터 GPU 상한까지, 로그 | 적합성 검사와 행 업로드의 GPU 예산. 감지된 기본값을 넘으면 *(감지값보다 높음)*, 상한에서는 *(최대)*로 표시. |
| **파서 스레드** | 1부터 논리 코어 수까지 | 불러오기 한 번에 동시에 파싱하는 파일 수. 각각 자신의 작업자에서. 기본값은 코어 - 2(코어가 4개 이하면 코어 - 1). [파서 스레드](#parser-threads)를 보세요(개발자용 아래). |
| 소스 줄 | | 각 수치가 어디서 왔는지(`RAM: …. GPU: …. CPU: ….`). |
| **다시 감지** | | 개발 서버에 새 메모리 값을 요청하고 모든 예산을 다시 계산. |
| GPU 이름 | | 어댑터의 짧은 이름. 전체 렌더러 문자열은 툴팁. |

### GPU 예산 올리기 {#raising-the-gpu-budget}

감지된 수치보다 높은 GPU 예산은 설정한 그대로 적용됩니다. 적합성 검사와 업로드는 같은 수치를 한 함수([`effectiveGpuBudget`](https://github.com/Holdi601/3DHeat/blob/main/src/render/budget.ts))에서 받으며, 이 함수는 슬라이더가 멈추는 GPU 상한에서만 자릅니다. 그러므로 검사를 통과한 불러오기는 전부 업로드됩니다. 감지된 수치를 넘으면 슬라이더는 *(감지값보다 높음)*이라고 읽힙니다. 이때 그 숫자는 측정이 아니라 카드에 대한 당신의 판단이며, 카드가 감당하는 것보다 높게 설정하면 컨텍스트 상실이나 기어가는 속도의 위험이 있습니다.

## 매우 큰 데이터셋: 조절 수단 {#huge-datasets-the-levers}

가장 싼 것부터 가장 과격한 것까지:

1. **필터 열 줄이기.** 각각 행당 4바이트이고 디코드 한 번입니다.
2. **간격.** N번째마다 행.
3. **시간 열 없애기.** 정렬 없음, 정렬 상한 없음, 시간과 수명에 드는 행당 4~8바이트 없음 - 그리고 타임라인도 없음.
4. **예산 올리기**, 메모리가 있다는 것을 알 때.

렌더링할 때 큰 데이터셋은 데이터를 줄이는 대신 샘플링과 점진적 누적으로 처리합니다. [샘플링과 예산](sampling-and-budgets.md)을 보세요.

## 개발자용 {#for-developers}

### 파서 스레드 {#parser-threads}

여러 파일을 불러올 때는 **파서 스레드** 수만큼 동시에 파싱합니다. 각 파일은 그 불러오기를 위해 인제스트 작업자가 시작한 파서 작업자에서 파싱합니다([`ingestFiles.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/data/ingestFiles.ts), `parseInOrder`). 1이거나 파일이 하나뿐이면 파일을 하나씩 순서대로 인제스트 작업자 자체에서 파싱합니다.

여러 개를 동시에 하는 것이 적합성 검사를 느슨하게 하지는 않습니다.

- **빌더가 먼저 셉니다.** 병합된 열은 첫 파일을 읽기 전에 전체 선택에 대해 할당합니다. 그래서 진행 중인 파일은 RAM 예산이 그 옆에 남겨 둔 것만 받습니다(`parseHeadroom`). 불러올 행마다 위치, 64비트 시간, 바라보는 각도, 사람, 32비트 그룹, 세션, 필터 열, `Source file`. 행 수가 CSV 추정치일 때는 더 큰 열로 자라는 열을 위해 2.6을 곱합니다.
- **각 파일은 시작하기 전에 자기 비용을 예약합니다**(`fileParseBytes`). 그 행 수(Parquet 푸터에서. CSV는 크기에 따른 추정치의 몫)에 같은 열을 곱하고 **8**을 곱합니다. 블록 자체, 위치가 없는 행을 버리는 동안 그 옆의 복사본, 그리고 디코더의 작업 집합입니다. 텍스트 열에서는 이것이 그 id보다 훨씬 큽니다. 간격은 이것을 줄이지 않습니다. 파일은 전체를 읽고 나중에 솎기 때문입니다. 8은 측정으로 정한 여유입니다. 3이나 5에서는 사람과 세션 이름이 있는 8600만 행에서 파서 스레드 30개가 탭을 한계 너머로 밀었습니다. 8에서는 그렇지 않았습니다.
- **다른 파일은 그 예약이 남은 것 안에 들어갈 때만 시작합니다.** 끝났지만 앞선 파일의 병합을 기다리는 파일은 병합될 때까지 예약을 유지합니다.
- **파일 하나는 항상 실행됩니다.** 아무것도 예약되지 않았으면, 다음 파일은 비용과 상관없이 시작합니다. 그것이 적합성 검사가 허용한 한 번에 하나씩 불러오기이므로, 빠듯한 예산은 거부하는 대신 그쪽으로 되돌아갑니다.

*불러오는 동안 최고치* 수치는 한 번에 하나씩 불러올 때의 최고치입니다. 그것은 모든 파일을 읽은 뒤 정렬에서 옵니다. 나란히 파싱한 파일은 읽는 동안 그 수치 이상의 메모리를 쓸 수 있습니다. 예약은 위의 추정이 맞는 한 그것을 RAM 예산 안에 둡니다.

병합 순서는 파일이 끝나는 순서와 상관없이 선택의 순서입니다. 그래서 사람, 그룹, 세션 번호, 행, `Source file` 값이 한 번에 하나씩 불러오기와 똑같습니다. 읽을 수 없는 파일은 건너뛰고 전과 똑같이 나열합니다. 파서 작업자가 죽으면 인제스트 작업자가 죽었을 때와 같이 전체 불러오기가 끝납니다. 불러오기가 어떻게 끝나든, 모든 파서 작업자는 끝날 때 종료됩니다. 파서 작업자를 전혀 시작할 수 없으면, 파일은 대신 인제스트 작업자에서 파싱합니다.

### 수치를 감지하는 방법 {#how-the-figures-are-detected}

[`detectBudgets`](https://github.com/Holdi601/3DHeat/blob/main/src/data/memory.ts)는 시작할 때, 렌더러가 생기면 다시, 그리고 **다시 감지**에서 실행합니다.

**RAM, 개발 서버 사용.** `start.bat`과 `npm run dev`는 기계의 메모리를 읽을 수 있는 프로세스에서 페이지를 제공합니다. `/__host/memory`에서(1.5 s 안에 응답하지 않으면 무시). 기본값은 설치된 RAM의 60%와 지금 여유 있는 RAM의 80% 중 작은 값입니다. 상한은 설치된 것의 60%입니다. 여유 메모리가 기본값을 누르고 있으면, 패널이 그것을 말하고 프로그램을 닫고 **다시 감지**를 누르라고 제안합니다.

**RAM, 개발 서버 없이** (정적 배포): 어떤 브라우저 API도 여유 메모리를 알려 주지 않으며, `navigator.deviceMemory`는 2의 거듭제곱으로 내림되고 Chrome과 Edge에서 8 GiB로 제한됩니다. 기본값은 `deviceMemory`의 60%이며, 브라우저가 보고하는 경우 탭의 여유 JS 힙의 4배로 더 제한합니다. 아무것도 보고하지 않으면 4 GiB입니다. `deviceMemory`가 정확히 8(상한)을 읽으면, 수치는 *제한됨*으로 표시되고 상한은 기본값의 4배이며, 기본값을 넘는 수치는 측정이 아니라 당신의 주장이라는 메모가 붙습니다.

**어느 쪽이든**, RAM 기본값과 상한은 **12 GiB**로 제한합니다. 기계가 무엇을 가졌든 Chrome 탭 하나가 가질 수 있는 최대 타입 배열 메모리입니다(한 페이지가 약 15.75 GB에 도달해서 실패했습니다. 12는 나머지를 위한 여유를 남깁니다). 그리고 256 MiB 아래로는 내려가지 않습니다.

**GPU 메모리.** 웹 API는 이것을 전혀 보고하지 않습니다.

- 개발 서버가 있으면, 카드의 메모리는 `nvidia-smi`(가장 큰 어댑터)가 읽거나, Windows에서는 디스플레이 어댑터의 레지스트리 값 `HardwareInformation.qwMemorySize`에서 읽습니다. 기본값은 그것의 70%, 상한은 90%입니다.
- 읽은 값이 없으면 추론합니다. 기본적으로 2 GiB. 가장 큰 텍스처가 16,384 px 이상(개별 카드)이면 4 GiB, 더 작으면 1 GiB, 또는 WebGPU의 `maxBufferSize`의 8배 중 더 큰 값. 추론이 내장형과 개별형을 구별할 뿐 더 세밀하게 구별하지 못하므로, 상한은 추론한 수치의 8배입니다. 패널은 그 수치가 추론임을 말합니다.
- 128 MiB 아래로는 결코 내려가지 않습니다.

**CPU.** `navigator.hardwareConcurrency`(보고되지 않으면 4).

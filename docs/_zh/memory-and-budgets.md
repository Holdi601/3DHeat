# 内存、预算与适配检查

你的电脑内存有限。3DHeat 会累加你的文件所需的内存，并在你点击**加载**之前告诉你它们是否放得下。

![内存估算提示"放不下"，已预填"每 [N] 行加载"，加载按钮显示"过大 - 减少或抽稀"](../assets/img/en/memory-and-budgets-wont-fit.webp)

*这台电脑装不下？3DHeat 会建议改为每隔 N 行加载一次。*

浏览器标签页若在加载途中耗尽内存，就会崩溃并丢失数分钟的工作；而显卡被要求提供超过其所拥有的显存时，要么丢失上下文，要么慢得几乎停滞。因此，在加载开始之前，数据源面板会说明它需要多少内存，将其与为此电脑检测到的预算进行比较；若放不下，它会拒绝加载，并给出解决办法。该模型位于 [`src/data/memory.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/data/memory.ts)。

## 内存估算 {#the-memory-estimate}

行数统计完成后，显示在**加载**按钮上方。

| 行 | 含义 |
|---|---|
| **内存估算** - *放得下* / *紧张* / *放不下* | 结论，分别为绿色、琥珀色或红色。 |
| `N 行 · B B/行` | 将被加载的行数（经步长处理后），以及每行的稳定字节数。 |
| `内存 X 常驻，加载时峰值 Y` | 加载完成后占用的内存，以及加载过程中的最高水位。 |
| `显存 Z · 预计加载 T` | 行数据占用的显存，以及按每秒 120 万行估算的耗时。 |
| 显卡名称 | 渲染器的名称，驱动程序报告时才显示。 |
| 消息 | 放不下或紧张的原因，以及该怎么做。 |
| **每 [N] 行加载** | 抽稀步长（见下文）。 |
| `预算：内存 X，显存 Y。可在 性能 → 资源预算 下调整。` | 检查所用的预算。 |

### 每行字节数 {#bytes-per-row}

| 列 | 稳定占用（内存） | 说明 |
|---|---|---|
| 位置 | 12 | 三个 32 位浮点数，始终存在（即使某个轴是平的，它仍是一个数组） |
| 时间 | 4 | 映射时 |
| 生命周期 | 4 | 映射了时间和人员时 |
| 人员 | 4 | 映射时 |
| 分组 | 2 | 映射时 |
| 会话 | 4 | 映射时 |
| `Source file` | 4 | 加载了多个文件时 |
| 每个筛选列 | 4 | 每个勾选了*保留用于筛选*的列 |

**峰值**会加上加载时仅短暂需要的部分——合并时的 64 位时间（8 字节）、排序键和索引（12 字节）、置换的临时空间（4 字节），以上三项在映射了时间时均会计入；另外，分组列仍为 32 位时还需 4 字节——并将总和乘以 **2.0**。这个系数是实测得出的（一次真实的多文件加载，峰值为逐项列出的数组的 1.9 倍，来自 Parquet 解码器的工作集、将每列裁剪到正确长度时的复制，以及已释放但尚未归还的内存），并向上取整，因为估计偏低会导致标签页崩溃，而估计偏高只会造成不必要的抽稀。

在**显卡**上，每行占用 8 字节（位置和分组，各 16 位），若同时映射了时间和人员，则另加 4 字节（时间和生命周期，各 16 位）。见[显存驻留](gpu-memory.md)。筛选纹理（每个活动筛选每行 4 字节）和线条热力的线段起点（开启线条模式时每行 8 字节）不计入此估算。

## 适配检查 {#the-fit-check}

比较三项约束（[`checkFit`](https://github.com/Holdi601/3DHeat/blob/main/src/data/memory.ts)）：

- 峰值内存与**内存预算**相比；
- 显存字节数与**显存预算**相比；
- 行数与 **排序上限** 4 亿行相比（当映射了时间列时）。

三个比值中最差的一个决定结论：不超过 70% 为*放得下*，不超过 100% 为*紧张*（应能加载，但可能较慢），超过则为*放不下*。放不下时，面板会指出限制性的约束，并建议：

- 每隔 *N* 行加载一次，其中 *N* = ⌈行数 / 能放下的行数⌉，并预填在步长框中；
- 去掉筛选列，取消映射时间列（这会去掉排序及其上限，代价是失去时间线），或提高预算。

当预算本身并非硬件的真实情况时——浏览器限制了内存数字，默认值被当前可用的内存压低，或显存数字只是猜测——消息会说明这一点，以免你去使用并不需要的步长。

### 抽稀 {#decimation}

**每 [N] 行加载**按文件计数，每 *N* 行保留一行。热力是平均值，因此每隔 *N* 行取一行会得到相同的分布，只是噪点更多——这与渲染器每帧已做的权衡相同。该框初始为 1（*全部行*）；当所选内容放不下时，它会预填建议的步长，除非你已手动输入过。加载按钮随后显示为*加载 N 个文件（每 K 行取 1）*，数据集的名称会记录 `每 K 行`。

### 排序上限 {#the-sort-ceiling}

渲染器需要按时间升序排列的行，因此映射时间列意味着要对每一行进行排序，使用的是基于 32 位键的基数排序（[`sort.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/data/sort.ts)）。超过 **4 亿**行时，系统会拒绝，而不会在标签页中尝试。这一检查在加载前进行，因此超过上限的选择会被拒绝，并附上步长建议，而不会被完整读入后在最后一步失败。接近上限（*紧张*）时，面板会警告排序是一次没有进度显示的长时间处理。没有时间列时，不进行排序，也不适用任何上限。

## 资源预算 {#resource-budgets}

**性能 → 资源预算**（性能面板底部的一个可折叠行，显示为 `资源预算 - 内存、显存、核心`）。预算是自动检测的；检测到的数值即为默认值；滑块的最大值是一个**上限**，即检测到的数值，除非已知该检测并非实际测量。

| 控件 | 范围 | 含义 |
|---|---|---|
| **行数据内存** | 256 MiB 至内存上限，对数刻度 | 适配检查所用的内存预算。超过检测默认值时标为 *（高于检测值）*，到达上限时标为 *（最大）*。 |
| **行数据显存** | 128 MiB 至显存上限，对数刻度 | 适配检查和上传行数据所用的显存预算。超过检测默认值时标为 *（高于检测值）*，到达上限时标为 *（最大）*。 |
| **解析线程** | 1 至逻辑核心数 | 加载时同时解析的文件数，每个文件在其自己的工作线程中运行。默认值为核心数 - 2（四核或以下则为核心数 - 1）。见[解析线程](#parser-threads)（位于开发者参考下）。 |
| 数据来源行 | | 每个数值的来源（`内存：…。显存：…。CPU：…。`）。 |
| **重新检测** | | 向开发服务器请求新的内存读数，并重新计算所有预算。 |
| 显卡名称 | | 适配器的简称；完整的渲染器字符串显示在提示中。 |

### 提高显存预算 {#raising-the-gpu-budget}

高于检测值的显存预算会按所设定的值生效：适配检查和上传都从同一个函数中取得同样的数值（[`effectiveGpuBudget`](https://github.com/Holdi601/3DHeat/blob/main/src/render/budget.ts)），该函数只将其限制在滑块所能达到的显存上限之内。因此，通过检查的加载会被完整上传。超过检测值后，滑块会显示 *（高于检测值）*：此时该数字是你对显卡的判断，而不是测量值；把它设置得高于显卡实际能力，可能导致上下文丢失或严重卡顿。

## 超大数据集：可调节的因素 {#huge-datasets-the-levers}

从代价最小到最激进：

1. **减少筛选列。** 每列每行占 4 字节，并需要一次解码。
2. **步长。** 每隔 *N* 行取一行。
3. **不使用时间列。** 没有排序、没有排序上限，也不需要每行 4–8 字节的时间和生命周期——但也没有时间线。
4. **提高预算**，前提是你确知内存足够。

在渲染时，超大数据集通过采样和渐进式累积来处理，而不是通过缩减数据来处理；见[采样与预算](sampling-and-budgets.md)。

## 开发者参考 {#for-developers}

### 解析线程 {#parser-threads}

加载多个文件时，最多会同时解析 **解析线程** 数量的文件，每个文件都在该次加载由导入工作线程启动的解析工作线程中运行（[`ingestFiles.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/data/ingestFiles.ts)，`parseInOrder`）。当为 1 时，或只有一个文件时，文件会在导入工作线程本身中依次解析。

同时运行多个文件并不会放宽适配检查：

- **构建器先被计入。** 合并后的列在读取第一个文件之前，就已为整个选择分配好，因此正在处理的文件只能使用内存预算在其旁边留下的部分（`parseHeadroom`）：位置、64 位时间、视角、人员、32 位分组、会话、筛选列和 `Source file`，按每个待加载的行计算——当行数是 CSV 的估计值时，再乘以 2.6，以应对列增长为更大的列。
- **每个文件在开始前预留其成本**（`fileParseBytes`）：其行数（来自 Parquet 页脚；CSV 则按大小取估计值的比例）乘以上述同样的列，再乘以 **8**——即数据块本身、丢弃没有位置的行时旁边的复制，以及解码器的工作集（对于文本列，其工作集远大于其 ID）。步长不会降低这一成本，因为文件是完整读取的，之后才会抽稀。这个 8 是通过测量确定的余量：在 3 或 5 时，三十个解析线程在有人员和会话名称的 8600 万行数据上使标签页超过了其上限；在 8 时则没有。
- **只有预留量能放入剩余空间时，另一个文件才会开始。** 已完成但仍在等待较早文件合并的文件，会一直保留其预留量，直到被合并。
- **总有一个文件在运行。** 当没有任何预留时，下一个文件无论成本如何都会开始——这就是适配检查所允许的逐个加载方式，因此紧张的预算会回落到它，而不是拒绝加载。

*加载时峰值*这一数字是逐个加载的峰值，它出现在排序时，即所有文件都已读完之后。并排解析的文件在读取时可能会超过该数字；只要上文的估计正确，预留量就会把它限制在内存预算之内。

合并顺序取决于所选内容的顺序，而与文件完成的先后无关，因此人员、分组和会话的编号、行以及 `Source file` 的值，都与逐个加载时完全相同。无法读取的文件会被跳过，并像以前一样列出。若某个解析工作线程崩溃，整个加载都会结束，这与导入工作线程崩溃时的行为一致；无论加载如何结束，所有解析工作线程都会在加载结束时被终止。若根本无法启动解析工作线程，则改在导入工作线程中解析这些文件。

### 数值如何检测 {#how-the-figures-are-detected}

[`detectBudgets`](https://github.com/Holdi601/3DHeat/blob/main/src/data/memory.ts) 会在启动时运行，在渲染器创建后再运行一次，以及在点击**重新检测**时运行。

**内存（使用开发服务器）。** `start.bat` 和 `npm run dev` 通过一个能读取电脑内存的进程提供页面，地址为 `/__host/memory`（在 1.5 秒内响应，否则忽略）。默认值为已安装内存的 60% 与当前可用内存的 80% 两者中较小的一个；上限为已安装内存的 60%。当可用内存把默认值压低时，面板会说明这一点，并建议关闭程序后按**重新检测**。

**内存（不使用开发服务器）**（静态部署）：浏览器 API 都不报告可用内存，而 `navigator.deviceMemory` 会被向下取整为 2 的幂，并且 Chrome 和 Edge 将其上限设为 8 GiB。默认值为 `deviceMemory` 的 60%，若浏览器报告了标签页的可用 JS 堆，则进一步以其 4 倍为上限；若什么都没有报告，则为 4 GiB。当 `deviceMemory` 恰好读为 8（即上限）时，该数值会被标记为*已封顶*，上限为默认值的 4 倍，并附注说明：超过默认值的数字是你的断言，而不是测量值。

**无论哪种情况**，内存的默认值和上限都以 **12 GiB** 为限——这是无论电脑配置如何，一个 Chrome 标签页能够持有的最大类型化数组内存（曾有页面达到约 15.75 GB 后失败；12 GiB 为其他所有内容留出了余量），并且永远不低于 256 MiB。

**显存。** 没有任何 Web API 能报告显存。

- 使用开发服务器时，显卡的显存由 `nvidia-smi`（最大的适配器）读取，或在 Windows 上从显示适配器的注册表值 `HardwareInformation.qwMemorySize` 读取。默认值为其 70%，上限为 90%。
- 没有读数时则进行推断：默认 2 GiB；若最大纹理为 16,384 px 或更大（独立显卡），则为 4 GiB；更小则为 1 GiB；或当 WebGPU 的 `maxBufferSize` 的 8 倍更大时，则取该值。此时上限为推断值的 8 倍，因为推断只能区分集成显卡与独立显卡，无法更精确。面板会说明该数值为推断得出。
- 永远不低于 128 MiB。

**CPU。** `navigator.hardwareConcurrency`（未报告时为 4）。

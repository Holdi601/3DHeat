# 半浮点累积

有些显卡只能把热度保存在小的 16 位数字中，这可能会截断或舍入最热的地方。查看器会缩放这些数字，使这一问题不会显现出来。你不需要做任何事情；本页面向开发者。

## 开发者须知 {#for-developers}

无法混合到 32 位浮点纹理的设备（WebGPU 上没有 `float32-blendable` 和 `float32-filterable`，WebGL2 上没有 `EXT_float_blend`）会使用 **16 位浮点**（`r16float`）热度目标：最大值 65,504，尾数 11 位。密集区域的值可以达到几十万，所以 16 位目标既会**截断**又会**舍入**，而且舍入误差随数值增大：表现非常特别——最密集的区域显示得比实际冷得多，而稀疏区域看起来正常。有两种机制来处理它；只有两者都生效，画面才是正确的。

### 范围：对每次喷溅施加增益 {#range-a-gain-on-every-splat}

每次喷溅都会乘以一个**增益**，合成时再把它除回去，这样场就处于半浮点能很好处理的数量级内（[`heatGain`](https://github.com/Holdi601/3DHeat/blob/main/src/render/engine.ts)）：

```
estimate = 该数据集、半径和中心强度的解析饱和估计
gain     = 2 ^ round(log2(2048 / estimate))，指数限制在 -20..20
```

2048 使得在达到 65,504 之前，色带顶端之上还留有约 32 倍的余量。增益是 **2 的幂**，因此估计值的微小漂移不会改变它，也不会改变累积缓冲区；它也是[几何签名](accumulation.md#what-restarts-it)的一部分，所以一旦改变，就会重新开始累积。

它锚定在解析估计上，并且刻意**不**锚定在饱和点上。饱和是在合成时应用的，正是为了使拖动它永远不会重新开始收敛；如果增益随它一起移动，缓冲区仍会保存以旧增益写入的值，而合成却除以新增益，两个误差会精确地相互抵消，滑块看起来就像没有任何作用。

在 32 位目标上，增益始终为 1。

### 精度：从零开始的部分帧 {#precision-partial-frames-from-zero}

以 1/n 权重合并进累加器的一帧，会先从零喷溅到一个**临时目标**中，然后再混合进去，而不是直接以 1/n 的权重喷溅进累加器（[累积](accumulation.md#why-each)）。如果直接喷溅，每个精灵的贡献只有它所加入的运行总和的 1/n 大小，而半浮点会把这些数值舍掉——像素越密，问题越严重。从零开始的话，每个加数都与它所加入的总和相当，这与单帧已经在做的运算相同。

### 实测效果 {#measured-effect}

在一个密集的合成场景上，以对应单位读取场的数值：

| | p50 | p90 | p99 | max |
|---|---|---|---|---|
| 32 位（参考） | 6051 | 60742 | 121199 | 232744 |
| 16 位，修复前 | 1372 | 6972 | 7840 | 7840 |
| 16 位，修复后 | 5996 | 59666 | 118824 | 210357 |

峰值从偏低 30 倍变为 0.90 倍，合成后的帧与 32 位的帧在平均亮度的 0.1% 以内一致。

### 测试 {#testing-it}

`?heat=f16` 会在任一后端上强制使用这条路径——如果没有这个开关，只有较弱显卡才会运行的运算就只能由运行它们的人来测试。`npm run smoke:f16` 会用它运行整个浏览器测试套件。

读回会撤销增益：自动曝光会用它除以读取的场，`engine.readHeatProbe()` 则把它传给渲染器——[标尺的实时热度读数](measure.md#notes)也是以这种方式读取的。

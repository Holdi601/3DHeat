# 采样与预算

当一帧中要画的点太多时，查看器会取一个均匀的样本，并让每个点代表更多的数据，使画面保持正确。控制器会调整它绘制的数量，使查看器保持帧率。

## 性能面板控件 {#performance-panel-controls}

| 控件 | 默认值 | 范围（拖动） |
|---|---|---|
| **每帧绘制所有行** | 开 | |
| **自适应预算** | 开 | |
| **目标 FPS** | 60 | 20-240（1000） |
| **初始精灵数/帧**（自适应时）或 **精灵数/帧** | 4.00M | 65,536-268,435,456，对数刻度（268,435,456） |
| **热度分辨率** | 100% | 25-100%，再乘以自适应第二阶段的比例 |
| **渐进细化** | 开 | 关：每一帧都是新的单帧估计（用于查看原始样本）。 |

另见[性能面板与统计](performance-and-stats.md)。

## 开发者信息 {#for-developers}

### 候选行 {#candidate-rows}

行按时间升序存储。时间线窗口 [*lo*, *hi*] 通过对时间列进行两次二分查找，变成一个行范围（[`candidateRange`](https://github.com/Holdi601/3DHeat/blob/main/src/render/sampling.ts)）；没有时间列时，每一行都是候选行。这些就是统计叠加中的**窗口内行数**。逐行测试——筛选、分组、拆分、剔除、切片、生命周期——稍后在着色器中进行；未通过测试的行只消耗一次顶点调用，不产生片段。

### 采样计划 {#the-sampling-plan}

[`planFrame`](https://github.com/Holdi601/3DHeat/blob/main/src/render/sampling.ts) 把候选范围划分为**每块 4,096 个连续行**的块，并根据该帧的精灵预算决定绘制多少块：

- 如果预算能覆盖所有块，则全部绘制——该帧是精确的。
- 否则，块会以均匀的步长取遍整个范围，并带有一个抖动偏移，该偏移每帧按黄金分割比前进，因此相邻的帧覆盖不同的块，所有帧的并集会均匀填满。这是一种**分层**采样：时间范围的每个部分都在每一帧中有代表。

每个被绘制行的热度都会乘以**候选数 / 提交数**，因此在任何预算下，一帧的期望热度都是精确的；只有噪声取决于预算。行以 8,388,608 个为一块存储（见 [GPU 内存驻留](gpu-memory.md)）；块在跨越数据块的地方被切分，每个数据块获得它必须绘制的块起点列表。

一个计划最多可以包含 65,536 个块——即 268,435,456 个精灵——因为两个后端都保存着固定 65,536 槽位的块起点缓冲区。超出的请求会被限制在这一上限，不足的部分会如实表现为需要更多帧才能收敛。

### 每帧绘制所有行 {#draw-every-row-each-frame}

**性能 → 每帧绘制所有行**（默认**开**）：预算成为下限而不是上限，开始新估计的帧会绘制它负责的每一行（最多到 2.68 亿的上限）。

原因：摄像机移动会丢弃累积结果，因此移动中的帧是一次单帧估计，其噪声取决于它绘制了多少数据——只绘制四分之一时，你看到的是四分之一数据以明亮的加权点呈现，这正是移动视图闪烁的原因。全部绘制则让每一帧都是完成的画面。代价是帧时间随窗口内数据的大小而变化；可以调节的手段是更窄的时间窗口、筛选，或距离剔除，它们减少候选行，而不是把它们更稀疏地采样。

在无法一次承担整个场的硬件上请关闭它：此时*精灵数/帧*就是真正的限制，视图会在几个静止帧中逐步收敛。

在高端桌面 GPU、4K 画布、大型关卡、半径为 1 m（约一两个像素）的精灵上，完整计划的开销测得大约为：每帧 1 亿个精灵时 30 fps，2 亿个时 15 fps，最高 2.68 亿个时约 12 fps。精灵如此之小时，顶点阶段就是全部开销，热度分辨率没有任何影响；精灵较大时，开销来自填充：8M 个半径为 100 m 的精灵，在全热度分辨率下每帧耗时 2.5 s，在 25% 时为 170 ms。因此**每帧绘制所有行**从 6,700 万开始，帧时间低于 150 ms 时每帧增加四分之一，超过 400 ms 时减半，这样一个很重的视图就不会使单帧超过 GPU 看门狗所允许的时长。

### 自适应预算 {#the-adaptive-budget}

**性能 → 自适应预算**（默认开）会调整精灵预算，使其保持在**目标 FPS**（[`BudgetController`](https://github.com/Holdi601/3DHeat/blob/main/src/render/sampling.ts)）。在方框回放中和视频渲染期间，它处于空闲状态。

输入是经过平滑的帧时间（90% 旧值 + 10% 新值，单帧上限为 2 s），目标为 1000 / max(15, 目标 FPS) ms。

**第一阶段——精灵。** 每一帧，预算乘以 `1 + (目标 / 帧时间 - 1) × 增益`；速度过慢时增益为 0.35，有余量时为 0.08；每帧限制在 0.5-1.25 倍之间，并限制在 65,536-268,435,456 个精灵之间。

**第二阶段——分辨率。** 只有当预算已经降到下限、而帧仍然慢了 10% 以上时，热度缓冲区的分辨率才会下降，每帧降低 8%，最低降到画布的 25%；当有 30% 的余量时，每帧恢复 4%。片段开销随分辨率的平方下降，在平滑的颜色带下几乎看不出来。（在软件渲染下、1,000 万行、过大精灵的条件下测得：每帧从 141 ms 降到 17 ms。）比例会取整到十六分之一；叠加中的*热度分辨率*会显示它。

**放弃。** 无论是精灵造成的慢帧，还是很重的关卡造成的慢帧，外观都一样——没有分阶段的计时。如果预算停在下限，且帧时间连续 30 帧都低于目标的 70%，说明瓶颈不是精灵：控制器会切换到**爬升**模式，每 14 帧把预算乘以 1.5 并恢复分辨率，只要帧时间保持在下限时的 1.5 倍以内。如果爬升导致的情况比这更糟，它会退回到 60% 并恢复正常控制；达到目标则结束爬升。

关闭自适应预算时，预算就是简单的**精灵数/帧**。

开启*每帧绘制所有行*时，自适应预算仍然运行，但精确规则会把预算提高到覆盖所有候选行，因此实际上它只控制分辨率阶段，以及不开始新估计的帧。

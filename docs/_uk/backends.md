# Два рушії

Браузер може дозволити сторінці використовувати відеокарту двома способами: WebGPU (новіший) і WebGL2. Переглядач може використовувати обидва і сам обирає найкращий, тож зазвичай вам нічого не потрібно робити. Щоб побачити, який рушій у вас працює, подивіться **Backend** у накладці статистики (угорі праворуч у вікні).

![Накладка статистики: Backend, FPS, Frame, Rows in window, Sprites / frame, Budget, Heat res, Coverage](../assets/img/en/performance-stats-overlay.webp)

Переглядач має два повні рендерери за одним інтерфейсом ([`types.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/render/types.ts)): **WebGPU** ([`webgpu/`](https://github.com/Holdi601/3DHeat/tree/main/src/render/webgpu)) і **WebGL2** ([`webgl2/`](https://github.com/Holdi601/3DHeat/tree/main/src/render/webgl2)). Обидва малюють однакову картинку за тими самими алгоритмами; шейдери існують у WGSL і GLSL ES 3.00 поруч. Перший рядок накладки статистики, **Backend**, каже, який рушій працює. Якщо навести на нього курсор, побачите причину, чому WebGPU не використано, якщо це сталося.

## Для розробників {#for-developers}

### Як обирається рушій {#how-one-is-chosen}

Полотно може містити лише один тип контексту, тому вибір робиться один раз, перед будь-яким малюванням ([`createRenderer.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/render/createRenderer.ts)):

1. Якщо WebGL2 не примусово вказано: якщо є `navigator.gpu`, запитати адаптер з `powerPreference: 'high-performance'` і пристрій, і створити рендерер WebGPU. Будь-яка помилка запам'ятовується як причина.
2. Якщо WebGPU примусово вказано і він не спрацював, зупинитися: вид показує *Cannot initialise the renderer.* з причиною.
3. Інакше створити рендерер WebGL2 (теж із запитом адаптера з високою продуктивністю). Якщо WebGL2 недоступний або не може малювати в float-текстури (`EXT_color_buffer_float`), вид показує помилку.

`powerPreference: 'high-performance'` не дає ноутбуку з перемикальною графікою передати сторінці інтегрований GPU. Понад це сторінка нічого не вирішує: апаратне прискорення — це налаштування браузера.

### Перемикачі в адресі {#url-switches}

Додайте до адреси сторінки, наприклад `http://127.0.0.1:5273/?backend=webgl2`.

| Параметр | Дія |
|---|---|
| `?backend=webgpu` | Використати WebGPU або видати помилку. |
| `?backend=webgl2` | Використати WebGL2, навіть там, де доступний WebGPU. Так можна відрізнити «це малюється неправильно» від «це малюється неправильно у WebGPU». |
| `?heat=f16` | Примусово використати 16-бітний шлях накопичення тепла на будь-якому рушії ([Накопичення half-float](half-float-accumulation.md)). |
| `?glcheck` | WebGL2: читати помилки GL під час кадру і показувати їх у `renderer.heatDebug`. Вимкнено за замовчуванням, бо `getError` синхронізує конвеєр. |
| `?occdebug=<n>` | Допомога для розробників у WebGL2: замінює тепло значеннями налагодження закриття. Не для звичайного використання. |

### Відмінності, які мають значення {#differences-that-matter}

| | WebGPU | WebGL2 |
|---|---|---|
| Зберігання рядків | Буфери сховища: індекс рядка — це індекс масиву. Запитує найбільше прив'язування буфера сховища адаптера і розміри буферів. | Цілочисельні текстури (8 192 texel завширшки), до яких звертаються з `gl_VertexID` через текстуру індексів блоків для кожного кадру. |
| 32-бітне накопичення тепла | Коли адаптер пропонує і `float32-blendable`, і `float32-filterable` | Коли є `EXT_float_blend` |
| Інакше | 16-бітне (`r16float`) | 16-бітне (`R16F`) |
| Діапазон глибини | [0, 1]; рушій попередньо множить матриці three.js з діапазоном [-1, 1] на перетворення. Без цього паралельна проєкція, чия глибина лінійна, майже повністю опиняється нижче 0 і непомітно обрізається. | [-1, 1], використовується як є |
| Uniform-змінні | Кільце слотів, вирівняних по 256 байт, по одному на кожне малювання, прив'язане через зсув. `queue.writeBuffer` впорядковано в черзі, тож якби один буфер перезаписувався під кожне малювання, кожне малювання читало б останній запис. Блок uniform проходу тепла — рівно один слот по 256 байт. | Звичайні uniform-змінні |
| Ціль тепла нижча за роздільність полотна | Отримує власну текстуру глибини (усі вкладення в проході мають бути однакового розміру) | |
| Захоплення кадру | `captureFrame()` малює композит удруге в позаекранну ціль і зчитує його (headless Chromium малює WebGPU, але ніколи не композитує своє полотно) | Зчитує стандартний буфер кадру на наступному намальованому кадрі |
| Зчитування | Проміжні буфери зберігаються і повторно використовуються; одночасно лише один читач у роботі | `readPixels`, із запитом драйверу, яка пара формату і типу дозволена |

Обидва рушії завантажують таблицю кривих спрайтів як half-float. `queue.writeTexture` у WebGPU копіює сирі байти, тому дані спершу кодуються в binary16 ([`half.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/render/half.ts)).

#### Обмеження текстур {#texture-limits}

`texStorage2D` понад `MAX_TEXTURE_SIZE` не видає помилки: виділення відкидається, наступні завантаження не вдаються, а вибірка повертає нуль. Допоміжна функція WebGL2 [`createTexture`](https://github.com/Holdi601/3DHeat/blob/main/src/render/webgl2/glutil.ts) перевіряє обидва розміри щодо ліміту і видає помилку з розміром. Текстура індексів блоків двовимірна (4 096 завширшки), тож вона не може вийти за ліміт. `src/render/limits.test.ts` фіксує кожен розмір текстури щодо лімітів, які варто підтримувати. Рендерер WebGL2 також відмовляється від пристрою, чий максимальний розмір текстури менший за ширину 8 192 текстури рядків.

### Перевірка обох {#testing-both}

`npm run smoke` запускає справжній застосунок у headless Chromium на WebGL2 (за замовчуванням `http://127.0.0.1:5273/`). Передайте `"http://127.0.0.1:5273/?backend=webgpu"` до `node tools/smoke.mjs` для WebGPU, а `npm run smoke:f16` — для шляху half-float. `tools/probe-webgpu.mjs` і `tools/probe-present.mjs` (перелічені серед інструментів розробника в [Інструменти командного рядка](ref-tools.md)) діагностують доступність адаптера і показу в headless браузерах.

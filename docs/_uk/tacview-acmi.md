# Записи Tacview (ACMI)

Tacview — це програма, яка записує польоти в симуляторах. Її файли закінчуються на `.acmi`. 3DHeat відкриває їх, щоб ви могли побачити, де летів кожен літак.

Записи польотів Tacview завантажуються, як будь-яка таблиця: оберіть або перетягніть `.acmi` (текст, `.txt.acmi` або в zip, `.zip.acmi`) і натисніть **Завантажити**. Далі ви отримаєте тепло всіх польотів, а на вкладці **Матч** — повтор із фігурами, треками і списком подій ([Розбір матчу](match-replay.md)). ACMI — це публічний формат файлів Tacview ([документація](https://www.tacview.net/documentation/acmi/)). DCS (через експортер Tacview), IL-2 Great Battles, Falcon BMS, X-Plane, MSFS та інші записують у ньому, тож переглядач читає будь-який із них.

## Що стає з запису {#what-a-recording-becomes}

Один рядок щоразу, коли записується позиція об'єкта. Один рядок на кожну подію на місці об'єкта. І один рядок, коли об'єкт зникає (`Removed`, там, де він був востаннє). Подія, яка не стосується жодного ще не баченого об'єкта (закладка, повідомлення всім), — це рядок об'єкта `(recording)` у опорній точці. Запис містить власні інструкції читання, тож крок відображення заповнюється сам. Читач записує такі стовпці: `Time`, `X`, `Y`, `Altitude`, `Object`, `Coalition`, `Heading`, `Pitch`, `Roll`, `Type`, `Name`, `Pilot`, `Group`, `Country`, `Color`, `Event`, `Latitude`, `Longitude`, `Recording`, `EventObjects`, `RecordingInfo`, а далі будь-які інші властивості, які є в записі. Їхні ролі:

| Стовпець | Роль | Значення |
|---|---|---|
| Time | час | Секунди після ReferenceTime запису; Unix-секунди, якщо він є, тож годинник показує справжній час. |
| X, Y | позиція | Схід і північ, метри, на площині, що дотикається до Землі в опорній точці запису: відстані й азимути справжні поблизу неї, а на 100 км зміщуються менш ніж на тисячну частину. Північ стає світовим -Z. |
| Altitude | позиція (вгору) | Метри. |
| Object | особа | Пілот і назва об'єкта з його ідентифікатором, наприклад `Viper 1 (F-16C_50) #a01`; безпілотний об'єкт — `(T-90A) #401`. |
| Coalition | команда | Сторона (або колір, якщо коаліції немає). |
| Heading, Pitch | погляд | Градуси; курс 0 — північ. |
| Recording | сесія | Title запису або назва файлу: кілька записів завантажуються поруч, і їхні треки не з'єднуються. |
| Type, Name, Pilot, Group, Country, Color, Event, Roll, Latitude, Longitude | фільтри | Зберігаються для фільтрації. Type і Name вибирають [фігуру](figures.md) кожного об'єкта, Event живить список подій розбору, Roll нахиляє літак. |
| U, V | | Власні плоскі метри гри, якщо вони є в кожному зразку (DCS їх записує). |
| EventObjects | фільтри | Кожен об'єкт, який називає подія (`Message|a01|b02|...`), за ідентифікатором. |
| RecordingInfo | | Власні властивості запису такими, якими вони були в той момент: DataSource, DataRecorder, Author, Category, Briefing, Comments, ... — як JSON. |
| IAS, Mach, AOA, FuelWeight, ... | фільтри | Будь-яка інша числова властивість, яку має запис. |
| Parent, CallSign, LockedTarget, Label, Shape, ... | фільтри | Будь-яка інша текстова властивість запису. Властивість, чиє значення не є числом, — це текст. |

Читаються всі чотири форми позиції Tacview (`lon|lat|alt`, з `u|v`, з `roll|pitch|yaw` і з усіма ними разом із курсом). Порожні поля зберігають останнє значення. `-id` видаляє об'єкт, а ідентифікатор, знову використаний після цього, — це новий об'єкт. Екрановані коми і рядки з продовженням обробляються.

Позиції завжди проєктуються з широти та довготи, ніколи не беруться з U/V. Тож записи з кожної гри мають одну проєкцію з підкладкою справжнього світу.

## Сервери DCS: хто переміг і як закінчився кожен виліт {#dcs-servers-who-won-and-how-each-sortie-ended}

Мультиплеєрний сервер DCS цілодобово записує свої місії через Tacview. Постійний PvP-сервер веде кампанію через багато таких місій: сторона перемагає, коли захоплює кожен аеродром, FARP і зону іншої сторони. Це триває дні й потребує багатьох перезапусків місії. Записи містять польоти, а не кампанію: жодне повідомлення не каже, хто що захопив, аеродроми записано один раз на початку, і ніщо не каже, хто переміг. Конвертер Tacview (`node tools/acmi-to-parquet.mjs`, [`data/dcsOutcome.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/data/dcsOutcome.ts)) додає до кожного рядка те, що можна знати, а те, чого знати не можна, лишає порожнім. Він ніколи не вгадує.

| Стовпець | Значення |
|---|---|
| `server` | сервер або кампанія, із заголовка запису (його Title, Author і Comments називають відомі публічні сервери - Blue Flag, SPS Contention, Growling Sidewinder; інакше Author, що називає когось); `--server Name` дає назву для цілої теки. Запис, чий заголовок не називає сервера - Author на кшталт `Admin`, Title і Comments, яких не пише жоден відомий сервер, - лишається без прив'язки: `server` порожній, навіть якщо його завантажено зі сторінки записів сервера, бо ця сторінка може містити й місії інших спільнот |
| `mission` | Title запису без його версії чи місяця кампанії: `Operation_Example_V7.7.99` стає `Operation Example` |
| `campaign` | раунд кампанії, до якого належить запис, за сервером, мапою і номером: `Example Server North 3`. Один запис - це одна сесія (від перезапуску до перезапуску); раунд триває через багато сесій, дні або тижні |
| `round` | номер цього раунду: власний номер сервера, якщо він його публікує, інакше n-й раунд, побачений на цьому сервері й мапі; з файлу раундів (нижче), без нього порожній |
| `session` | місце запису серед сесій раунду, 1, 2, ...; `sessionStart` - його справжній початок (секунди Unix) |
| `heldRed`, `heldBlue` | спірні місця, які кожна сторона утримувала на початку сесії, з ланцюгового файлу раундів (нижче) |
| `won`, `matchWon` | 1, коли сторона рядка (його Color, Red або Blue) виграла цю кампанію, 0, коли програла; порожні, де жоден файл раундів не називає переможця, і в нейтральних рядках. Кампанія - це водночас раунд і матч, тож обидва стовпці мають однакове значення |
| `roundEndReason` | `capture` для кампанії, виграної захопленням усього |
| `won`, `matchWon` у кожній сесії раунду | результат раунду, записаний у кожному його записі, щойно відомий його кінець |
| `sortie` | у рядках літака: його політ, 1, 2, ... від зльоту до зльоту; час на землі до першого зльоту і після посадки належить до польоту, до якого він відноситься |
| `sortieResult` | як закінчився цей політ: `landed`, `landed damaged` (після влучання в повітрі), `ejected`, `shot down`, `destroyed` (на землі), `crashed`, `despawned` (зник у повітрі без видимої причини - гравець вийшов), `airborne at end`, `no takeoff` |
| `sortieKills` | знищення, зараховані літаку в цьому польоті |

На постійному сервері саме виліт має значення. Фільтруйте за `sortieResult` = `shot down`, щоб побачити, де втрачали польоти, або розбийте тепло за `sortieResult` чи `server` у [розбивці](breakdown.md). Зльоти, посадки, катапультування, знищення й аварії, з яких складається виліт, - це події, які конвертер визначає з того, як рухається літак (вище).

Місця, захоплені між двома сесіями раунду (їх видно з файлу раундів, нижче), стають подіями `capture` на початку пізнішого запису: `Object` `(campaign)`, у тому місці, `Detail` `Red to Blue, between missions`, `Inferred` `between missions`.

Аеродром або FARP, що змінює сторону там, де це видно в записі (записаний знову в кольорі іншої сторони, або видалений і записаний знову на своєму місці в кольорі іншої протягом п'яти хвилин), стає подією `capture` на цьому майданчику: `Event` = `capture`, `Airfield` - його назва, `Detail` `Red to Blue`, `Coalition` - його нова сторона. Майданчик, уперше записаний у якомусь кольорі, - це не захоплення. Сервери, які ми досі переглянули, записують свої майданчики один раз, тож у їхніх записах захоплень немає.

### Файли раундів {#rounds-files}

Файл раундів для кожного сервера каже, які в нього раунди кампанії, хто їх виграв і які сесії має кожен раунд. Він береться з того, що публікує сервер, або з самих записів (нижче).

Хто виграв кампанію - це те, що публікує сервер (журнал кампанії на його вебсторінці), а не щось у записі. Файл раундів несе цю інформацію, і конвертер читає його з `--rounds file.json` (можна дати кілька):

```json
{
  "format": "heat3d-dcs-rounds",
  "version": 1,
  "server": "Example Server",
  "source": "Example Server's public campaign log, read 2026-11-15",
  "rounds": [
    { "id": 41, "title": "^Example-Campaign-North$", "start": "2026-11-01T08:00:00Z", "end": "2026-11-04T19:30:00Z", "winner": "Blue", "endReason": "capture", "state": "won" },
    { "id": 42, "title": "^Example-Campaign-North$", "start": "2026-11-04T19:30:00Z", "end": null, "winner": null, "state": "in progress" }
  ]
}
```

Запис належить до тих раундів свого `server`, чий `title` (регулярний вираз) збігається з його Title. Кожен рядок належить до раунду, в який потрапляє його справжній час: RecordingTime запису плюс секунди рядка, а не ігрова дата місії. Час - у UTC. Раунд без переможця (змінений, ще триває) дає своїм рядкам номер раунду й порожній результат.

Відповідник документа матчу, нижній блок `acmi`, каже, звідки взявся результат, як це робить `result.source` матчу War Thunder: `outcome.result` - це `{ winner, round, endReason, source }`, де `source` - це `source` файлу раундів, або `null`, коли ніщо не назвало переможця. `outcome` також перелічує раунди запису, його захоплення і його вильоти за тим, як вони закінчилися:

```json
"outcome": {
  "server": "Example Server", "mission": "Example-Campaign-North", "kind": null,
  "result": { "winner": "Blue", "round": 41, "endReason": "capture", "source": "Example Server's public campaign log, read 2026-11-15" },
  "rounds": [{ "id": 41, "start": "2026-11-01T08:00:00.000Z", "end": "2026-11-04T19:30:00.000Z", "winner": "Blue", "endReason": "capture", "state": "won" }],
  "captures": 0,
  "sorties": { "landed": 31, "shot down": 12, "ejected": 3, "crashed": 2, "despawned": 9, "no takeoff": 4 }
}
```

Рядок пілота `Viper 1 (F-16C_50) #a01` на синій стороні в цій кампанії тоді має: `server` Example Server, `round` 41, `won` 1, `roundEndReason` capture, `sortie` 2, `sortieResult` landed, `sortieKills` 1.

### Раунди з самих записів {#rounds-from-the-recordings-themselves}

Постійний сервер зберігає свою кампанію між перезапусками, і кожен запис починається з наземних підрозділів і статичних об'єктів обох сторін там, де їх лишила кампанія. `node tools/dcs-campaign-rounds.mjs <out-folder> <folder>...` читає перші хвилини кожного запису ([`data/dcsCampaign.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/data/dcsCampaign.ts)), ставить записи кожного сервера на одній мапі за часом і з'єднує їх у ланцюг:

- **Місця**: земля, поділена на клітинки приблизно по 2 km; клітинка належить стороні, якщо три чверті підрозділів у ній на початку сесії - її. *Спірні* місця - це ті, які бачили в руках обох сторін.
- **Захоплення**: місце, яке на початку наступної сесії утримує інша сторона - захоплене між місіями або під час попередньої.
- **Новий раунд**: сесія, чиї місця відрізняються від місць попередньої більш ніж на 60% - це початкове розташування нового раунду, а не крок старого. Раунд також закінчується, коли сервер переходить на іншу мапу (його сесії починаються після останньої й тривають далі).
- **Хто переміг**: у раунді, що закінчився, - сторона, яка утримувала кожне місце на початку його останньої сесії (`capture`, впевненість висока), інакше сторона, яка утримувала більше спірних місць (середня, якщо вдвічі більше, ніж інша, інакше низька; низька, якщо раунд закінчився зміною мапи). Відкритий раунд не має переможця, але кожна сесія каже, скільки місць утримувала кожна сторона на її початку, тож видно, хто був попереду.
- Сервер, чиї сесії всі починаються однаково, не зберігає стан між ними: його не з'єднують у ланцюг.

Початок останньої сесії може бути за години до кінця раунду, тому впевненість важлива. Перевірка на сервері, який публікує своїх переможців: ланцюг знайшов кожен новий раунд у тій сесії, з якої почався опублікований раунд, а сторона, що була попереду на останньому початку, була опублікованим переможцем у кожному з 9 раундів, які можна було перевірити. `--official file.json` зберігає опубліковані раунди такого сервера і додає до них сесії з ланцюга; поле `validation` у файлі каже, наскільки ланцюг збігся. У вигаданій кампанії:

```json
{ "id": 2, "campaign": "Example Server North 2", "title": "^(?:Example_North_V1\.0)$",
  "start": "2026-11-02T06:00:00.000Z", "end": "2026-11-06T12:00:00.000Z", "winner": "Red", "endReason": null,
  "state": "won (reset)", "confidence": "medium", "ahead": "Red",
  "sessions": [
    { "start": "2026-11-02T06:00:00.000Z", "red": 12, "blue": 11, "redAll": 30, "blueAll": 28, "captures": [] },
    { "start": "2026-11-02T12:00:00.000Z", "red": 14, "blue": 9, "redAll": 32, "blueAll": 26,
      "captures": [{ "lat": 42.36, "lon": 42.02, "from": "Blue", "to": "Red" }, { "lat": 42.4, "lon": 41.98, "from": "Blue", "to": "Red" }] }
  ] }
```

### Перегляд раунду кампанії як серії {#watching-a-campaign-round-as-a-series}

Завантажте записи одного раунду разом (файли з однаковим `campaign`), і переглядач відтворить їх як одну серію: сесія за сесією в їхньому справжньому порядку, а години чи дні між двома сесіями скорочено до перерви в одну хвилину. Шкала часу позначає початок кожної сесії жовтим, а перерви - темними смугами. Годинник каже, яка сесія грає, і її справжню дату (`session 4/12 · 2026-11-02 12:38 UTC`). Тепло, повтор, фільтри та Insights працюють на всій серії, як на будь-яких завантажених даних. Розділ **Раунд кампанії** на вкладці **Матч** перелічує сесії з їхніми датами, скільки спірних місць кожна сторона утримувала на кожному початку (також як графік за весь раунд) і скільки з них захопили перед ним; клік переходить до початку сесії. Запис, завантажений окремо, каже там, який це раунд і яка сесія. Записи різних раундів, завантажені разом, - це не серія: кожен починається з нуля, як окремі матчі. Завантажувач багатьох матчів (**Багато матчів одразу**) теж відтворює раунд як серію, потоково і з розміром під GPU, для раундів на багато гігабайтів.

Місця, які змінювали власника під час раунду, намальовано на мапі як зони захоплення. Кожна зона має колір сторони, яка утримувала її на початку сесії, що грає, і колір змінюється на межах сесій; кожна зміна - це захоплення у списку подій повтору. Їх визначають із завантажених рядків (наземні підрозділи і статичні об'єкти кожної сесії в її перші хвилини, у клітинках приблизно по 2 km, як це робить ланцюг), тож їм потрібен повний завантажувач (завантажувач багатьох матчів зберігає надто мало з кожного рядка).

**Завантаження всього раунду з одного його запису.** У звичайному браузері переглядач не може відкривати файли, яких ви не вибрали: завантажте файли раунду разом. Коли його обслуговує локальний сервер переглядача (`npm run dev` або `npm run preview`), він може: додайте до ігнорованого git файлу `tools/local-data.json` запис `campaigns`, що називає теку файлів раундів і теки конвертованих записів. Тоді розділ «Раунд кампанії» окремого запису пропонує **Завантажити весь раунд**: він отримує знайдені там сесії раунду й завантажує їх завантажувачем багатьох матчів:

```json
"campaigns": { "rounds": "D:/dcs/rounds", "recordings": ["D:/dcs/converted"] }
```

Обслуговуються лише записи, які називає файл раундів (`tools/campaign-files.mjs`); сесію, не знайдену в цих теках, враховують, але не завантажують.

Що публікують відомі сервери:

| Сервер | Раунд | Як сторона перемагає | Де можна прочитати переможця |
|---|---|---|---|
| SPS Contention | кампанія на одній мапі й в одній епосі (дні), через багато перезапусків | захоплено кожен аеродром, FARP і опорний пункт; кампанію, що закінчилася без переможця, змінили | публічний журнал кампаній сервера (переможець, початок, кінець кожної кампанії) |
| Blue Flag | раунд кампанії через багато 5-годинних місій; `_YYYY_MM` у Title з кожним перезапуском просувається на один місяць | захоплено кожну позицію ворога; старіші раунди називали сторону, яка утримувала більше після певного часу | досі не знайдено в опублікованому вигляді; ланцюг записів стежить за кожним раундом і за тим, хто скільки утримує на кожному початку |
| Growling Sidewinder | запуск місії (6 годин) місії відкритого конфлікту | захоплено зони й аеродроми | його сторінка статистики показує пілотів, а не результати; кожна сесія починається однаково, тож жоден раунд не охоплює кілька сесій: порожньо |
| Місії проти ШІ (місії із захопленням зон) | запуск місії | сторона гравців проти ШІ місії: немає результату PvP | порожньо |
| Без прив'язки (заголовок не називає сервера) | - | - | порожньо, `server` теж порожній |

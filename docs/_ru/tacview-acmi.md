# Записи Tacview (ACMI)

Tacview — это программа, которая записывает полёты в авиасимуляторах; её файлы оканчиваются на `.acmi`. 3DHeat открывает их, чтобы вы могли видеть, где летала каждая машина.

Записи полётов Tacview загружаются как любая таблица: выберите или перетащите `.acmi` (текстовый, `.txt.acmi` или в архиве, `.zip.acmi`) и нажмите **Загрузить**. Вы получите тепло всех полётов, а на вкладке **Матч** — повтор с фигурами, треками и списком событий ([Повтор матча](match-replay.md)). ACMI — открытый формат файлов Tacview ([документация](https://www.tacview.net/documentation/acmi/)); DCS (через экспортёр Tacview), IL-2 Great Battles, Falcon BMS, X-Plane, MSFS и другие пишут в этом формате, поэтому просмотрщик читает любой из них.

## Во что превращается запись {#what-a-recording-becomes}

Одна строка каждый раз, когда записывается положение объекта, одна строка на событие в месте объекта и одна строка, когда объект уходит (`Removed`, там, где он был последним). Событие, не относящееся ни к одному ещё не виденному объекту, — закладка, сообщение всем, — это строка объекта `(recording)` в опорной точке. Запись содержит собственные инструкции чтения, поэтому шаг сопоставления заполняется сам. Читатель записывает такие столбцы: `Time`, `X`, `Y`, `Altitude`, `Object`, `Coalition`, `Heading`, `Pitch`, `Roll`, `Type`, `Name`, `Pilot`, `Group`, `Country`, `Color`, `Event`, `Latitude`, `Longitude`, `Recording`, `EventObjects`, `RecordingInfo`, а затем любые другие свойства, которые есть в записи. Их роли:

| Столбец | Роль | Значение |
|---|---|---|
| Time | время | Секунды после ReferenceTime записи; у записи с ним — Unix-секунды, так что часы показывают реальное время. |
| X, Y | положение | Восток и север, метры, на плоскости, касающейся Земли в опорной точке записи: расстояния и курсы верны рядом с ней, а на 100 км уходят меньше чем на одну тысячную. Север становится -Z мира. |
| Altitude | положение (вверх) | Метры. |
| Object | персона | Пилот и имя объекта с его идентификатором, например `Viper 1 (F-16C_50) #a01`; необитаемый объект `(T-90A) #401`. |
| Coalition | команда | Сторона (или цвет, если коалиции нет). |
| Heading, Pitch | взгляд | Градусы; курс 0 — это север. |
| Recording | сессия | Title записи или имя файла: несколько записей загружаются рядом, не сливая свои треки. |
| Type, Name, Pilot, Group, Country, Color, Event, Roll, Latitude, Longitude | фильтры | Сохраняются для фильтрации; Type и Name выбирают [фигуру](figures.md) каждого объекта, Event подаёт список событий разбора, Roll наклоняет самолёт. |
| U, V | | Собственные плоские метры игры, когда они есть у каждого отсчёта (DCS их пишет). |
| EventObjects | фильтры | Каждый объект, который называет событие (`Message|a01|b02|...`), по идентификатору. |
| RecordingInfo | | Собственные свойства записи такими, какими они были в этот момент — DataSource, DataRecorder, Author, Category, Briefing, Comments, ... — в виде JSON. |
| IAS, Mach, AOA, FuelWeight, ... | фильтры | Любое другое числовое свойство записи. |
| Parent, CallSign, LockedTarget, Label, Shape, ... | фильтры | Любое другое текстовое свойство записи; свойство, значение которого не число, считается текстом. |

Читаются все четыре формы положения Tacview (`lon|lat|alt`, с `u|v`, с `roll|pitch|yaw` и со всеми ними и курсом); пустые поля сохраняют последнее значение; `-id` удаляет объект, а идентификатор, использованный снова после этого, — это новый объект. Экранированные запятые и продолженные строки обрабатываются.

Положения всегда проецируются из широты и долготы, никогда не берутся из U/V, поэтому записи из всех игр используют одну проекцию с подложкой настоящего мира.

## DCS-серверы: кто победил и чем закончился каждый вылет {#dcs-servers-who-won-and-how-each-sortie-ended}

Многопользовательский сервер DCS записывает свои миссии в Tacview круглые сутки, а постоянный PvP-сервер ведёт кампанию через многие из них: сторона побеждает, когда захватит все аэродромы, FARP и зоны другой стороны, а на это уходят дни и много перезапусков миссии. В записях есть полёты, но не кампания: ни одно сообщение не говорит, кто что захватил, аэродромы записываются один раз в начале, и ничто не говорит, кто победил. Конвертер Tacview (`node tools/acmi-to-parquet.mjs`, [`data/dcsOutcome.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/data/dcsOutcome.ts)) добавляет в каждую строку то, что можно знать, и оставляет пустым то, чего знать нельзя, — он никогда не угадывает.

| Столбец | Значение |
|---|---|
| `server` | сервер или кампания, из заголовка записи (его Title, Author и Comments называют известные публичные серверы — Blue Flag, SPS Contention, Growling Sidewinder; иначе Author, который кого-то называет); `--server Name` задаёт его для всей папки. Запись, заголовок которой не называет ни одного сервера, — Author вроде `Admin`, Title и Comments, каких не пишет ни один известный сервер, — остаётся без привязки: `server` пуст, даже если она скачана со страницы записей какого-то сервера, ведь на этой странице могут быть и миссии других сообществ |
| `mission` | Title записи без версии и месяца кампании: `Operation_Example_V7.7.99` становится `Operation Example` |
| `campaign` | раунд кампании, к которому относится запись, по серверу, карте и номеру: `Example Server North 3`. Одна запись — одна сессия (от перезапуска до перезапуска); раунд идёт через много сессий, дни или недели |
| `round` | номер этого раунда: собственный номер сервера, если он его публикует, иначе n-й раунд, замеченный на этом сервере и карте; из файла раундов (ниже), без него пусто |
| `session` | место записи среди сессий раунда, 1, 2, ...; `sessionStart` — её настоящее начало (секунды Unix) |
| `heldRed`, `heldBlue` | спорные места, которые каждая сторона удерживала в начале сессии, из связанного в цепочку файла раундов (ниже) |
| `won`, `matchWon` | 1, когда сторона строки (её Color, Red или Blue) выиграла эту кампанию, 0, когда проиграла; пусто там, где ни один файл раундов не называет победителя, и в нейтральных строках. Кампания — это одновременно и раунд, и матч, поэтому в обоих одно и то же |
| `roundEndReason` | `capture` для кампании, выигранной захватом всего |
| `won`, `matchWon` в каждой сессии раунда | итог раунда, записанный в каждую его запись, как только известен его конец |
| `sortie` | в строках самолёта: его вылет, 1, 2, ... от взлёта до взлёта; время на земле до первого взлёта и после посадки относится к вылету, которому оно принадлежит |
| `sortieResult` | чем закончился этот вылет: `landed`, `landed damaged` (после попадания в воздухе), `ejected`, `shot down`, `destroyed` (на земле), `crashed`, `despawned` (исчез в воздухе без видимой причины — игрок вышел), `airborne at end`, `no takeoff` |
| `sortieKills` | победы, засчитанные самолёту в этом вылете |

На постоянном сервере вылет — это единица, которая что-то значит: отфильтруйте `sortieResult` = `shot down`, чтобы увидеть, где терялись полёты, или разбейте тепло по `sortieResult` или `server` в [разбивке](breakdown.md). Взлёты, посадки, катапультирования, победы и крушения, из которых он состоит, — это события, которые конвертер выводит из того, как движется самолёт (выше).

Места, захваченные между двумя сессиями раунда, — известные из файла раундов, ниже, — это события `capture` в начале более поздней записи: `Object` `(campaign)`, на этом месте, `Detail` `Red to Blue, between missions`, `Inferred` `between missions`.

Аэродром или FARP, который меняет сторону там, где это видно в записи, — записан снова в другом цвете или удалён и в течение пяти минут снова записан на своём месте в другом цвете, — становится событием `capture` на площадке: `Event` = `capture`, `Airfield` — её название, `Detail` `Red to Blue`, `Coalition` — её новая сторона. Площадка, впервые записанная в каком-то цвете, — это не захват. Серверы, которые мы до сих пор смотрели, записывают свои площадки один раз, поэтому в их записях нет захватов.

### Файлы раундов {#rounds-files}

Файл раундов говорит для каждого сервера, какие у него раунды кампании, кто их выиграл и какие сессии у каждого из них. Он берётся из того, что публикует сервер, или из самих записей (ниже).

Кто выиграл кампанию, публикует сервер — журнал кампании на своей веб-странице, — в записи этого нет. Это несёт файл раундов, а конвертер читает его через `--rounds file.json` (можно указать несколько):

```json
{
  "format": "heat3d-dcs-rounds",
  "version": 1,
  "server": "Example Server",
  "source": "Example Server's public campaign log, read 2026-11-15",
  "rounds": [
    { "id": 41, "title": "^Example-Campaign-North$", "start": "2026-11-01T08:00:00Z", "end": "2026-11-04T19:30:00Z", "winner": "Blue", "endReason": "capture", "state": "won" },
    { "id": 42, "title": "^Example-Campaign-North$", "start": "2026-11-04T19:30:00Z", "end": null, "winner": null, "state": "in progress" }
  ]
}
```

Запись относится к раундам своего `server`, чей `title` (регулярное выражение) совпадает с её Title; каждая строка — к раунду, в который попадает её настоящее время: RecordingTime записи плюс секунды строки, а не дата миссии в игре. Время указано в UTC. Раунд без победителя (сменён, ещё идёт) даёт своим строкам номер раунда и пустой итог.

Аналог документа матча, нижний блок `acmi`, говорит, откуда взят итог, как `result.source` у матча War Thunder: `outcome.result` — это `{ winner, round, endReason, source }`, `source` — это `source` файла раундов или `null`, если ничто не назвало победителя. `outcome` также перечисляет раунды записи, её захваты и её вылеты по тому, чем они закончились:

```json
"outcome": {
  "server": "Example Server", "mission": "Example-Campaign-North", "kind": null,
  "result": { "winner": "Blue", "round": 41, "endReason": "capture", "source": "Example Server's public campaign log, read 2026-11-15" },
  "rounds": [{ "id": 41, "start": "2026-11-01T08:00:00.000Z", "end": "2026-11-04T19:30:00.000Z", "winner": "Blue", "endReason": "capture", "state": "won" }],
  "captures": 0,
  "sorties": { "landed": 31, "shot down": 12, "ejected": 3, "crashed": 2, "despawned": 9, "no takeoff": 4 }
}
```

Строка пилота `Viper 1 (F-16C_50) #a01` на синей стороне в этой кампании тогда выглядит так: `server` Example Server, `round` 41, `won` 1, `roundEndReason` capture, `sortie` 2, `sortieResult` landed, `sortieKills` 1.

### Раунды из самих записей {#rounds-from-the-recordings-themselves}

Постоянный сервер сохраняет свою кампанию между перезапусками, и каждая запись начинается с наземных юнитов и статических объектов обеих сторон там, где их оставила кампания. `node tools/dcs-campaign-rounds.mjs <out-folder> <folder>...` читает первые минуты каждой записи ([`data/dcsCampaign.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/data/dcsCampaign.ts)), выстраивает записи каждого сервера на одной карте по времени и связывает их в цепочку:

- **Места**: земля в ячейках около 2 km; ячейка принадлежит стороне, если ей принадлежат три четверти юнитов, которые там есть в начале сессии. *Спорные* места — те, которые видели в руках обеих сторон.
- **Захваты**: место, которое в начале следующей сессии удерживает другая сторона, — захваченное между миссиями или во время предыдущей.
- **Новый раунд**: сессия, места которой отличаются от мест предыдущей больше чем на 60 %, — это начальная расстановка нового раунда, а не шаг старого. Раунд также заканчивается, когда сервер переходит на другую карту (её сессии начинаются после последней и идут дальше).
- **Кто победил**: у закончившегося раунда — сторона, которая удерживала все места в начале его последней сессии (`capture`, уверенность высокая), иначе сторона, которая удерживала больше спорных мест (средняя, если их вдвое больше, чем у другой стороны, иначе низкая; низкая, если раунд закончился сменой карты). У открытого раунда нет победителя, но каждая сессия говорит, сколько мест удерживала каждая сторона в её начале, поэтому видно, кто был впереди.
- Сервер, все сессии которого начинаются одинаково, не хранит состояние между ними: в цепочку он не связывается.

Начало последней сессии может быть за много часов до конца раунда, поэтому уверенность важна. Проверено на сервере, который публикует своих победителей: цепочка нашла каждый новый раунд в той сессии, где начался опубликованный раунд, а сторона, которая была впереди при последнем начале, оказалась опубликованным победителем во всех 9 раундах, которые удалось проверить. `--official file.json` сохраняет опубликованные раунды такого сервера и добавляет к ним сессии из цепочки; `validation` в файле говорит, насколько цепочка совпала. В выдуманной кампании:

```json
{ "id": 2, "campaign": "Example Server North 2", "title": "^(?:Example_North_V1\.0)$",
  "start": "2026-11-02T06:00:00.000Z", "end": "2026-11-06T12:00:00.000Z", "winner": "Red", "endReason": null,
  "state": "won (reset)", "confidence": "medium", "ahead": "Red",
  "sessions": [
    { "start": "2026-11-02T06:00:00.000Z", "red": 12, "blue": 11, "redAll": 30, "blueAll": 28, "captures": [] },
    { "start": "2026-11-02T12:00:00.000Z", "red": 14, "blue": 9, "redAll": 32, "blueAll": 26,
      "captures": [{ "lat": 42.36, "lon": 42.02, "from": "Blue", "to": "Red" }, { "lat": 42.4, "lon": 41.98, "from": "Blue", "to": "Red" }] }
  ] }
```

### Просмотр раунда кампании как серии {#watching-a-campaign-round-as-a-series}

Загрузите записи одного раунда вместе — файлы с одинаковым `campaign`, — и программа проиграет их как одну серию: сессию за сессией в их настоящем порядке, а часы или дни между двумя сократит до перерыва в одну минуту. Шкала времени отмечает начало каждой сессии жёлтым, а перерывы — тёмными полосами, а часы показывают, какая сессия идёт, и её настоящую дату (`session 4/12 · 2026-11-02 12:38 UTC`). Тепло, повтор, фильтры и Выводы работают на всей серии, как на любых загруженных данных. Раздел **Раунд кампании** на вкладке Матч перечисляет сессии с их датами, сколько спорных мест удерживала каждая сторона при каждом начале — также в виде графика за раунд — и сколько было захвачено перед ним; щелчок переходит к началу сессии. Запись, загруженная отдельно, говорит там, какой это раунд и какая сессия. Записи разных раундов, загруженные вместе, — не серия: каждая начинается с нуля, как отдельные матчи. Загрузчик многих матчей (**Много матчей сразу**) тоже проигрывает раунд как серию, потоком и с учётом видеокарты, для раундов во много гигабайт.

Места, которые за раунд сменили владельца, рисуются на карте как зоны захвата, окрашенные по стороне, которая удерживала каждое из них в начале идущей сессии, и переключаются на границах сессий; каждая смена — это захват в списке событий повтора. Они выводятся из загруженных строк — наземных юнитов и статических объектов каждой сессии в её первые минуты, в ячейках около 2 km, как это делает цепочка, — поэтому им нужен полный загрузчик (загрузчик многих матчей хранит слишком мало от каждой строки).

**Загрузка всего раунда из одной его записи.** В обычном браузере программа не может открыть файлы, которые вы не выбрали: загрузите файлы раунда вместе. Если её отдаёт локальный сервер программы (`npm run dev` или `npm run preview`), это возможно: добавьте в игнорируемый git файл `tools/local-data.json` запись `campaigns`, которая называет папку с файлами раундов и папки с конвертированными записями, и раздел Раунд кампании отдельной записи предложит **Загрузить весь раунд**, скачает найденные там сессии раунда и загрузит их загрузчиком многих матчей:

```json
"campaigns": { "rounds": "D:/dcs/rounds", "recordings": ["D:/dcs/converted"] }
```

Отдаются только записи, которые называет файл раундов (`tools/campaign-files.mjs`); сессия, не найденная в этих папках, учитывается в подсчёте, но не загружается.

Что публикуют известные серверы:

| Сервер | Раунд | Как сторона побеждает | Где можно узнать победителя |
|---|---|---|---|
| SPS Contention | кампания на одной карте и в одной эпохе (дни), через много перезапусков | захвачены все аэродромы, FARP и опорные пункты; кампанию, закончившуюся без победителя, сменили | публичный журнал кампаний сервера (победитель, начало и конец каждой кампании) |

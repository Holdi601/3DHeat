# Два бэкенда

Браузер может дать странице использовать видеокарту двумя способами: WebGPU (новее) и WebGL2. Просмотрщик умеет оба и сам выбирает лучший, поэтому обычно ничего делать не нужно. Чтобы увидеть, какой из них работает, посмотрите строку **Бэкенд** в оверлее статистики (вверху справа в области просмотра).

![Оверлей статистики: Бэкенд, FPS, Кадр, Строк в окне, Спрайтов / кадр, Бюджет, Разрешение тепла, Покрытие](../assets/img/en/performance-stats-overlay.webp)

За одним интерфейсом у просмотрщика стоят два полных рендерера ([`types.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/render/types.ts)): **WebGPU** ([`webgpu/`](https://github.com/Holdi601/3DHeat/tree/main/src/render/webgpu)) и **WebGL2** ([`webgl2/`](https://github.com/Holdi601/3DHeat/tree/main/src/render/webgl2)). Оба рисуют одну и ту же картинку одними и теми же алгоритмами; шейдеры есть и на WGSL, и на GLSL ES 3.00 рядом друг с другом. Первая строка оверлея статистики, **Бэкенд**, показывает, какой из них работает; если навести на неё курсор, появится причина, по которой WebGPU не использовался, если он не использовался.

## Для разработчиков {#for-developers}

### Как выбирается бэкенд {#how-one-is-chosen}

Холст может держать только один вид контекста, поэтому выбор делается один раз, до любого рисования ([`createRenderer.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/render/createRenderer.ts)):

1. Если WebGL2 не задан принудительно: если есть `navigator.gpu`, запросить адаптер с `powerPreference: 'high-performance'` и устройство и создать рендерер WebGPU. Любая ошибка запоминается как причина.
2. Если WebGPU был задан принудительно и не сработал, остановиться: в области просмотра выводится *Не удалось инициализировать рендерер.* с причиной.
3. Иначе создать рендерер WebGL2 (тоже с запросом адаптера высокой производительности). Если WebGL2 недоступен или не может рисовать в float-текстуры (`EXT_color_buffer_float`), область просмотра показывает ошибку.

`powerPreference: 'high-performance'` не даёт ноутбуку с переключаемой графикой отдать странице встроенный GPU. Дальше страница ничего не решает: аппаратное ускорение — это настройка браузера.

### Переключатели в адресе {#url-switches}

Добавьте к адресу страницы, например `http://127.0.0.1:5273/?backend=webgl2`.

| Параметр | Действие |
|---|---|
| `?backend=webgpu` | Использовать WebGPU или выдать ошибку. |
| `?backend=webgl2` | Использовать WebGL2, даже если WebGPU доступен — отделяет «здесь рисуется неверно» от «здесь неверно рисуется на WebGPU». |
| `?heat=f16` | Принудительно включить путь накопления с 16-битной точностью на любом бэкенде ([Накопление в half-float](half-float-accumulation.md)). |
| `?glcheck` | WebGL2: читать ошибки GL во время кадра и показывать их в `renderer.heatDebug`. По умолчанию выключено, потому что `getError` останавливает конвейер. |
| `?occdebug=<n>` | Помощь разработчику для WebGL2: заменяет тепло отладочными значениями перекрытия. Не для обычного использования. |

### Различия, которые важны {#differences-that-matter}

| | WebGPU | WebGL2 |
|---|---|---|
| Хранение строк | Буферы хранения: индекс строки — это индекс массива. Запрашивает самую большую привязку буфера хранения адаптера и размеры буферов. | Целочисленные текстуры (шириной 8 192 текселя), адресуемые из `gl_VertexID` через текстуру индексов блоков, которая обновляется каждый кадр. |
| 32-битное накопление тепла | Когда адаптер поддерживает и `float32-blendable`, и `float32-filterable` | Когда есть `EXT_float_blend` |
| Иначе | 16-битное (`r16float`) | 16-битное (`R16F`) |
| Диапазон глубины | [0, 1]; движок заранее умножает матрицы three.js, приведённые из [-1, 1]. Без этого параллельная проекция, у которой глубина линейна, почти полностью попадает ниже 0 и молча обрезается. | [-1, 1], используется как есть |
| Uniform-данные | Кольцо слотов по 256 байт с выравниванием, по одному на каждый вызов отрисовки, привязываются по смещению — `queue.writeBuffer` выполняется по порядку в очереди, поэтому если бы один буфер переписывался на каждый вызов, каждый вызов читал бы последнюю запись. Блок uniform-данных прохода тепла занимает ровно один слот по 256 байт. | Обычные uniform-переменные |
| Цель тепла ниже разрешения холста | Получает собственную текстуру глубины (все вложения прохода должны быть одного размера) | |
| Захват кадра | `captureFrame()` рисует композицию второй раз во внеэкранную цель и читает её обратно (безголовый Chromium рисует WebGPU, но не выводит свой холст) | Читает буфер кадра по умолчанию при следующем отрисованном кадре |
| Чтение обратно | Промежуточные буферы сохраняются и используются повторно; одновременно один читатель в работе | `readPixels`, с запросом у драйвера допустимой пары формат/тип |

Оба бэкенда загружают таблицу кривой спрайтов как half-float; `queue.writeTexture` в WebGPU копирует сырые байты, поэтому данные сначала кодируются в binary16 ([`half.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/render/half.ts)).

#### Пределы текстур {#texture-limits}

`texStorage2D` при превышении `MAX_TEXTURE_SIZE` не выдаёт ошибку: выделение молча отбрасывается, последующие загрузки не удаются, а выборка возвращает ноль. Вспомогательная функция WebGL2 [`createTexture`](https://github.com/Holdi601/3DHeat/blob/main/src/render/webgl2/glutil.ts) проверяет обе стороны по пределу и выдаёт ошибку с размером; текстура индексов блоков двумерна (4 096 в ширину), поэтому она не может перерасти предел; а `src/render/limits.test.ts` закрепляет каждый размер текстуры относительно пределов, которые стоит поддерживать. Рендерер WebGL2 также отказывается работать на устройстве, у которого максимальный размер текстуры меньше ширины 8 192 у текстуры строк.

### Проверка обоих {#testing-both}

`npm run smoke` запускает настоящее приложение в безголовом Chromium на WebGL2 (по умолчанию `http://127.0.0.1:5273/`); чтобы проверить WebGPU, передайте `"http://127.0.0.1:5273/?backend=webgpu"` в `node tools/smoke.mjs`, а для пути half-float — `npm run smoke:f16`. `tools/probe-webgpu.mjs` и `tools/probe-present.mjs` (перечислены в разделе инструментов разработчика в [Инструменты командной строки](ref-tools.md)) проверяют, доступны ли адаптер и вывод изображения в безголовых браузерах.

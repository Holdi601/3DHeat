# 大量分析：何千もの試合を一度に

**大量分析**は、試合のフォルダー全体が合計するとどうなるかを示します。どの車両がよく勝つか、どちらの側が有利か、戦闘がどこで起きているか、などです。見きれないほど多くの試合がある場合に使います。

各試合の小さな要約から動くので、1,000 や 10,000 の試合でも速く開きます。完全な行は、クリックした試合のものだけを読み込みます。

## 試してみる {#try-it}

1. ヒートマップのサイドバーで **大量分析** を開きます。
2. **フォルダー...**（または **ファイル...**）を押し、`.3dheat` の試合を選びます。
3. パネルが要約を読んでいる間待ちます（「要約... n / N」）。
4. **分析を開く**を押します。タブのあるウィンドウが開きます。
5. フィルター（ゲーム、マップ、モード、元、先）を設定し、タブを読みます。たとえば「バランス」です。
6. 行、セル、インサイトのどれかをクリックします。その試合が3Dビューに読み込まれ、カメラがその場所に向きます。

![バランスタブ：車両ごとの勝率と、デス1回あたりのキル数](../assets/img/en/mass-balance.webp)

```
.3dheat のフォルダー -> 要約 -> ウィンドウ（タブ） -> 行をクリック -> 試合が3Dで開く
```

`.3dheat` ファイルは1試合です（[1試合1ファイル](container.md)）。*ヒートマップ*と*行*は[用語集](glossary.md)で説明しています。

## 要約を得る {#getting-the-summaries}

ほとんどの人は何もする必要がありません。パネルは、足りない要約を自分で作ります。大きなフォルダーを一度に準備したい場合は、下のオフラインツールを使います。

`.3dheat` の試合はすべて要約を持ちます（`src/mass/summarize.ts`）。要約は、コンテナーの中のメンバー `<match>.summary.json`（役割 `summary`。[1試合1ファイル](container.md)を参照）として保持されます。オフラインツールはそれらを書き出し、フォルダーごとに索引も作ります。開発者向けのツールです。大きなフォルダーで実行すると、パネルの作業を省けます。

```
node tools/3dheat-summarize.mjs <folder>... [--jobs N] [--force] [--no-write] [--no-index] [--limit N] [--settle MIN]
```

- すでに要約された試合（同じ形式のバージョン）は、読むだけです。`--force` は再計算します。`--no-write` はコンテナーに手を付けません。
- `--settle` の分（既定 10 分）以内に変更されたファイルは飛ばします。コンバーターがまだ書いているかもしれないためです。
- `<folder>/3dheat-index.jsonl.gz`：試合ごとに1行。そのパス、サイズ、時刻、グリッドを除いた要約を含みます。`<folder>/3dheat-index.grids.jsonl.gz`：試合ごとに1行。グリッドを含みます。
- ファイルのあるマシンで、低い優先度で実行します（Linux では例えば `nice -n 19 ionice -c3`）。

パネルは、試合ごとに次の最初に見つかったものを使います。フォルダーの索引の行（同じパスとサイズ）、ブラウザのキャッシュ（IndexedDB。名前、サイズ、時刻で）、コンテナーの `summary` メンバー、またはワーカーのプールで計算し、キャッシュした要約です。そのため、索引のないフォルダーでも動きます。最初はテーブルを読む速さで、その後はキャッシュから読みます。

## パネル {#the-panel}

フォルダー（またはファイル）を選びます。**フォルダーを追加...** で別のフォルダーを加えられます。ウィンドウには、フィルターの **ゲーム**、**マップ**、**モード**、**元**、**先**、**分割の基準**、**ライフ数が少ない順**、**プレイヤーのみ**、そして次のタブがあります。すべての数値は要約から来ます。行、セル、インサイトをクリックすると、その試合が、それを示すフィルター（車両、クラス、武器、チーム、プレイヤー）とカメラの場所つきで、多試合のオーバーレイとしてビューに読み込まれます。

| タブ | 内容 |
|---|---|
| 概要 | 試合数、時間、プレイヤー数、ライフ、行数、日付。1日あたりの試合数。ゲーム、マップ、モード別。イベントの合計。通貨別の経済。試合のどの時点で何が起きるか |
| バランス | 車両、クラス、武器、チーム別。マップ、モード、ティア、ゲームで分割。K/D と約95%の区間、勝率（Wilson）、生存、1分あたりのキルと命中、1分あたりの収入、そして K/D と勝率の Benjamini-Hochberg の偽発見率（q）を、分割の残りに対して。**ライフ数が少ない順**は、信頼するには少なすぎるライフの行を隠します。**プレイヤーのみ**は、ミッションの AI が動かしたものを除きます |
| 傾向 | 使用率（存在の割合）、または上位の車両かクラスの K/D や勝率を、日、週、月ごとに |
| プレイヤー | 別々のプレイヤー、プレイヤーごとの試合数、試合ごとのプレイヤー数、最もよく出てくるプレイヤー |
| 側 | 各マップの各側：均等な分割に対して勝った試合数 |
| 近接戦 | ラウンドのデータ：側ごとの先制デュエルと、その成功率、トレード、待ち伏せ対保持、十字砲火、フラッシュされた突入、エイム、設置、人数の優位。そして **マップ別**では、そこに入るプレイヤーを倒す場所。すべて割合で、Wilson の区間付き。要約の `cqb` の数から（[近接戦とラウンド](close-quarters.md)） |
| マップ | マップの合計グリッド：存在、キル、デス、K/D、任意のイベント、流れ、そして**何試合で熱いか**（安定性）。チーム別、セルの1、2、4、8倍のサイズで |
| 場所 | 数字では目立つが、ヒートマップでは目立たない場所（広い区域が全体として混んでいる、通路、高さの帯）。**場所を探す** |
| ニッチ | ほかより著しく良い、または悪いグループ（1つのマップでの車両、1つの高さでの区画）。**ニッチを探す** |
| インサイト | 大量の検出器とマップの検出器（下記）。**レポートをコピー（JSON）**は、言語モデルが読む JSON を渡します |

## 多数の試合にわたるインサイト {#insights-over-many-matches}

**場所**タブは、数字では目立つが熱では目立たない場所を見つけます。広い区域が全体として混んでいる、通路、高さの帯、試合のある部分だけで混んでいる場所などです。単純な熱では見えないものを**隠れている**とマークし、3Dビューで輪郭を描きます。**読み込む**を押すと、保持している試合とともにそこへ飛びます。**ニッチ**タブは、ほかより著しく良い、または悪いグループ（1つのマップと側での車両、1つの高さでの区画）を見つけます。1つクリックすると、その細分を見られます。

**インサイト**タブは、すべての試合にわたって、ほかより良く、または悪く取引する、あるいは勝つ車両、一定の割合の試合で熱い場所、均等な分割より多く勝つ側、日付にわたって使用が変わる車両、均等な分布より多くのキルを持つ試合の部分を見つけます。各検出には、その件数、効果、区間、偽発見率（5%に保つ）が付き、クリックすると試合が読み込まれます。詳細は[開発者向け](#for-developers)を参照してください。

## 規模 {#scale}

この小さな版は、自分で繰り返せます。`node tools/demo-data.mjs` は、150 件の合成された戦車の試合を `tools/.shots/demo/mass` に書き出します（それぞれ約1,000行）。デスクトップ PC で、`tools/demo-data.mjs` の150件の合成デモの試合で計測しました（実際の試合はずっと大きくなります）。

- 4 ワーカーの `tools/3dheat-summarize.mjs`：150件すべてで 2.6〜4.8 秒。ワーカー内では試合あたり 8〜21 ミリ秒。要約を読むだけの2回目の実行は約2秒です。
- 索引がある状態でパネルにフォルダーを開き、ウィンドウが表示されるまで：0.9〜1.6 秒（ワーカー自身の部分、150行の索引の読み取りは 20〜40 ミリ秒）。
- タブに切り替え、そのテーブルが描かれるまで：概要 10〜30 ミリ秒、バランス 30〜70 ミリ秒、傾向 30〜45 ミリ秒、プレイヤー 15〜35 ミリ秒、側 15〜20 ミリ秒、マップ 55〜130 ミリ秒。
- ストアは、150試合を約 0.5 MB で保持します。

ウィンドウを開くのは、短いフレーム1回分です。選んだファイルは16個ずつワーカーに渡され、日付の欄と最初のタブは、ウィンドウの1フレーム後に表示されます。

ストアは、1試合あたり約 15 KB を保持します。そのため、10,000 試合でもワーカーの中で約 150 MB です。グリッドは、マップが求めた分より長くは保持されません。

## 開発者向け {#for-developers}

### 多数の試合にわたるインサイト {#insights-over-many-matches}

`src/mass/detect.ts`：すべての検出結果と、その件数、効果、区間、p と q（検出器が試したすべてにわたる Benjamini-Hochberg。5% に保つ）、その試合を読み込む掘り下げ、値つきの文のキー。レポート（`heat3d.mass/1`）は `massReportForModel` が語り手に渡すもので、1試合のレポート（`insights/seam.ts`）と同じ形です。

| 検出器 | 見つけるもの |
|---|---|
| `balance` | マップまたはモードで、プレイヤーの車両がほかより良く、または悪く取引する、または勝つもの |
| `hotspot` | 来た試合のうち一定の割合の試合で熱い場所（熱い試合数 / 見た試合数。マップの他のセルと比較）。合計で熱いだけではない |
| `side` | マップの側が、均等な分割より多く勝つもの |
| `meta` | プレイヤーのライフのうち車両の割合、または K/D が、日付の前半と後半の間で動いたもの。マップごとに。十分大きく、四半期にわたって傾向があり、ほとんどのマップで同じように（下記） |
| `phase` | 試合の長さの一部が、均等な分布より多くのキル、命中、発射などを持つもの |
| `place` | 多数の試合で目立つ場所（下の段階 B）。地域の割合や、キルの割合を、それぞれの試合自身と比べたもの。円、通路、拡大したゾーン、高さの帯、フェーズ。単純な熱では見えない場合は隠れる |
| `niche` | ほかより著しく良い、または悪いグループ（下の段階 B） |
| `grid.*` | 単一データセットの検出器（強い位置、熱いゾーンと静かなゾーン、クラスの場所）を、各マップの合計グリッドに適用。`GridMerge.toInsightJob` が、要約からインサイトの処理のグリッドを埋めます。軌跡を必要とする検出器は省きます |

### 要約 {#the-summary}

単純な JSON（`src/mass/types.ts`）。圧縮後、1試合あたり約 5〜30 KB です。

- 試合：ゲーム、マップ、モード、ミッション、開始、長さ、行数、ライフ、プレイヤー、AI、チーム（ライフ、プレイヤー、存在、キル、デス、勝利、お金）、勝者。
- 車両とチームごと：クラス、ティア、ライフ、プレイヤーのライフ、存在、正規の種類別のイベント、対象のクラス別のキル、勝利、お金。
- プレイヤーごと（ユーザー ID、なければ名前）：チーム、ライフ、存在、キル、デス、命中、発射、勝利、車両。武器ごと：種類別のイベント。
- 経済の列（`cost_*`、`earn_*`）とその合計。
- フェーズ：試合の長さを20の区間に分けた種類別のイベント、および分ごとのイベント。
- 行動：試合の集合的行動の指標（整列、経路の群れ、レーン、混雑、先頭、取り残され、崩壊点、損失後のリスク、連勝、購入の一致、抑制）。それぞれ独自の帰無モデル、p と q を持ちます（[集合行動](collective-behaviour.md)を参照）。
- グリッド（下記）。

ビューアーが数えるのと同じ方法で数えます。列は多試合ローダーが見つけるとおりに（`leanSpec`）、イベントは `data/canonical.ts` で。Tacview の武器によるキルは、撃った側のカウントになります。同時に2回宣言されたデス（`dead`、`death`）は、1回と数えます。

#### グリッド：段階 B が基づくもの {#the-grid-what-stage-b-builds-on}

空間の部分は、熱の絵だけでなく、どんな大きさと形の地域に対してもスキャン統計ができるように作られています。

- **ピラミッド。** セルは、ワールド単位（ビューアーが置く x、z）で揃えた2の冪です。レベル `k` は、`ix >> k, iz >> k` で合計したセルです。これは正確で、1つの試合の中でも、ほかのセルサイズの試合をまたいでも同じです。どの地域（箱、直線に沿った通路、リング）も、セルの合計です。最も細かいレベルは、試合の頑健な広がり（存在の99%を含むセル）を 128 セルに収めます。その外にある外れ値は保持されます。
- **すべての件数の隣に露出。** セルごとの存在時間を、チームごと（`pt`）、車両クラスごと（`pc`）、高さの帯ごと（`ph`）に持つので、どの部分集合についても、地域の割合、期待値、比を計算できます。
- **高さ。** 試合の床（高さの1パーセンタイル）より上の帯：3 m 未満、3〜10、10〜30、30〜100、100〜300、300〜1000、1000〜3000、それ以上。`floor`、`storey`、`deck` の列があるファイルは、代わりにその階で帯を作ります。`y` は各セルの平均高さ、`y0` はその最も低い高さ（その上の高さに対する階）です。
- **イベント**はタプル `[cell, kind, team, class, band, count]` です。
- **時間のスライス**は粗いレベル（一辺8セル）で、試合の開始からの分ごとに：`[cx, cz, minute, kind, value]`。存在の秒数は種類 `GRID_KINDS.length` になります。試合のフェーズは、長さに対する分です。
- まばら。件数は整数、秒は10分の1秒まで。起きたことで上限が決まります。

### 段階 B：場所とニッチ {#stage-b-places-and-niches}

段階 B は、目を引かずに数字では目立つものを探します。全体として混んでいる広い区域で、その中に熱いセルがないもの。少ないイベントでの奇妙なキルデス比。通路。高さの帯。試合の一部だけにある集まり。そして、ほかより著しく良い、または悪いグループ（1つのマップ、1つの側での車両、1つの高さでの区画）です。1つの**場所を探す** / **ニッチを探す** / **インサイトを探す**がすべての検出器を実行します。3つのタブは、同じレポートを共有します。

#### 場所（`src/mass/scan.ts`） {#places-srcmassscants}

各マップの試合は、1試合ずつ2回読まれます。メモリに保持されるのは、一辺最大64セル（時空間スキャンでは16）のラスターの合計だけで、試合そのものは保持しません。

- **指標。** 存在1秒あたりのイベントの率：キル、デス、命中、発射、占領。すべてのユニット、クラスごと（イベントが最も多い4つ）、高さの帯ごと。キルとデスの中のキルの割合。側ごと、帯ごとにも。どのクラスと側を使うかは、ヘッド（`planOf`）から決まります。
- **試合ごとの期待値。** 各試合自身の率を、そのセルでの自身の存在に対して広げたものが、そのセルの期待値です（試合で層別した、共変量調整の Kulldorff スキャン）。少数の血なまぐさい試合や、1つの混んだサーバーでは、場所にはなりません。
- **分散。** 試合は、ポアソンをはるかに超えて食い違います。各試合の残差は、1、2、4、8、16 セルのブロックで合計されます。ブロックのサイズごとの分散（帰無分散に対する二乗残差。プールし、最悪の5%のブロックを除く）が、その大きさの地域のすべての検定を調整します。率にはポアソン、割合には二項の、準尤度比です。
- **地域。** 0.75〜18 セルの円。6つの角度の楕円（幅の3倍と6倍の長さ。3〜18 セル。通路。軸はインサイトの `place.path`）。地域のz が大きくなる間、最も強い局所の Getis-Ord Gi* セルから、セルごとに拡大するゾーン（不規則な形）。試合の半分で拡大し、残りの半分で検定するので、拡大の自由度が偽の場所を生みません。各高さの帯は、地図全体で試合のほかの帯と比べます（クラスタに頑健）。時空間の円柱：試合の長さの5分の1か2分の1の中の円。試合自身の、場所と時間にわたるイベントの広がりと比べます（時空間の並べ替えスキャン）。
- **検定。** p は準尤度から。すべてのマップで試したすべての地域に対して Benjamini-Hochberg（3マップで70万は普通）。5%。通過したものは刈り込まれます（強い方の地域に大部分が含まれる地域は、同じことを言っています）。その後、**安定性**を読み直します。その地域を見た試合、その中にいた試合、試合の5つの折りでの向き。さらに、試合自身が示す分散で、もう一度検定します（クラスタに頑健。試合をクラスタとして。ポアソンの下では決してしない）。もう一度 BH。基地の上の静かな場所（マップのスポーン、離陸、着陸の2%以上）は除きます。
- **効果。** 率（またはオッズ）の比。経験ベイズで縮小（マップの 2×2 のブロックに当てはめたガンマの事前分布）。分散での約95%の区間。1、2、4 セルでの Gi*、中心での局所 Moran。
- **視覚的な明白さ。** 地域は、そのイベントの単純な熱ですでにどれだけ見えているか（ビューがそうするように、最も明るいセルへの対数スケール）。その周りのリングとのコントラスト（パレットの10分の1は見えにくく、5分の2は単純）と、余分を運ぶ明るいピーク。比は熱では描かれないので、割合は半分と数えます。35% 未満は**隠れている**です。順位：強さ（効果は4倍で飽和。静かな場所は 0.7）× `1 - 0.7 x 明白さ` × 折りの一致。

**場所**タブはそれらを一覧にします（既定では隠れているものだけ。マップ、形、方向で）。クリックすると、マップの場所の輪郭が3Dビューに描かれます（`placeLines.ts`：エンジンの上の線を一度作り、隠れは赤紫、単純は琥珀色、静かはシアン、選んだものは全体。帯は床から天井までの箱として）。マップタブのキャンバスにも描かれます。**読み込む**をクリックすると、そこへ飛び、その場所が最も多く含んだ60試合を、そのイベント（とクラス）で絞り込んで読み込みます。

#### ニッチ（`src/mass/niche.ts`） {#niches-srcmassnichets}

3つの表にわたる、幅24、深さ3のビーム探索：**ライフ**（プレイヤーのライフ：ゲーム、マップ、モード、クラス、車両、側、ティア、日付の四半期、試合の長さの3分の1。K/D、勝利、ライフとしてのデス、1時間あたりのキル、1分あたりの収入）、**場所**（マップ、モード、日付、マップの 4×4 の区画、クラス、側、帯ごとのキルとデス）、**フェーズ**（試合の区画と5分の1：K/D、存在1時間あたりのデス）。グループは、全体に対して試合をクラスタとして検定します（試合ごとの残差のサンドイッチ分散）。その効果はオッズまたは率の比で、20の結果の事前分布で縮小されます。8試合にわたる30の結果が必要です。細分は、その親より10%強くなければなりません。結果がすべてあるか、まったくないグループ（記録されていないもの）は省きます。残すもの：評価したすべてのグループに対して BH で5%未満、縮小した比が少なくとも 1.25（または 1/1.25）、5つの折りのうち4つが一致、親を繰り返すだけの細分ではないもの。**ニッチ**タブはそれらを一覧にします。クリックすると、そのグループのすべての1条件の細分（探索）が表示されます。**読み込む**はその試合を読み込みます。装備は、まだ要約に入っていません。

#### 実質的な有意性を持つ、メタの変化 {#meta-shifts-with-practical-significance}

日付が混ざったとき、ライフに対する二項検定は、ほぼすべての変化を有意と判定していました。`meta` は、今はクラスタに頑健に検定します（各試合のライフをクラスタとして）。使用の変化は、2ポイントかつ少なくとも25%の場合のみ残し、K/D の変化は 1.3 倍、日付の四半期が同じ方向に傾向があること（ケンドールの tau が少なくとも 0.5）、そして複数のマップにまたがる車両については、それらのほとんどで同じ方向であることを求めます。単純な検定がほぼすべてに旗を立てた検証セットでも、残るのは数個の変化だけです。

#### モデルのために {#for-a-model}

`massReportForModel` は、各場所に `region`（形、隠れている、明白さ、高さ、フェーズ）を、各ニッチに `conditions` を与えます。試された地域とグループの数も加わります。知識レンズは、場所を殺傷地帯や接近路として読めます。その種類は `place.*` と `niche.*` です。

#### 検査 {#checks}

`scan.test.ts` は、拡散した区域（22 セルの円にわたり、死亡率 1.6 倍。どのセルでも弱い）、通路、高さの帯、フェーズだけの集まりを、240 件の合成の過分散の試合に埋め込みます。すべて見つかり、拡散したものは隠れていることを確認します。また、60試合の帰無集合を8つ実行し、場所がないことを確認します。`niche.test.ts` は、埋め込んだ車両×マップ×側のグループを見つけ、5つの帰無表では何も見つけないことを確認します。

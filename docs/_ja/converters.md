# 変換ツールはすべて保持する

このページがなくても、リプレイは開けます。このページは、ゲームのファイルを 3DHeat のテーブルに変換するツールを書く人、そして、それらのテーブルがなぜこれほど多くを持っているのかを知りたい人のためのものです。

ゲームのリプレイ、デモ、ログ、またはライブのテレメトリを、ビューアーが開けるものに変換するツールはすべて、次の1つの規則に従います。

> **元が持っているもののうち、今読めるものはすべて変換し、残りはそのまま丸ごと保持して、元のファイルなしでも後で読めるようにする。**

リプレイは、ゲームのアップデート、再インストール、ディスクの容量不足の後には、なくなっていることがよくあります。ライブのフィードは、送られた瞬間になくなります。変換ツールが捨てたものは、永久に失われます。そのまま丸ごと保持したものは、それを理解した人がいつか解読できます。そのため、変換ツールはどれが役に立つかを決めることはしません。読めるものは解読し、それ以外のすべてのメッセージ、パケット、イベント、プロパティ、行は、テーブルの横に変更せずに保持します。そして、どれだけを読み、どれだけを保持しただけなのかを、自分の出力で示します。

このページは、すべての変換ツールが共有する約束です。War Thunder、World of Tanks、World of Warships、Squad のリプレイ変換ツール、CS2 のデモ変換ツール、バックグラウンドのウォッチャー（その Dota のリプレイの解読器とすべてのライブのアダプター）、ゲームのキャプチャツールのテレメトリの読み取り、そしてビューアー自身の取り込み（Tacview ACMI、OCAP、GPX/KML/IGC/FIT/NMEA）に共通です。ビューアー自身の読み取り機能は、[Tacview の記録](tacview-acmi.md)と[ファイルの読み込み](loading-files.md)で説明しています。1ファイルの形は[1試合1ファイル](container.md)です。1試合は、1つのテーブル、`match.json`、サイドカーになり、必要なら1つの `.3dheat` ファイルにまとめられます。各ツールの README には**完全性**のセクションがあり、そのソースについて、何が読まれ、何が生のまま保持され、何が利用できないか、その理由を示しています。

## すべての項目の3つの置き場所 {#three-homes-for-every-item}

元が持つものはすべて、次の3つのうちちょうど1か所に入ります。

| 置き場所 | 入るもの |
|---|---|
| **解読済み** | テーブル（サンプルまたはイベントごとに1行。ビューアーが読む列と、行に属するほかのすべての値のための追加の列）と、試合の文書 `<match>.match.json`（試合全体に属するもの：設定、名簿、結果、スコアボード、自己チェック）。 |
| **生のまま保持** | テーブルの横のサイドカー。解読されなかった、または一部だけ解読された項目を、その型、時刻、属する単位またはエンティティとともに、丸ごと変更せずに。 |
| **利用できない** | README の完全性のセクションに、理由とともに書かれます。形式がそれを持っていない（クライアントのリプレイには、ほかのプレイヤーの入力がない）、ソースが送らない、または読むことが許されない（保護されたプロセス、自分が使うべきでない鍵で暗号化されたブロック）。 |

**一部だけ**解読された項目は、解読され、*かつ*生のまま保持されます。テーブルには理解できた部分が入り、サイドカーには項目全体が入ります。そのため、後でより良い解読器ができても、元のファイルは不要です。

4つ目の置き場所はありません。役に立たないように見えた、「たぶん」重複していた、または大きかったという理由で捨てるのは、バグです。間引きが許されるのはテーブルの中だけです（60 Hz ではなく 2 Hz のカメラ）。サイドカーでは決して許されません。

## サイドカー {#sidecars}

サイドカーは、テーブルの横にある、その名前にちなんだ Parquet ファイルです。

```
<folder>/<match>.parquet              テーブル
<folder>/<match>.match.json           試合の文書
<folder>/<match>.<what>.parquet       サイドカー
```

`<what>` は、このリストにある1つの単語です。新しい変換ツールは、合う単語を選ぶか、ここに新しい単語を追加します。**そして**、[`src/data/filePick.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/data/filePick.ts) の `SIDECAR_PARQUET` にも追加します。そうすると、フォルダー全体を読み込んだときにビューアーがそれを飛ばします。

| `<what>` | 持つもの | 使うツール |
|---|---|---|
| `messages` | ネットワークストリームのパケット、エンティティのメソッド呼び出し、プロパティの更新。丸ごと | War Thunder、World of Tanks、World of Warships |
| `flight` | 機体ごとの飛行モデルの項目。丸ごと | War Thunder |
| `packets` | エンティティのストリームの外にある、フレームとネットワークメッセージ全体、またはコンテナーのチャンク | CS2、Dota 2、Squad |
| `events` | ゲームのイベントを、解析器が与えるすべてのキーとともに | CS2 |
| `entities` | エンティティとプロパティの更新、リモート呼び出し、開かれて閉じられたチャンネル。デコーダーが必要とする書き出しを含む | Squad、Dota 2 |
| `props` | 解析器が読むすべてのエンティティのプロパティ。変わるたびに | CS2 |
| `units` | 位置のテーブルの外にある、単位ごとの状態 | Dota 2 |
| `combatlog` | 戦闘ログ。すべての項目とすべてのフィールド | Dota 2 |
| `strings` | すべての文字列テーブルのすべての項目 | CS2、Dota 2 |
| `objectives` | 占領ゾーンと目標。変化ごとに、その時刻とともに | War Thunder |
| `raw` | ライブのフィード。受け取ったすべてのパケット、行、API の文書、またはメモリの読み取りを丸ごと | ウォッチャーのセッション（`heat.raw.parquet`）、ゲームのキャプチャツールのラップの記録（`<stamp>_<game>.raw.parquet`）、ウォッチャーの osu!、LoL、Valorant のリプレイファイル |

ビューアーのフォルダー読み込みは、このリストにある `*.<what>.parquet` をすべて、そして `*.match.json`、`*.meta.json`、`*.summary.json` とほかの JSON のサイドカーをすべて飛ばします。そのどれか1つを単独で開く（そのファイルだけを選んだりドロップしたりする）と、ほかのテーブルと同じように読み込まれます（[ファイルの読み込み](loading-files.md)を参照）。

ここに示したのは、変換ツールが `--loose` で書いたファイルです。既定では、War Thunder、CS2、Tacview の変換ツールは、試合のテーブル、文書、サイドカーを、同じ名前で1つのファイル `<match>.3dheat` にまとめます（[1試合1ファイル](container.md)を参照）。ここに書かれたことは、そのメンバーのそれぞれに当てはまります。

### 列 {#columns}

サイドカーの各行は1つの項目です。列は、当てはまるものを次の順で並べたものです。

| 列 | 型 | 内容 |
|---|---|---|
| `time` | float64 | テーブルの `time` と同じ時計の秒（元がティックを数える場合は `tick`。その場合は両方） |
| `type` | string（辞書） | 項目が何か。元の用語で：パケットの型、メッセージの ID、イベント名、プロパティのパス、行の接頭辞 |
| `name` | string（辞書） | わかっている場合の名前（コミュニティの名前、クラス名）。なければ空 |
| `entity` / `unit` / `uid` / `player` | 整数または文字列 | 誰に属するか。テーブルと同じ ID で、サイドカーの行をトラックに結合できます |
| `decoded` | string（JSON） | 理解できた内容。何かあれば。なければ空 |
| `payload` | binary | 項目のバイト列。丸ごと、変更せず（バイナリのソース） |
| `text` | string | 項目のテキスト。丸ごと、変更せず（テキストのソース：ログの行、JSON オブジェクト、キーと値のブロック） |

ほかの列も許されます（ビット位置、サイズ、チャンネル）。繰り返す文字列は辞書で符号化され、ファイルは zstd で書かれるので、サイドカーはリプレイ自体のサイズのごく一部に収まります。

サイドカーは、それだけで十分でなければなりません。後で書かれた解読器は、元のリプレイではなく、サイドカーを読みます。文脈なしには理解できない項目（エンティティのクラス、文字列テーブル、メッセージが参照するキー）は、その文脈もサイドカーか、試合の文書に入れます。

### ライブのソース {#live-sources}

ライブのアダプター（UDP のテレメトリ、共有メモリ、ゲームのログ、ローカルの API）には、戻るべきファイルがそもそもありません。そのため、**ソースが送るすべてのフィールド**を、まだ誰も使っていないものも含めて記録します。

- パケットのフィード：すべてのパケットを丸ごと。`payload` はバイト列、`type` はそのパケットの ID または形式で、届いた速度のまま。
- 共有メモリまたはポーリングする API：すべての読み取りのすべてのフィールド。名前つきの列として、または `payload` としてブロック全体を。アダプターが読む速度で。
- ログ：すべての行。`text` は行そのもの、`type` は行の種類。アダプターが何もしない行も含みます。

これらは、セッションのテーブルの横の `<session>.raw.parquet` に入ります。サイズは規則の代償です。それを抑えるのは、項目を省くことではなく、zstd と辞書の符号化です。

## 自己チェック {#the-self-check}

すべての変換ツールは、試合の文書（または、試合の文書がない場合はセッションの `meta.json` か要約）に、`selfCheck` の下の `completeness` ブロックを書きます。

```json
"selfCheck": {
  "completeness": {
    "rule": "https://github.com/Holdi601/3DHeat/blob/main/docs/converters.md",
    "sidecars": ["match-0001.events.parquet"],
    "types": {
      "player_death": {"seen": 182, "decoded": 182, "partial": 0, "raw": 0, "lost": 0},
      "bullet_damage": {"seen": 2410, "decoded": 0, "partial": 0, "raw": 2410, "lost": 0}
    },
    "lost": 0
  }
}
```

| フィールド | 意味 |
|---|---|
| `seen` | ソースが持つ、この型の項目の数 |
| `decoded` | テーブルまたは試合の文書に丸ごと読まれたもの |
| `partial` | テーブルまたは文書に一部だけ読まれ、サイドカーには丸ごと保持されたもの |
| `raw` | サイドカーにだけ丸ごと保持され、解読されなかったもの |
| `lost` | `seen - decoded - partial - raw`。必ず 0 |

最上位の `lost` は合計です。変換ツールのテストは、合成サンプルでそれが 0 であることを確認します。README には、実際のデータでの値を書きます。`lost` がゼロでないのは、変換ツールがこの規則を破ったと伝えることです。型の名前を挙げるので、欠けている部分を見つけられます。

「型」は、ソース自身のものです。パケットの型、メッセージの ID、イベント名、プロパティのグループ、行の種類です。期待するものの一覧からではなく、変換ツールが出会ったときに数えるので、誰も知らなかった型も、その数つきで現れ、消えることはありません。

## README の完全性のセクション {#the-readmes-completeness-section}

各変換ツールの README には、**完全性**という見出しのセクションがあり、3つの一覧があります。

- **読んだもの**：テーブルと試合の文書に入るもの。そして、新しい各フィールドが、独立した何か（ゲーム自身の数値、2つ目のソース、そのために作った記録）でどう確認されたか。
- **生のまま保持したもの**：どのサイドカーに、どの `type` で入っているか、そして今までに何がわかっているか。
- **利用できないもの**：ソースが持っていない、または読むことを許されていないもの、そしてその理由。

それはこのページへ戻るリンクを張ります。

### ビューアー自身の取り込み {#the-viewers-own-imports}

Tacview ACMI、OCAP、GPS の形式は、ユーザー自身のファイルからブラウザで読まれます。ビューアーはそれらから何も保存しないので、ファイル自体が記録として残ります。それでも、読めるものはできるだけ読みます。

- **Tacview ACMI**（`src/data/acmi.ts`）：位置のあるオブジェクトの行はすべて、記録が持つすべてのプロパティを持つ行になります。イベントはすべて行になります。削除はすべて行になります。記録自身のプロパティ（ヘッダーの FileType と FileVersion を含む）は、すべての行に `RecordingInfo` として付きます。コメントの行はイベント `Comment` になります。一度も位置を得ないオブジェクトは、基準点で `Unplaced` の行になります。U と V は、どの行にあっても列になります。位置のないプロパティの行は一部だけ読まれます。その値は、自分の時刻ではなく、オブジェクトの次の行に届きます。`AcmiTable.completeness` は、ファイルの行を種類ごとに数えます。
- **OCAP**（`src/data/ocap.ts`）：すべてのエンティティのフレーム、発射、マーカー、すべてのイベントの種類（未知の種類は「Mission」の行として、そのテキストとともに）、そして文書自身のフィールド（`Info`）。まだ読んでいないもの：エンティティのフィールドと、ヘッダーに挙げられていない末尾の位置の要素（新しい記録ツールの追加分）、死んだ単位の死後の繰り返しのフレーム（意図して間引かれています。何も変わらないからです）。
- **GPS の形式**（`src/data/geoTracks.ts`）：位置の測定値、その時刻、高度、コース、速度、そしてファイルが記録している場合は心拍数、ケイデンス、パワー、気温、衛星数、HDOP、気圧高度。まだ読んでいないもの：ほかの GPX と KML の拡張、位置以外の NMEA の文、位置の測定値とその拡張以外の IGC のレコード、レコード以外の FIT のメッセージ（ラップ、セッション、デバイス情報）。

これらの欠けている部分は、言い訳のためではなく、埋めるために挙げています。読み込んだ記録のビューアーの書き出し（`src/data/exportRecording.ts`）は、読まれたものだけを書きます。

## 変換ツールの追加 {#adding-a-converter}

1. 形式が持つものを一覧にします。その文書、その構造、または実際のサンプルにある各メッセージの型を数えることで。この一覧が自己チェックの `types` になります。
2. 今確認できるものを解読します。新しい各フィールドは、テーブルに入る前に、独立した何かで確認します。まだ確認できないフィールドは、生のまま残します。
3. 残りは、上に挙げた名前のサイドカーに、上の列で丸ごと保持します。
4. `completeness` ブロックと、`lost` が 0 であることを確認するテストを書きます。
5. README の完全性のセクションを書き、ここにリンクします。
6. サイドカーの `<what>` が新しい場合は、上の表と `src/data/filePick.ts` の `SIDECAR_PARQUET` に追加します。

変換ツールはクリーンルームで書かれます。GPL や AGPL のコードからではなく、形式、ドキュメント、サンプルから書きます。実際のリプレイのサンプルは、それを作ったマシンに残し、テストは合成ファイルを使います。

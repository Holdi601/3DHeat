# サンプリングと予算

1フレームで描くには点が多すぎる場合、ビューアーは均等な標本を描き、それぞれの点をより多くを表すものとして扱うため、画像は正しいままになります。コントローラーが描く数を調整し、ビューアーのフレームレートを保ちます。

## パフォーマンスパネルの設定 {#performance-panel-controls}

| 設定 | 既定値 | 範囲（ジョグ） |
|---|---|---|
| **毎フレームすべての行を描画** | オン | |
| **自動予算** | オン | |
| **目標 FPS** | 60 | 20〜240（1000） |
| **初期スプライト/フレーム**（自動）または **スプライト/フレーム** | 4.00M | 65,536〜268,435,456、対数（268,435,456） |
| **ヒート解像度** | 100% | 25〜100%。自動の第2段階の倍率を掛ける |
| **段階的な精緻化** | オン | オフ: 毎フレームが、新しい1フレームの推定値になります（生の標本を見るのに便利）。 |

[パフォーマンスパネルと統計のオーバーレイ](performance-and-stats.md)も参照してください。

## 開発者向け {#for-developers}

### 候補の行 {#candidate-rows}

行は、時刻の昇順で保存されます。タイムラインの窓 [*lo*, *hi*] は、時刻の列に対する2回の二分探索で、行の範囲になります（[`candidateRange`](https://github.com/Holdi601/3DHeat/blob/main/src/render/sampling.ts)）。時刻の列がなければ、すべての行が候補です。これらは統計のオーバーレイの**窓内の行**です。行ごとの検査（フィルター、グループ、分割、カリング、スライス、ライフタイム）は後で、シェーダーで行われます。検査に落ちた行は、1つの頂点の呼び出しのコストだけで、フラグメントは生じません。

### 標本抽出の計画 {#the-sampling-plan}

[`planFrame`](https://github.com/Holdi601/3DHeat/blob/main/src/render/sampling.ts)は、候補の範囲を**連続する4,096行のブロック**に分け、フレームのスプライト予算から描く数を選びます:

- 予算がすべてのブロックを覆う場合、すべてが描かれます。フレームは正確です。
- そうでない場合、ブロックは範囲全体に等間隔に取られます。そのずれは、毎フレーム黄金比で進むため、次のフレームは異なるブロックを覆い、その和が均等に埋まります。これは**層化**された標本です。時刻範囲のすべての部分が、すべてのフレームに含まれます。

描かれた各行のヒートには、**候補 / 送信数**が掛けられます。そのため、フレームの期待されるヒートは、どの予算でも正確です。予算によって変わるのはノイズだけです。行は8,388,608行のチャンクに入ります（[GPU メモリの常駐](gpu-memory.md)を参照）。ブロックがチャンクをまたぐところで分割され、各チャンクは描くべきブロックの開始位置の一覧を受け取ります。

1つの計画は、最大 65,536 ブロック（268,435,456 スプライト）までしか持てません。両方のバックエンドが、固定の 65,536 スロットのブロック開始バッファを持つためです。それ以上の要求はその上限で抑えられ、不足は収束までのフレーム数が増えることとして、正直に現れます。

### 毎フレームすべての行を描画 {#draw-every-row-each-frame}

**パフォーマンス → 毎フレームすべての行を描画**（既定は**オン**）: 予算は上限ではなく下限になり、新しい推定値を始めるフレームは、担当するすべての行を描きます（268M の上限まで）。

理由: カメラの移動は累積を捨てるため、動いているフレームは1つの推定値になります。そのノイズは、描かれたデータの量で決まります。4分の1だけ描くと、明るい重み付きの点として4分の1しか見えません。これが、動いている視点がきらめく理由です。すべて描けば、どのフレームも完成した画像になります。代償として、フレーム時間は窓の中のデータの大きさに従うようになります。調整できるのは、より狭い時間窓、フィルター、または距離カリングです。これらは、標本を薄くする代わりに、候補を減らします。

全体の場を一度に描けないハードウェアでは、オフにしてください。その場合、*スプライト/フレーム* が実際の上限になり、ビューは静止したフレームの数回で収束します。

すべての計画のコストを、大きなレベルで4K キャンバスの高性能デスクトップ GPU で測ると、半径1 m のスプライト（1〜2ピクセル）で、およそ 30 fps で1フレームあたり 1 億スプライト、15 fps で 2 億スプライト、12 fps 前後で最大の 2億6,800万スプライトです。これほど小さいスプライトでは、頂点段階がコストのすべてであり、ヒート解像度は何も変えません。大きなスプライトでは、塗りつぶしが問題になります。半径 100 m のスプライト 800 万個は、全解像度のヒートで1フレーム 2.5 秒、25% では 170 ms かかりました。そのため、**毎フレームすべての行を描画**は、6,700 万から始まり、フレームが 150 ms 未満のとき毎フレーム 4分の1ずつ増え、400 ms を超えると半分に減ります。重いビューが、GPU のウォッチドッグが許す以上にフレームを走らせないようにするためです。

### 自動予算 {#the-adaptive-budget}

**パフォーマンス → 自動予算**（既定はオン）は、スプライト予算を、**目標 FPS** を保つように調整します（[`BudgetController`](https://github.com/Holdi601/3DHeat/blob/main/src/render/sampling.ts)）。ボックスリプレイ中と動画のレンダリング中は働きません。

入力はフレーム時間です。平滑化されます（前の値の90% + 新しい値の10%。単一のフレームは2秒で上限）。目標は 1000 / max(15, 目標 FPS) ms です。

**第1段階 - スプライト。** 毎フレーム、予算は `1 + (target / frame - 1) × gain` を掛けられます。遅すぎるときの gain は 0.35、余裕があるときは 0.08 です。1フレームあたり 0.5〜1.25 の倍率、および 65,536〜268,435,456 スプライトに制限されます。

**第2段階 - 解像度。** 予算がすでに下限にあり、フレームがまだ目標より 10% 以上遅い場合にだけ、ヒートバッファーの解像度が下がります。1フレームあたり 8% ずつ、キャンバスの 25% まで下がります。30% の余裕がある間は、1フレームあたり 4% ずつ戻ります。フラグメントのコストは解像度の2乗で下がります。滑らかなランプの下では、ほとんど見えません。（ソフトウェア描画で、1,000万行と大きすぎるスプライトで測定: 1フレームあたり 141 ms → 17 ms。）倍率は 16分の1 単位に丸められ、オーバーレイの *ヒート解像度* に表示されます。

**諦める。** 遅いフレームは、スプライトが原因でも重いレベルが原因でも、同じに見えます。パスごとの時間計測はありません。予算が下限にあり、30 フレームの間フレームが目標の 70% 未満のままなら、原因はスプライトではなかったということです。コントローラーは**上昇**に切り替わります。14 フレームごとに予算を 1.5 倍にし、解像度を戻します。ただし、フレーム時間が下限のときの 1.5 倍以内に収まっている間だけです。それ以上に悪化した上昇は、60% まで戻して通常の制御を再開します。目標に達すると、上昇は終わります。

自動予算がオフのときは、予算は単純に **スプライト/フレーム** になります。

*毎フレームすべての行を描画* がオンでも、自動予算は動きますが、厳密なルールは予算を上げてすべての候補行を覆うようにするため、実際には解像度の段階と、新しい推定値を始めないフレームだけを制御します。

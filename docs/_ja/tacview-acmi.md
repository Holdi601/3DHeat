# Tacview の記録（ACMI）

Tacview は、フライトシミュレーターの飛行を記録するプログラムです。そのファイルの拡張子は `.acmi` です。3DHeat はそれを開き、すべての機体がどこを飛んだかを見せます。

Tacview の飛行の記録は、ほかの表と同じように読み込めます。`.acmi`（テキスト、`.txt.acmi`、または圧縮された `.zip.acmi`）を選ぶか、ドロップして **読み込む** を押します。すると、すべての飛行のヒートが得られます。**マッチ** タブでは、フィギュア、航跡、イベントの一覧を含む再生が見られます（[マッチの再生](match-replay.md)）。ACMI は Tacview の公開されたファイル形式です（[ドキュメント](https://www.tacview.net/documentation/acmi/)）。DCS（Tacview のエクスポーター経由）、IL-2 Great Battles、Falcon BMS、X-Plane、MSFS などがこの形式で書き出すため、どれも読めます。

## 記録が何になるか {#what-a-recording-becomes}

オブジェクトの位置が書き込まれるたびに1行、オブジェクトの場所で起きたイベントごとに1行、オブジェクトがいなくなったとき（`Removed`、最後にいた場所）に1行です。まだ見ていないオブジェクトに関するイベント（ブックマーク、全員へのメッセージなど）は、基準点にある `(recording)` というオブジェクトの行になります。記録には、読み方の指示が含まれているので、マッピングの手順は自動で埋まります。読み取りは、次の列を書きます: `Time`、`X`、`Y`、`Altitude`、`Object`、`Coalition`、`Heading`、`Pitch`、`Roll`、`Type`、`Name`、`Pilot`、`Group`、`Country`、`Color`、`Event`、`Latitude`、`Longitude`、`Recording`、`EventObjects`、`RecordingInfo`。そのあとに、記録が持つそのほかのプロパティが続きます。それぞれの役割は次のとおりです。

| 列 | 役割 | 意味 |
|---|---|---|
| Time | 時間 | 記録の ReferenceTime からの秒数。ReferenceTime があるときは Unix 秒なので、時計は実際の時刻を示します。 |
| X、Y | 位置 | 東と北（メートル）。記録の基準点で地球に接する面の上での値です。基準点の近くでは距離と方位が正確で、100 km 先でも誤差は千分の一未満です。北はワールドの -Z になります。 |
| Altitude | 位置（上） | メートル。 |
| Object | 人物 | パイロットとオブジェクトの名前（ID 付き）。例: `Viper 1 (F-16C_50) #a01`。無人のオブジェクトは `(T-90A) #401`。 |
| Coalition | チーム | 陣営（陣営がないときは色）。 |
| Heading、Pitch | 向き | 度。方位 0 は北です。 |
| Recording | セッション | 記録の Title、またはファイル名。複数の記録を並べて読み込んでも、航跡はつながりません。 |
| Type、Name、Pilot、Group、Country、Color、Event、Roll、Latitude、Longitude | フィルター | フィルター用に保存されます。Type と Name は、各オブジェクトの[フィギュア](figures.md)を選びます。Event は、ディブリーフのイベント一覧に使われます。Roll は、機体の傾きに使われます。 |
| U、V | | すべてのサンプルにある場合の、ゲーム自身の平面のワールドのメートル値（DCS が書き出します）。 |
| EventObjects | フィルター | イベントが指名するすべてのオブジェクト（`Message|a01|b02|...`）。ID で書かれます。 |
| RecordingInfo | | その時点での記録自身のプロパティ（DataSource、DataRecorder、Author、Category、Briefing、Comments など）。JSON で書かれます。 |
| IAS、Mach、AOA、FuelWeight など | フィルター | 記録が持つそのほかの数値のプロパティ。 |
| Parent、CallSign、LockedTarget、Label、Shape など | フィルター | 記録が持つそのほかの文字列のプロパティ。値が数値でないプロパティは、文字列として扱われます。 |

Tacview の位置の 4 つの形式（`lon|lat|alt`、`u|v` を伴うもの、`roll|pitch|yaw` を伴うもの、そしてそれらすべてと方位を伴うもの）はすべて読まれます。空の欄には、直前の値が残ります。`-id` はオブジェクトを削除します。削除のあとに同じ ID が再び使われると、それは新しいオブジェクトになります。エスケープされたカンマと、続きの行も扱われます。

位置は常に緯度と経度から投影されます。U/V からとることはありません。そのため、どのゲームの記録も、実際の世界の背景と同じ投影を共有します。

## DCS サーバー: 誰が勝ったか、各出撃がどう終わったか {#dcs-servers-who-won-and-how-each-sortie-ended}

DCS のマルチプレイヤーサーバーは、ミッションを 24 時間 Tacview で記録します。永続型の PvP サーバーは、その多くのミッションにまたがってキャンペーンを進めます。一方の陣営が、相手のすべての飛行場、FARP、ゾーンを奪うと勝ちです。これには何日もかかり、ミッションの再起動も何度もあります。記録に入っているのは飛行であって、キャンペーンではありません。誰が何を奪ったかを伝えるメッセージはなく、飛行場は最初に一度だけ書かれ、誰が勝ったかを示すものもありません。Tacview コンバーター（`node tools/acmi-to-parquet.mjs`、[`data/dcsOutcome.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/data/dcsOutcome.ts)）は、分かることをすべての行に加え、分からないことは空のままにします。推測は決してしません。

| 列 | 意味 |
|---|---|
| `server` | サーバーまたはキャンペーン。記録のヘッダーから取ります（その Title、Author、Comments が既知の公開サーバー、Blue Flag、SPS Contention、Growling Sidewinder を示します。それ以外では、誰かの名前を示す Author）。`--server Name` でフォルダー全体に名前を付けられます。ヘッダーがどのサーバーも示さない記録（`Admin` のような Author、既知のサーバーが書かない Title と Comments）は、どこにも割り当てません。`server` は空です。サーバーの記録ページからダウンロードしたものでも同じです。そのページには、ほかのコミュニティのミッションも含まれることがあるからです |
| `mission` | バージョンとキャンペーンの月を除いた記録の Title。`Operation_Example_V7.7.99` は `Operation Example` になります |
| `campaign` | 記録が属するキャンペーンラウンド。サーバー、マップ、番号で表します: `Example Server North 3`。1 つの記録が 1 つのセッション（再起動から再起動まで）です。1 つのラウンドは、多くのセッション、何日も何週間も続きます |
| `round` | そのラウンドの番号。サーバーが番号を公開していればその番号、そうでなければそのサーバーとマップで見た n 番目のラウンドです。ラウンドファイル（下記）から取り、なければ空です |
| `session` | ラウンドのセッションの中での記録の順番、1、2、...。`sessionStart` はその実際の開始時刻（Unix 秒）です |
| `heldRed`, `heldBlue` | セッション開始時に各陣営が持っていた係争地。連結したラウンドファイル（下記）から取ります |
| `won`, `matchWon` | 行の陣営（その Color、Red または Blue）がそのキャンペーンに勝ったとき 1、負けたとき 0。勝者を示すラウンドファイルがない場合と、中立の行では空です。キャンペーンはラウンドであり、同時にマッチでもあるので、両方とも同じ値です |
| `roundEndReason` | すべてを奪って勝ったキャンペーンでは `capture` |
| ラウンドのすべてのセッションの `won`, `matchWon` | ラウンドの結果。ラウンドの終わりが分かった時点で、そのすべての記録に書かれます |
| `sortie` | 航空機の行で、その飛行。離陸から離陸まで 1、2、...。最初の離陸前と着陸後の地上の時間は、それが属する飛行に数えます |
| `sortieResult` | その飛行がどう終わったか: `landed`、`landed damaged`（空中で被弾したあと）、`ejected`、`shot down`、`destroyed`（地上で）、`crashed`、`despawned`（原因が見えないまま空中で消えた。プレイヤーの退出）、`airborne at end`、`no takeoff` |
| `sortieKills` | その飛行でその航空機に記録された撃墜数 |

永続型サーバーでは、出撃こそが意味のある単位です。`sortieResult` = `shot down` でフィルターすると、どこで飛行が失われたかが分かります。[内訳](breakdown.md)で、ヒートを `sortieResult` や `server` ごとに分けることもできます。出撃を形作る離陸、着陸、脱出、撃墜、墜落は、コンバーターが航空機の動きから割り出すイベントです（上記）。

ラウンドの 2 つのセッションの間に奪われた場所（下記のラウンドファイルから分かります）は、あとの記録の開始時の `capture` イベントになります: `Object` `(campaign)`、その場所で、`Detail` `Red to Blue, between missions`、`Inferred` `between missions`。

記録の中で陣営が変わったことが見える飛行場や FARP（もう一方の色で書き直された、または削除されて 5 分以内に同じ場所にもう一方の色で書き直された）は、そのパッドでの `capture` イベントになります: `Event` = `capture`、`Airfield` はその名前、`Detail` `Red to Blue`、`Coalition` は新しい陣営です。ある色で初めて書かれたパッドは占領ではありません。これまでに調べたサーバーはパッドを一度だけ書くので、その記録には占領がありません。

### ラウンドファイル {#rounds-files}

ラウンドファイルは、サーバーごとに、キャンペーンラウンド、その勝者、各ラウンドのセッションを示します。サーバーが公開するもの、または記録そのもの（下記）から作ります。

キャンペーンに誰が勝ったかは、サーバーが公開するもの（ウェブページのキャンペーンログ）で、記録の中にはありません。ラウンドファイルがそれを運び、コンバーターは `--rounds file.json` でそれを読みます（複数指定できます）:

```json
{
  "format": "heat3d-dcs-rounds",
  "version": 1,
  "server": "Example Server",
  "source": "Example Server's public campaign log, read 2026-11-15",
  "rounds": [
    { "id": 41, "title": "^Example-Campaign-North$", "start": "2026-11-01T08:00:00Z", "end": "2026-11-04T19:30:00Z", "winner": "Blue", "endReason": "capture", "state": "won" },
    { "id": 42, "title": "^Example-Campaign-North$", "start": "2026-11-04T19:30:00Z", "end": null, "winner": null, "state": "in progress" }
  ]
}
```

記録は、その `server` のラウンドのうち、`title`（正規表現）が記録の Title に一致するものに属します。各行は、その実際の時刻が入るラウンドに属します。実際の時刻とは、記録の RecordingTime に行の秒数を足したもので、ゲーム内のミッションの日付ではありません。時刻は UTC です。勝者のないラウンド（入れ替えられた、まだ続いている）は、その行にラウンド番号と空の結果を与えます。

マッチ文書に当たる `acmi` フッターは、War Thunder のマッチの `result.source` と同じように、結果がどこから来たかを示します。`outcome.result` は `{ winner, round, endReason, source }` で、`source` はラウンドファイルの `source`、何も勝者を示さなかったときは `null` です。`outcome` には、記録のラウンド、占領、終わり方ごとの出撃も並びます:

```json
"outcome": {
  "server": "Example Server", "mission": "Example-Campaign-North", "kind": null,
  "result": { "winner": "Blue", "round": 41, "endReason": "capture", "source": "Example Server's public campaign log, read 2026-11-15" },
  "rounds": [{ "id": 41, "start": "2026-11-01T08:00:00.000Z", "end": "2026-11-04T19:30:00.000Z", "winner": "Blue", "endReason": "capture", "state": "won" }],
  "captures": 0,
  "sorties": { "landed": 31, "shot down": 12, "ejected": 3, "crashed": 2, "despawned": 9, "no takeoff": 4 }
}
```

そのキャンペーンで Blue 側のパイロット `Viper 1 (F-16C_50) #a01` の行は、次のようになります: `server` Example Server、`round` 41、`won` 1、`roundEndReason` capture、`sortie` 2、`sortieResult` landed、`sortieKills` 1。

### 記録そのものから作るラウンド {#rounds-from-the-recordings-themselves}

永続型サーバーは、再起動をまたいでキャンペーンを保ちます。各記録は、キャンペーンが残した場所にある両陣営の地上ユニットと静的オブジェクトから始まります。`node tools/dcs-campaign-rounds.mjs <out-folder> <folder>...` は、各記録の最初の数分を読み（[`data/dcsCampaign.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/data/dcsCampaign.ts)）、サーバーごと、マップごとに記録を時刻順に並べて、連結します:

- **場所**: 約 2 km のセルに分けた地面です。セッション開始時にそこにいるユニットの 4 分の 3 がある陣営のものなら、そのセルはその陣営のものです。*係争地*とは、両方の陣営が持っているのを見た場所です。
- **占領**: 次のセッションの開始時にもう一方の陣営が持っている場所です。ミッションの間に、または前のミッションの最中に奪われたものです。
- **新しいラウンド**: 場所が前のセッションと 60% を超えて違うセッションです。古いラウンドの一歩ではなく、新しいラウンドの開始配置です。サーバーが別のマップに移ったときも、ラウンドは終わります（そのセッションは最後のセッションのあとに始まり、続いていきます）。
- **誰が勝ったか**: 終わったラウンドでは、最後のセッションの開始時にすべての場所を持っていた陣営（`capture`、信頼度は高）です。そうでなければ、係争地を多く持っていた陣営です（相手の 2 倍なら中、それ以外は低。マップの変更で終わったときは低）。続いているラウンドには勝者がありませんが、各セッションがその開始時に各陣営の場所の数を示すので、どちらが優勢だったかが分かります。
- セッションがすべて同じ状態で始まるサーバーは、セッションの間に状態を保ちません。連結はしません。

最後のセッションの開始は、ラウンドの終わりの何時間も前のことがあるので、信頼度が大切です。勝者を公開しているサーバーと照らし合わせました。連結は、公開されたラウンドが始まったセッションで、新しいラウンドをすべて見つけました。そして、最後の開始時に優勢だった陣営は、確かめられた 9 ラウンドのすべてで、公開された勝者でした。`--official file.json` は、そのようなサーバーの公開ラウンドを保ち、連結で得たセッションを加えます。ファイルの `validation` は、連結がどこまで一致したかを示します。架空のキャンペーンの例:

```json
{ "id": 2, "campaign": "Example Server North 2", "title": "^(?:Example_North_V1\.0)$",
  "start": "2026-11-02T06:00:00.000Z", "end": "2026-11-06T12:00:00.000Z", "winner": "Red", "endReason": null,
  "state": "won (reset)", "confidence": "medium", "ahead": "Red",
  "sessions": [
    { "start": "2026-11-02T06:00:00.000Z", "red": 12, "blue": 11, "redAll": 30, "blueAll": 28, "captures": [] },
    { "start": "2026-11-02T12:00:00.000Z", "red": 14, "blue": 9, "redAll": 32, "blueAll": 26,
      "captures": [{ "lat": 42.36, "lon": 42.02, "from": "Blue", "to": "Red" }, { "lat": 42.4, "lon": 41.98, "from": "Blue", "to": "Red" }] }
  ] }
```

### キャンペーンラウンドをシリーズとして見る {#watching-a-campaign-round-as-a-series}

1 つのラウンドの記録（`campaign` が同じファイル）をまとめて読み込むと、ビューアはそれを 1 つのシリーズとして再生します。セッションを実際の順に 1 つずつ再生し、2 つのセッションの間の何時間、何日を 1 分の休憩に縮めます。タイムラインは各セッションの開始を黄色で、休憩を暗い帯で示し、時計は再生中のセッションとその実際の日付を示します（`session 4/12 · 2026-11-02 12:38 UTC`）。ヒート、リプレイ、フィルター、**インサイト**は、読み込んだほかのデータと同じように、シリーズ全体で動きます。**マッチ**タブの**キャンペーンラウンド**セクションには、セッションとその日付、各開始時に各陣営が持っていた係争地の数（ラウンド全体のグラフとしても）、その前に奪われた数が並びます。クリックすると、そのセッションの開始に移ります。1 つだけ読み込んだ記録は、そこに、どのラウンドのどのセッションかを示します。別々のラウンドの記録をまとめて読み込んでも、シリーズにはなりません。別々のマッチと同じように、それぞれがゼロから始まります。多数マッチローダー（**多数の試合を一度に**）も、ラウンドをシリーズとして再生します。何ギガバイトもあるラウンドのために、ストリーミングし、GPU に合わせた大きさにします。

ラウンドの間に持ち主が変わった場所は、マップに占領ゾーンとして描かれます。再生中のセッションの開始時にそれぞれを持っていた陣営の色で塗られ、セッションの境目で切り替わります。変わるたびに、リプレイのイベント一覧に占領が 1 つ入ります。これらは読み込んだ行から割り出します（連結と同じように、各セッションの最初の数分の地上ユニットと静的オブジェクトを、約 2 km のセルで見ます）。そのため、完全なローダーが必要です（多数マッチローダーは、各行のデータを少ししか残しません）。

**ラウンドの記録の 1 つから、ラウンド全体を読み込む。** 普通のブラウザーでは、ビューアはあなたが選んでいないファイルを開けません。ラウンドのファイルをまとめて読み込んでください。ローカルのビューアサーバー（`npm run dev` または `npm run preview`）から提供されていれば、開けます。git が無視する `tools/local-data.json` に、ラウンドファイルのフォルダーと変換済み記録のフォルダーを示す `campaigns` の項目を加えてください。すると、1 つの記録のキャンペーンラウンドセクションに **ラウンド全体を読み込む** が出て、そこで見つかったラウンドのセッションを取得し、多数マッチローダーで読み込みます:

```json
"campaigns": { "rounds": "D:/dcs/rounds", "recordings": ["D:/dcs/converted"] }
```

提供されるのは、ラウンドファイルが示す記録だけです（`tools/campaign-files.mjs`）。それらのフォルダーで見つからないセッションは、数えますが、読み込みません。

既知のサーバーが公開しているもの:

| サーバー | ラウンド | 陣営の勝ち方 | 勝者を読める場所 |
|---|---|---|---|
| SPS Contention | 1 つのマップと時代でのキャンペーン（何日も）、多くの再起動にまたがる | すべての飛行場、FARP、拠点を奪う。勝者なしで終わったキャンペーンは入れ替えられた | サーバーの公開キャンペーンログ（キャンペーンごとの勝者、開始、終了） |
| Blue Flag | 5 時間のミッション多数にまたがるキャンペーンラウンド。Title の `_YYYY_MM` は再起動ごとに 1 か月進む | 敵の陣地をすべて奪う。古いラウンドでは、決まった時間のあとに多く持っていた陣営が勝ち | これまでに見つかった形では公開されていない。記録の連結が各ラウンドと、各開始時に誰がどれだけ持っているかを追う |
| Growling Sidewinder | オープンコンフリクトのミッションの 1 回の実行（6 時間） | ゾーンと飛行場を奪う | 統計ページが示すのはパイロットで、結果ではない。どのセッションも同じ状態で始まるので、セッションをまたぐラウンドはない: 空 |
| AI と戦うミッション（ゾーン占領型のミッション） | 1 回のミッションの実行 | プレイヤーの陣営とミッションの AI の対戦: PvP の結果はない | 空 |
| 割り当てなし（ヘッダーがサーバーを示さない） | - | - | 空、`server` も空 |

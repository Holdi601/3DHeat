# 試合ごとに1ファイル: `.3dheat`

`.3dheat` ファイルは、1 試合全体を 1 つのファイルにまとめたものです。コピー、保管、共有ができます。開くには、ファイルをソースパネルにドロップするだけです。

```
match.3dheat   (ZIP ファイル)
  manifest      試合が何か、そして中に入っているものの一覧
  table         位置 (Parquet)
  match.json    試合のドキュメント
  sidecars      コンバーターがまるごと残したもの (イベント、メッセージなど)
```

変換された試合は、以前は複数のファイルが並んでいました。表 `<試合>.parquet`、試合のドキュメント `<試合>.match.json`、付属ファイル `<試合>.<内容>.parquet` です ([コンバーターはすべて残す](converters.md))。`.3dheat` ファイルは、これらすべてを 1 つに入れます。1 つのリプレイ、1 つのファイルで、コピー、保管、共有ができます。

千個読み込んでも、ばらばらの表を読み込むのと同じくらい速いように作られています。また、後のコンバーターは、新しい形式を作らなくても、ずっと多くのものを入れられます。

## 1 つを読み込む {#loading-one}

ファイルやフォルダーを読み込めるところならどこでも、`.3dheat` ファイルも読み込めます。フォルダーには、コンテナとばらのファイルを混ぜて入れても構いません。

| 場所 | コンテナから読まれるもの |
|---|---|
| **ヒートマップ** のソースパネル (ファイル、フォルダー、ドラッグアンドドロップ) | その表。ばらの `<試合>.parquet` であるかのように読まれます |
| **ヒートマップ → 多数の試合を一度に** (ファイル、フォルダー、フォルダーを追加) | その表。読み込み機能のワーカーが、その場で読みます |
| **試合** タブ (読み込む、またはビューにドロップ) | 試合のドキュメント |
| **作戦** ボードのテレメトリ | その表 |

コンテナを開くと、その 2 つの小さな部分だけが読まれます。末尾にあるディレクトリと、先頭にあるマニフェストです。表の中身は、読み込み機能がそれを読むまで、一切読まれません。付属ファイルと試合のドキュメントは、何かがそれを求めたときだけ読まれます。同じ試合が、ばらとまとめた形の両方でフォルダーにあれば、一度だけ読み込まれます。

## まとめる、ほどく {#packing-and-unpacking}

新しい変換は、既定でコンテナを書きます。War Thunder のコンバーター (`heat3d-wt-replay`)、CS2 のコンバーター (`heat3d_cs2 demos`)、Tacview のツール (`node tools/acmi-to-parquet.mjs`) です。`--loose` を付けると、別々のファイルのままにします。

以前に、または別のツールで変換された試合は、次のコマンドでまとめます。

```
node tools/3dheat-pack.mjs <フォルダー>... [--delete-loose] [--jobs N] [--settle MIN]
node tools/3dheat-pack.mjs unpack <フォルダーまたは file.3dheat>... [--delete-container]
node tools/3dheat-pack.mjs verify <フォルダーまたは file.3dheat>...
node tools/3dheat-pack.mjs update <file.3dheat> [--add <役割>[:<名前>]=<ファイル>]... [--remove <名前>]...
node tools/3dheat-pack.mjs repack <フォルダーまたは file.3dheat>...
```

- **pack** は、フォルダーの下にあるすべての `<試合>.parquet` の表を、それに属するファイルとともに探し、その隣に `<試合>.3dheat` を書きます。すでにまとめられた試合は飛ばします。書いた各コンテナは、ほかの何よりも先に、全体を読み直します (各メンバーの sha256、サイズ、CRC、Parquet のフッター)。ばらのファイルは `--delete-loose` を付けたときだけ削除されます。前にまとめた試合では、ばらのファイルがコンテナの中身とバイト単位で同じときだけ削除されます。`--settle` の分 (既定では 10 分) の間に変更されたファイルがある試合は、そのままにされます。コンバーターがまだ書いている最中かもしれないからです。
- **unpack** は、メンバーをコンテナの隣に、ばらのファイルとして書き出します。
- **update** は、コンテナにすでにある表を書き直さずに、メンバーを追加または置き換えます (下を参照)。
- **repack** は、コンテナ全体を書き直し、更新で残ったものを捨てます。

## 形式 {#the-format}

`.3dheat` ファイルは ZIP アーカイブです (どの ZIP ツールでも開けます)。規則は次のとおりです。

1. コンテナを書くとき、**`manifest.json` が最初のメンバー** です。必ず存在します。ZIP の中央ディレクトリから見つけられるので、`update` の後には、ファイルの後ろの方にある場合もあります。
2. **バイト範囲で読まれるもの、またはすでに圧縮されているもの** は、そのまま格納されます (ZIP の方式 0)。Parquet、Arrow、画像、モデル、音声、動画、不透明な塊などです。格納されたメンバーは、コンテナの中の連続したバイト範囲 1 つです。そのため、読み手は、ブラウザなら `File.slice`、HTTP なら範囲リクエストで、表のフッターと列のチャンクをその場で読めます。ばらのファイルを読むのとまったく同じです。
3. **テキストは圧縮されます** (方式 8)。JSON、CSV、プレーンテキストです。小さく、まるごと読まれます。
4. 名前は UTF-8 (フラグのビット 11)、相対パス、区切りは `/`、`..` は含みません。フォルダーを含むこともできます (`analysis/heat.json`)。まとめられたばらのファイルは元の名前を保つので、ほどくと同じファイルが戻ります。
5. 4 GiB を超えるメンバー、または 65,535 を超えるメンバーを含むコンテナは、通常どおり ZIP64 を使います。書き手は、メンバーの後にデータ記述子を置きません。

コンバーターが今書くメンバーは、この順番です。

| 役割 | メンバー | 格納 |
|---|---|---|
| `table` | `<試合>.parquet` | はい |
| `match` | `<試合>.match.json` | いいえ (圧縮) |
| `messages`、`flight`、`events`、`effects`、`objectives`、`packets`、`props`、`strings` など | `<試合>.<役割>.parquet` | はい |
| `summary` | `<試合>.summary.json`。マスインデックスの要約 ([マスアナリシス](mass-analysis.md))。`tools/3dheat-summarize.mjs` が追加 | いいえ (圧縮) |

表は、マニフェストのすぐ後に来ます。そのため、読み手がファイルの先頭を最初に読むときに、マニフェストと表のローカルヘッダーが一緒に読まれます。

### マニフェスト {#the-manifest}

```json
{
 "format": "3dheat",
 "format_version": "1.0",
 "game": "warthunder",
 "source": "client replay",
 "converter": { "name": "heat3d-wt-replay", "version": "0.2.0" },
 "match": "<map>_RB_<date>_<session>",
 "map": "<map>",
 "mode": "RB ground",
 "started": "2026-01-01T12:00:00+00:00",
 "created": "2026-01-01T13:00:00.000Z",
 "roles": { "table": "<match>.parquet", "match": "<match>.match.json", "flight": "<match>.flight.parquet" },
 "members": [
  {
   "name": "<match>.parquet",
   "role": "table",
   "media_type": "application/vnd.apache.parquet",
   "compression": "stored",
   "bytes": 1738575,
   "rows": 38105,
   "sha256": "<64 桁の 16 進数>",
   "schema": { "id": "heat3d-table", "version": "1" }
  }
 ]
}
```

| 項目 | 意味 |
|---|---|
| `format` | いつも `3dheat` |
| `format_version` | `major.minor` (下を参照) |
| `game`、`source`、`converter`、`match`、`map`、`mode`、`started` | 試合が何か、そして何がそれを作ったか。不明な場合は `null` |
| `created`、`updated` | 書かれた時刻、最後に更新された時刻 (`updated` は更新の後にだけ出ます) |
| `roles` | 役割ごとに、その最初のメンバーの名前。手早い索引です |
| `members` | マニフェストを除くすべてのメンバー。完全な一覧で、読み手が信頼するものです |
| `matches` | 任意。複数の試合を入れたコンテナの試合 (下) |
| `references` | 任意。コンテナが必要とするが、中には入っていないファイル |
| `extensions` | 任意。コンバーター独自のメタデータ |

各メンバー:

| 項目 | 意味 |
|---|---|
| `name` | コンテナの中のパス |
| `role` | 何のためのものか (下) |
| `media_type` | `application/vnd.apache.parquet`、`application/json`、`image/png`、`model/gltf-binary`、`audio/ogg`、`application/octet-stream` など |
| `compression` | `stored` または `deflate` |
| `bytes` | サイズ (圧縮されていない状態) |
| `sha256` | その中身の (圧縮されていない状態の) ハッシュ |
| `rows` | 表の行数 |
| `schema` | 従う約束事。`{ "id", "version" }`。ドキュメントは自身の `format` と `version` (`heat3d-wt-replay-match` の 2)、ビューアが `heat3d` のフッターで読む表は `heat3d-table`、Tacview ツールの表は `heat3d-acmi-table` |
| `match` | 複数の試合を入れたコンテナでは、属する `matches[].id` |

### 成長できるように作る {#made-to-grow}

この形式は、今のものより、はるかに豊かなリプレイを運べるように作られています。しかも、今それを読んでいるものを壊しません。

- **バージョン管理。** `format_version` は `major.minor` です。読み手は、自分の major のすべての minor を読み、知らないフィールドはすべて無視します。何かが追加されると minor が上がります。major が上がるのは、古い読み手が誤って読んでしまうようにレイアウトが変わるとき (格納されなくなったメンバー、アーカイブの外へ移されたマニフェスト) だけです。各メンバー自身の約束事は、`schema` の中で別にバージョン管理されます。そのため、新しい表のレイアウトや新しいドキュメントのバージョンには、新しいコンテナのバージョンは要りません。最初に書かれたコンテナは、代わりに `"version": 1` と書いていました。読み手はそれを 1.0 として扱います。
- **役割は開かれています。** 役割は任意の文字列です。読み手は知っている役割を使い、残りはそのまま残します。知らない役割は一覧に出され、拒否されることはありません。`update` と `repack` は、それを手を加えずに運びます。役割には多数のメンバーがあっても構いません。複数の表 (ユニットごとの軌跡、別の頻度のテレメトリ)、イベント、音声、動画の同期、レベルの参照、フィギュアの上書き、分析結果などです。名前はフォルダーを含んでも構いません。
- **どんなメディアでも。** メンバーは、メディアの種類を持つものなら何でも構いません。Parquet、JSON、Arrow、PNG や JPEG のサムネイル、glTF のモデル、音声、生のブロブなどです。
- **複数の試合。** 1 つのセッションや大会を 1 つのコンテナに入れても構いません。`matches` がそれらを一覧にします (`{ "id", "map", "mode", "started", ... }`)。各メンバーは `match` で名前を挙げます。ビューアは、役割 `table` のすべてのメンバーを読み込みます。
- **参照。** コンテナが必要とするが中には入っていないファイル (たとえば、ある試合のレベル) は、名前と sha256 とともに `references` に一覧されます (`{ "kind": "level", "name": "...", "sha256": "..." }`)。そのため、正しいファイルが、すべての試合にコピーせずに見つかり、確かめられます。
- **拡張。** `extensions` には、コンバーター独自のメタデータが、その独自のキー `"<ベンダー>/<名前>": { ... }` の下に入ります。そのため、2 つのコンバーターが衝突することはなく、共有のフィールドに何かを足す必要もありません。
- **その場での更新。** `update` は、大きな格納された表を書き直さずに、メンバーを追加または置き換えます。新しいメンバーと新しいマニフェストは、コンテナの末尾の後に追記され、その後に新しい中央ディレクトリが続きます。置き換えられたものは、`repack` まで、参照されないバイトとして残ります。すべてのメンバーと、すべてのマニフェストのフィールド (知っているものも知らないものも) は保たれます。失敗した更新は、元のコンテナの状態まで切り戻されます。

ビューアのテストは、これを守らせています。形式 1.7 のコンテナで、知らない役割、メンバーのフィールド、拡張、フォルダーの中の音声メンバーを含むものは読み込まれ、更新と再まとめを経てもそのすべてが残ります。major 2 のコンテナは拒否されます。

## 書き手 {#writers}

- Node: [`tools/container.mjs`](https://github.com/Holdi601/3DHeat/blob/main/tools/container.mjs) (書く、読む、確かめる、更新する、再まとめする)。まとめるツールと Tacview のツールが使います。
- Python: `container.py`。標準の `zipfile` を使った約 140 行で、各コンバーターに同じファイルがあります (`heat3d_ext_warthunder/container.py`、`heat3d_cs2/container.py`)。そのため、どのコンバーターも別のコンバーターに依存しません。新しいコンバーターは、これをコピーします。
- ビューアは、[`src/data/container.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/data/container.ts) で読みます。

# メモリ、予算、収まるかの確認

お使いのコンピューターのメモリには限りがあります。3DHeat はファイルに必要な量を合計し、**読み込む**の前に、収まるかどうかを伝えます。

![メモリの見積もりが「収まらない」と表示され、「[N] 行ごとに読み込む」が入力済みで、読み込みボタンには「大きすぎる - 減らすか間引く」と表示されている](../assets/img/en/memory-and-budgets-wont-fit.webp)

*このコンピューターには大きすぎますか。3DHeat は代わりに、N 行ごとに読み込むことを提案します。*

読み込みの途中でブラウザのタブのメモリが尽きると、タブはクラッシュし、何分もの作業が失われます。また、GPU が持っている以上のものを求められると、コンテキストを失うか、極端に遅くなります。そのため、読み込みを始める前に、ソースパネルは必要なメモリ量を示し、このマシン用に検出した予算と比べます。収まらない場合は、逃げ道を示したうえで止めます。モデルは [`src/data/memory.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/data/memory.ts) にあります。

## メモリの見積もり {#the-memory-estimate}

行が数えられると、**読み込む**ボタンの上に表示されます。

| 行 | 意味 |
|---|---|
| **メモリの見積もり** - *収まる* / *ぎりぎり* / *収まらない* | 判定。緑、黄、赤で表示します。 |
| `N rows · B B/row` | 読み込まれる行数（間引き後）と、行ごとの定常的なバイト数。 |
| `RAM X resident, Y peak while loading` | 読み込み後に保持されるメモリと、読み込み中の最大値。 |
| `GPU Z · est. load T` | 行のための GPU メモリと、毎秒120万行で見積もった時間。 |
| GPU 名 | ドライバーが報告すれば、レンダラーの名前。 |
| メッセージ | 収まらない理由、またはぎりぎりの理由と、するべきこと。 |
| **[N] 行ごとに読み込む** | 間引きの間隔（下記）。 |
| `Budget: X RAM, Y GPU. Adjust under Performance → Resource budgets.` | 確認に使った予算。 |

### 行ごとのバイト数 {#bytes-per-row}

| 列 | 定常（RAM） | 備考 |
|---|---|---|
| 位置 | 12 | 32ビットの浮動小数点数3つ。常に（平らな軸も配列として） |
| 時刻 | 4 | 割り当てられている場合 |
| 寿命 | 4 | 時刻と人が割り当てられている場合 |
| 人 | 4 | 割り当てられている場合 |
| グループ | 2 | 割り当てられている場合 |
| セッション | 4 | 割り当てられている場合 |
| `Source file` | 4 | 2つ以上のファイルを読み込む場合 |
| フィルター用の各列 | 4 | 「フィルターに使う」にチェックした列ごと |

**ピーク**は、読み込みの間だけ必要な分を加えます。結合中の64ビット時刻の8バイト、並べ替えのキーと索引の12バイト、置換の作業用4バイト（時刻が割り当てられていればこの3つすべて）、グループ列がまだ32ビットの間の4バイトです。その合計に **2.0** を掛けます。この係数は測定して決めました。実際に複数ファイルを読み込んだとき、ピークは項目ごとの配列の1.9倍になりました（Parquet のデコーダーの作業用の領域、列を行数に合わせて切り詰めるためのコピー、解放済みだがまだ返されていないメモリによるものです）。見積もりが少なすぎるとタブのクラッシュになり、多すぎても不要な間引きになるだけなので、切り上げています。

**GPU** では、行ごとに8バイト（位置とグループ、それぞれ16ビット）かかり、時刻と寿命の両方（時刻と人が割り当てられている場合）は、さらに4バイト（それぞれ16ビット）かかります。[GPU メモリの常駐](gpu-memory.md)を参照してください。フィルターのテクスチャ（有効なフィルターごとに、行ごと4バイト）と、線のヒートのセグメントの開始点（線モードがオンの間、行ごと8バイト）は、この見積もりには含まれません。

## 収まるかの確認 {#the-fit-check}

3つの制約を比べます（[`checkFit`](https://github.com/Holdi601/3DHeat/blob/main/src/data/memory.ts)）。

- ピークの RAM と **RAM の予算**。
- GPU のバイト数と **GPU の予算**。
- 時刻の列が割り当てられている場合は、行数と、**並べ替えの上限** 4億行。

3つの比率のうち最も厳しいものが判定します。70%までは*収まる*、100%までは*ぎりぎり*（読み込めるはずですが、遅くなると思われます）、それを超えると*収まらない*です。収まらない場合、パネルは制約のうち何が原因かを示し、次のことを提案します。

- *N* 行ごとに読み込む。*N* = ⌈行数 / 収まる行数⌉ で、間隔の欄に入力されます。
- フィルターの列を減らす。時刻の列の割り当てを外す（並べ替えと、その上限がなくなります。ただしタイムラインは使えなくなります）。または予算を上げる。

予算そのものがハードウェアの事実ではない場合（ブラウザが RAM の数値を制限している、既定値が今の空き容量で抑えられている、GPU の数値が推定である）は、メッセージでそう伝えます。そのため、不要な間隔を選んでしまうことはありません。

### 間引き {#decimation}

**[N] 行ごとに読み込む**は、ファイルごとに数えて、*N* 行に1行を残します。熱は平均なので、N 行ごとの行は同じ分布をより多くのノイズとともに与えます。これは、描画がフレームごとにすでに行っているのと同じトレードオフです。欄は1（*row (all)*（すべての行））から始まります。選択が収まらない場合は、自分で入力していなければ、提案された間隔が入力されています。読み込みボタンは *Load N files (1 in K)*（N 個のファイルを読み込む（K 行に1行））と表示され、データセットの名前には `every Kth row`（K 行ごと）が記録されます。

### 並べ替えの上限 {#the-sort-ceiling}

描画は行を時刻の昇順で必要とするため、時刻の列が割り当てられていると、すべての行を並べ替える必要があります。32ビットのキーによる基数ソートです（[`sort.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/data/sort.ts)）。**4億**行を超えると、タブの中で試みるのではなく拒否します。これは読み込みの前に確認されるため、上限を超える選択は、全部読んでから最後の段階で失敗するのではなく、間隔の提案とともに拒否されます。上限の近く（*ぎりぎり*）では、パネルが、並べ替えには独自の進行表示がない長い処理になると警告します。時刻の列がなければ並べ替えは行われず、上限も適用されません。

## 資源の予算 {#resource-budgets}

**パフォーマンス → 資源の予算**（パフォーマンスパネルの下端にある折りたたみ行。`Resource budgets - RAM, GPU, cores` と表示されます）。予算は検出されます。検出された値が既定値になり、スライダーは**上限**を超えません。上限は検出された値ですが、検出が計測値だと確認できていない場合は例外です。

| 操作 | 範囲 | 意味 |
|---|---|---|
| **行データ用RAM** | 256 MiB から RAM の上限まで（対数） | 収まるかの確認に使う RAM の予算。既定の検出値を超えると *(above detected)*（検出値より上）、上限では *(max)*（最大）と表示されます。 |
| **行データ用GPU** | 128 MiB から GPU の上限まで（対数） | 収まるかの確認と、行のアップロードに使う GPU の予算。既定の検出値を超えると *(above detected)*、上限では *(max)* と表示されます。 |
| **パーサーのスレッド数** | 1 から論理コア数まで | 読み込みで同時に解析するファイル数。それぞれ別のワーカーで解析します。既定はコア数 - 2（4コア以下なら コア数 - 1）。[パーサーのスレッド数](#parser-threads)（開発者向けの項）を参照してください。 |
| ソースの行 | | 各数値の出所（`RAM: …. GPU: …. CPU: ….`）。 |
| **再検出** | | 開発サーバーに新しいメモリの値を問い合わせ、すべての予算を計算し直します。 |
| GPU 名 | | アダプターの短い名前。完全なレンダラーの文字列はツールチップに出ます。 |

### GPU の予算を上げる {#raising-the-gpu-budget}

検出された値より高い GPU の予算は、設定どおりに適用されます。収まるかの確認とアップロードは、同じ値を1つの関数（[`effectiveGpuBudget`](https://github.com/Holdi601/3DHeat/blob/main/src/render/budget.ts)）から受け取ります。その関数は、スライダーが止まる GPU の上限でのみ制限します。そのため、確認を通った読み込みは、全部アップロードされます。検出値を超えると、スライダーは *(above detected)* と表示します。その数値はそのときあなたがカードについて判断したものであり、計測値ではありません。カードが持つ量より高く設定すると、コンテキストの喪失や極端な遅さにつながるおそれがあります。

## 大規模なデータセット：取れる手段 {#huge-datasets-the-levers}

負担の軽いものから、最も極端なものの順です。

1. **フィルターの列を減らす。** 1つごとに、行ごと4バイトと、デコードの1回分の処理がかかります。
2. **間隔。** N 行ごとに1行。
3. **時刻の列なし。** 並べ替えも、並べ替えの上限も、時刻と寿命のための行ごと4〜8バイトもなくなります。ただしタイムラインもなくなります。
4. **予算を上げる。** メモリがあることがわかっている場合。

描画のときには、大きなデータセットは、データを減らすのではなくサンプリングと段階的な累積で扱います。[サンプリングと予算](sampling-and-budgets.md)を参照してください。

## 開発者向け {#for-developers}

### パーサーのスレッド数 {#parser-threads}

複数のファイルを読み込むとき、**パーサーのスレッド数**までのファイルを同時に解析します。それぞれは、その読み込みのために取り込みワーカーが起動したパーサーワーカーで解析されます（[`ingestFiles.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/data/ingestFiles.ts)、`parseInOrder`）。1のときや、ファイルが1つのときは、取り込みワーカー自身で、ファイルを1つずつ順に解析します。

同時に複数を解析しても、収まるかの確認は緩みません。

- **結合先を先に数えます。** 結合後の列は、最初のファイルを読む前に、選択全体のために割り当てられます。そのため、処理中のファイルには、RAM の予算がその隣に残した分だけが与えられます（`parseHeadroom`）。読み込む行ごとに、位置、64ビットの時刻、視線角、人、32ビットのグループ、セッション、フィルターの列、`Source file` を含みます。行数が CSV の推定の場合は2.6倍します。小さな列がより大きな列へ伸びていくためです。
- **各ファイルは、開始前にそのコストを確保します**（`fileParseBytes`）。その行数（Parquet のフッターから。CSV はサイズに応じた推定の割合）に、同じ列を掛け、**8** を掛けます。ブロックそのもの、位置のない行を捨てている間の隣のコピー、デコーダーの作業用の領域（テキストの列では、ID よりずっと大きくなります）の分です。ファイルは全体を読み、後で間引くので、間隔ではこれを減らせません。8 という係数は測定で決めました。3 や 5 では、人とセッションの名前を含む8600万行で、30個のパーサーのスレッドがタブの上限を超えましたが、8 では超えませんでした。
- **別のファイルは、残りの中にその確保が収まる場合にだけ始まります。** 終わっているのに、先のファイルの結合を待っているファイルは、結合されるまで確保を保持します。
- **1つのファイルは必ず動きます。** 何も確保されていないときは、次のファイルがどれだけのコストでも始まります。これは、収まるかの確認が認めた1つずつの読み込みそのものです。そのため、予算がぎりぎりの場合は、拒否せずにこの方式に戻ります。

*読み込み中のピーク*の値は、1つずつの読み込みのピークです。これは、すべてのファイルを読んだ後の並べ替えのときに出ます。並んで解析されるファイルは、読んでいる間にその値より多くのメモリを使うことがあります。確保が、上の見積もりが正しい範囲で、RAM の予算の中に収めます。

結合の順序は、ファイルが終わる順番にかかわらず、選択の順序です。そのため、人、グループ、セッションの番号、行、`Source file` の値は、1つずつの読み込みとまったく同じです。読めないファイルは、これまでどおり飛ばされ、一覧に出ます。パーサーのワーカーが死ぬと、読み込み全体が止まります。取り込みワーカーが死ぬ場合と同じです。読み込みが終わるときは、どのように終わってもすべてのパーサーのワーカーを停止します。パーサーのワーカーをまったく起動できない場合は、取り込みワーカーでファイルを解析します。

### 数値の検出方法 {#how-the-figures-are-detected}

[`detectBudgets`](https://github.com/Holdi601/3DHeat/blob/main/src/data/memory.ts) は、起動時に、描画が準備できたあとにもう一度、そして**再検出**のときに動きます。

**RAM、開発サーバーがある場合。** `start.bat` と `npm run dev` は、マシンのメモリを読める process からページを配信し、その値は `/__host/memory` にあります（1.5 秒以内に答えるか、無視されます）。既定値は、搭載 RAM の60%と、今の空き RAM の80%のうち小さい方です。上限は搭載 RAM の60%です。空き容量が既定値を抑えている場合は、パネルがそう表示し、プログラムを閉じてから**再検出**を押すよう提案します。

**RAM、開発サーバーがない場合**（静的な配信）。どのブラウザ API も空きメモリを報告しません。また、`navigator.deviceMemory` は2の累乗に切り捨てられ、Chrome と Edge では 8 GiB で頭打ちになります。既定値は `deviceMemory` の60%で、ブラウザが報告している場合は、さらにタブの空き JS ヒープの4倍で制限します。何も報告がなければ 4 GiB です。`deviceMemory` がちょうど 8（上限）と読める場合、その数値は *capped*（頭打ち）とマークされ、上限は既定値の4倍になります。既定値を超えると、その数値は計測値ではなくあなたの主張であることも、注記されます。

**どちらの場合も**、RAM の既定値と上限は **12 GiB** で頭打ちにします。マシンが何を持っていても、Chrome のタブ1つが持てる型付き配列のメモリの最大値だからです（あるページは約15.75 GB に達して失敗しました。12 なら、ほかのすべてのための余地が残ります）。また、256 MiB を下回ることはありません。

**GPU メモリ。** どの Web API もこれを報告しません。

- 開発サーバーがある場合は、カードのメモリを `nvidia-smi`（最大のアダプター）から、または Windows では、ディスプレイアダプターのレジストリ値 `HardwareInformation.qwMemorySize` から読みます。既定値はその70%、上限は90%です。
- 読み取り値がない場合は推定します。既定は 2 GiB です。最大のテクスチャが 16,384 px 以上の場合（ディスクリートのカード）は 4 GiB、それより小さい場合は 1 GiB です。WebGPU の `maxBufferSize` の8倍のほうが大きい場合は、その8倍を使います。推定は、統合型と独立型を区別するだけで、それ以上細かくはわからないため、上限は推定値の8倍になります。パネルは、その数値が推定であることを示します。
- 128 MiB を下回ることはありません。

**CPU。** `navigator.hardwareConcurrency`（報告がない場合は 4）。

# 渲染內部機制

檢視器會把數百萬個點畫成發光的光斑，再把它們加總起來。這一節說明讓這件事保持快速的技巧，以及統計浮層中數字的意義。如果檢視器感覺很慢，或你想修改渲染器，請閱讀這一節。

```
資料 -> 時間窗 -> GPU 過濾 -> 取樣計畫 -> 潑灑 -> 累積 -> 上色 -> 螢幕
```

要查看你自己的電腦運作狀況，請看檢視畫面右上角的統計方塊：[效能面板與統計浮層](performance-and-stats.md)。新名詞（GPU、資料列、sprite、熱度圖）見[詞彙表](glossary.md)。

## 核心問題 {#the-core-problem}

許多重疊的徑向漸層加總起來，每個影格的代價是 *N* × π*r*² 個混合片段。若有 1 億個半徑 8 px 的 sprite，就是 2 × 10¹⁰ 個片段——在高階 GPU 上大約要一秒的工作量。不可能每個影格都用暴力計算，所以檢視器結合了以下做法：

- **依時間排序的資料列**——一個時間軸視窗只需要兩次二分搜尋，播放的成本取決於視窗中的資料列，而不是整個資料集；
- **CPU 每個影格對每個資料列都不做任何事**——資料列以量化的形式存放在 GPU 記憶體中；過濾、群組正負號、生命週期測試、視窗、剔除與切片，全都在頂點著色器中計算；
- **分層取樣**，當一個影格無法繪製所有資料列時，使用補償權重；而**漸進式累積**會在視角不動時，收斂到精確的「全部資料列」結果（[取樣與預算](sampling-and-budgets.md)、[累積](accumulation.md)）；
- **兩段式節流**，先犧牲每個影格的 sprite 數，再犧牲熱度解析度，以換取影格率（[取樣與預算](sampling-and-budgets.md#the-adaptive-budget)）；
- **強制執行的記憶體預算**，因此放不下的資料集會以明顯的方式被截斷，而不是當機（[GPU 記憶體駐留](gpu-memory.md)）。

## 一個影格 {#one-frame}

影格迴圈是 [`Engine.frame`](https://github.com/Holdi601/3DHeat/blob/main/src/render/engine.ts)。所有以影格率變化的東西——攝影機、播放頭、預算——都放在引擎中，而不是應用程式狀態中，所以一個影格不會產生任何 React 工作；狀態每個影格只讀取一次，並且只為低頻率的讀數寫回。

1. **有新資料嗎？** 新資料集會在某一個影格宣告（*正在將 N 個資料列上傳到 GPU*），並在下一個影格上傳，這樣訊息會在工作阻塞執行緒之前先畫出來。新關卡會交給渲染器；線條熱度路線會被建立或釋放。
2. **播放頭前進**（每個影格最多 0.1 秒的實際時間），循環或停止。
3. **攝影機**讀取鍵盤、滑鼠與遊戲手把；座標軸鏡像會併入檢視矩陣；在 WebGPU 上，深度重映射矩陣會把 three.js 的 OpenGL 式深度範圍轉換成 WebGPU 的範圍。
4. **哪些內容可見**：來自時間軸與歷史的時間範圍；群組正負號表（只有在依某欄位分割時才用於可見性）；最多四個過濾器——欄位過濾器與實體選擇；差異分割。
5. **顏色與曲線表**若設定有變，就會重建。
6. **預算**：自適應控制器設定這個影格的 sprite 預算與熱度解析度；開啟*每個影格繪製所有資料列*時，預算會提高到涵蓋每個候選資料列。
7. **簽章**決定累積緩衝區還代表什麼：任何會改變哪些資料列如何貢獻的內容（*幾何*）、時間視窗，或只改變結果上色方式（*合成*）的變更。見[累積](accumulation.md#what-restarts-it)。
8. **取樣計畫**：要繪製哪些資料列區塊（[取樣與預算](sampling-and-budgets.md)）。
9. **累積模式**：重設、延伸、移動平均、running mean，或閒置。
10. **箱形重播幾何**（方塊、軌跡）在 CPU 上計算，只在該模式下，且只在非閒置時。
11. **渲染**：後端繪製場景（關卡、格線、座標軸、箱形、軌跡、量尺），將熱度潑灑到熱度目標中，合併進累積器，並把熱度疊在場景上合成到畫布。
12. **自動曝光**在倒數計時歸零時觸發；量尺的熱度探測最多每 120 毫秒讀取一個像素；讀數會被發佈。

閒置影格（已收斂，沒有任何變化）會跳過場景與潑灑，但仍然會**重新合成**：沒有設定 `preserveDrawingBuffer` 建立的 WebGL 畫布，在合成之後內容是未定義的，所以不能依賴它保留上一個影格。場景與熱度目標是檢視器自己的幀緩衝區，會保留內容，所以閒置影格只需要一次全螢幕通道。

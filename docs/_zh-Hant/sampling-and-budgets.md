# 取樣與預算

當一個影格中要繪製的點太多時，檢視器會繪製一個均勻的樣本，並讓每個點代表更多的量，使畫面保持正確。控制器會調整它繪製的數量，讓檢視器維持其影格率。

## 效能面板控制項 {#performance-panel-controls}

| 控制項 | 預設值 | 範圍（撥動） |
|---|---|---|
| **每個影格繪製所有資料列** | 開啟 | |
| **自適應預算** | 開啟 | |
| **目標 FPS** | 60 | 20-240（1000） |
| **起始 Sprite／影格**（自適應）或 **Sprite／影格** | 4.00M | 65,536-268,435,456，對數刻度（268,435,456） |
| **熱度解析度** | 100% | 25-100%，再乘以自適應第二階段的比例 |
| **漸進式精緻化** | 開啟 | 關閉時：每個影格都是全新的單影格估計（有助於查看原始樣本）。 |

另見[效能面板與統計覆蓋](performance-and-stats.md)。

## 給開發者 {#for-developers}

### 候選資料列 {#candidate-rows}

資料列以時間遞增的順序保存。時間軸視窗 [*lo*, *hi*] 會透過對時間欄位的兩次二分搜尋，轉換為一個資料列範圍（[`candidateRange`](https://github.com/Holdi601/3DHeat/blob/main/src/render/sampling.ts)）；沒有時間欄位時，每個資料列都是候選。這些即統計覆蓋中的**時間窗內資料列**。逐列的測試（篩選器、群組、分割、剔除、切片、存續期）稍後會在著色器中進行；未通過測試的資料列只會消耗一次頂點呼叫，不會產生任何片段。

### 取樣計畫 {#the-sampling-plan}

[`planFrame`](https://github.com/Holdi601/3DHeat/blob/main/src/render/sampling.ts) 會把候選範圍切分為**每塊 4,096 個連續資料列**的區塊，並從影格的 Sprite 預算中決定要繪製多少個：

- 若預算能涵蓋每個區塊，則全部繪製——該影格是精確的。
- 否則，區塊會以均勻的步幅在範圍內取樣，並加上一個每個影格都以黃金比例前進的抖動偏移，因此連續的影格會涵蓋不同的區塊，聯集會均勻地填滿。這是**分層**取樣：時間範圍的每個部分都會在每個影格中出現。

每個被繪製之資料列的熱度，都會乘以**候選數 / 提交數**，因此在任何預算下，一個影格的期望熱度都是精確的；只有雜訊會隨預算而變。資料列以每塊 8,388,608 個的區段保存（見[GPU 記憶體駐留](gpu-memory.md)）；區塊若跨越區段邊界就會被切開，每個區段會取得它必須繪製的區塊起點清單。

一個計畫最多只能包含 65,536 個區塊——即 268,435,456 個 Sprite——因為兩種後端都保存了一個固定 65,536 槽位的區塊起點緩衝區。超過此數的請求會被限制在此上限，不足的部分會誠實地以更多影格來收斂。

### 每個影格繪製所有資料列 {#draw-every-row-each-frame}

**效能 → 每個影格繪製所有資料列**（預設**開啟**）：預算會變成下限而非上限，而開始新估計的影格會繪製它負責的每一個資料列（上限為 2.68 億）。

原因：鏡頭移動會捨棄累積結果，因此移動中的影格只是一個單次估計，其雜訊取決於它繪製了多少資料——只畫了四分之一時，你看到的就是四分之一的資料，化為明亮的加權點，這正是移動中的視角會閃爍的原因。全部繪製則讓每個影格都是完成的畫面。代價是影格時間現在會隨時間窗內的資料量而變；可以調整的槓桿有：更窄的時間窗、篩選器，或距離剔除，它們是減少候選數，而不是讓取樣變得更稀疏。

在無力一次負擔整個熱度場的硬體上，請關閉它：此時 *Sprite／影格*就是真正的上限，而視角會在幾個靜止的影格中收斂。

完整計畫的成本（在高階桌上型 GPU、4K 畫布、大型關卡上測得，Sprite 半徑 1 m，即一兩個像素）：每個影格約 1 億個 Sprite 時為 30 fps，2 億個時為 15 fps，最大值 2.68 億個時約為 12 fps。在如此小的 Sprite 上，頂點階段就是全部成本，而熱度解析度完全不影響；對於大型 Sprite，成本則在填充：800 萬個半徑 100 m 的 Sprite，在全熱度解析度下每個影格耗時 2.5 秒，在 25% 時為 170 ms。因此**每個影格繪製所有資料列**會從 6,700 萬開始，當影格耗時低於 150 ms 時每個影格增加四分之一，當耗時超過 400 ms 時減半，使得繁重的視角不會讓單一影格超過 GPU 監控程式所允許的時間。

### 自適應預算 {#the-adaptive-budget}

**效能 → 自適應預算**（預設開啟）會調整 Sprite 預算，以維持**目標 FPS**（[`BudgetController`](https://github.com/Holdi601/3DHeat/blob/main/src/render/sampling.ts)）。在盒子重播與影片算繪期間，它處於閒置狀態。

輸入值為影格時間，經過平滑處理（90% 舊值 + 10% 新值，單一影格最多計 2 秒），目標為 1000 / max(15, 目標 FPS) ms。

**第一階段——Sprite。**每個影格，預算會乘以 `1 + (target / frame - 1) × gain`，速度太慢時增益為 0.35，有餘裕時為 0.08，每個影格的倍率限制在 0.5-1.25，預算限制在 65,536-268,435,456 個 Sprite。

**第二階段——解析度。**只有當預算已降到下限，而影格仍然比目標慢 10% 以上時，熱度緩衝區的解析度才會下降，每個影格降低 8%，最低降到畫布的 25%；當有 30% 的餘裕時，每個影格回升 4%。片段成本與解析度的平方成正比，在平滑漸變下幾乎看不出差異。（在軟體算繪、一千萬個資料列與過大 Sprite 的條件下測得：每個影格從 141 ms 降到 17 ms。）比例會四捨五入到十六分之一；覆蓋層的*熱度解析度*會顯示它。

**放棄。**無論是 Sprite 造成的，還是繁重的關卡造成的，慢的影格看起來都一樣——沒有逐階段的計時。若預算停在下限，且影格在 30 個影格內持續低於目標的 70%，表示成本不是來自 Sprite：控制器會切換到**爬升**模式，每 14 個影格把預算乘以 1.5 並恢復解析度，只要影格時間仍在下限時的 1.5 倍之內。若爬升使情況惡化到超過此範圍，就會退回 60% 並恢復正常控制；達到目標則結束爬升。

關閉自適應預算時，預算就只是 **Sprite／影格**。

在開啟*每個影格繪製所有資料列*時，自適應預算仍會運作，但精確規則會把預算提高到足以涵蓋所有候選資料列，因此實際上它只控制解析度階段，以及不開始新估計的影格。

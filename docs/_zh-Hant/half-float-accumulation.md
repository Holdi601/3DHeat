# 半精度浮點累積

有些顯示卡只能用小型 16 位元數字保存熱度，這可能會切掉或捨入最熱的地方。檢視器會縮放數字，讓這種情況不會顯示出來。你不需要做任何事；這一頁是給開發者看的。

## 給開發者 {#for-developers}

無法混合到 32 位元浮點紋理中的裝置（WebGPU 上沒有 `float32-blendable` 與 `float32-filterable`，WebGL2 上沒有 `EXT_float_blend`），會得到一個 **16 位元浮點**（`r16float`）熱度目標：最大值為 65,504，尾數有 11 位元。密集的區域會達到數十萬，所以 16 位元目標會同時**截斷**與**捨入**，而捨入誤差會隨數值變大而增加——表現得非常特定：最密集的區域會顯示得比實際冷很多，而稀疏的區域看起來正常。有兩個機制來處理這件事；只有兩者都正常運作，畫面才會正確。

### 範圍：每次潑灑都乘上增益 {#range-a-gain-on-every-splat}

每次潑灑都會乘上一個**增益**，合成時再把它除回去，所以場會落在半浮點能很好處理的數值範圍內（[`heatGain`](https://github.com/Holdi601/3DHeat/blob/main/src/render/engine.ts)）：

```
estimate = 此資料集、半徑與中心強度的解析式飽和估計
gain     = 2 ^ round(log2(2048 / estimate))，指數限制在 -20..20
```

2048 在達到 65,504 之前，讓漸層頂端上方留有約 32 倍的餘裕。增益是**二的冪次**，所以估計值的小幅漂移不會改變它，也不會改變累積緩衝區；它也是[幾何簽章](accumulation.md#what-restarts-it)的一部分，因此變更會重新開始累積。

它錨定在解析式估計上，而刻意**不**錨定在飽和點上。飽和是在合成時套用的，正是為了讓拖曳飽和值時不會重新開始收斂；如果增益跟著它移動，緩衝區仍會保存以舊增益寫入的值，而合成會以新增益去除，兩個誤差會完全抵消，結果滑桿看起來就像沒有作用。

在 32 位元目標上，增益永遠是 1。

### 精度：從零開始的部分影格 {#precision-partial-frames-from-zero}

以 1/n 權重合併到累積器中的影格，會先從零開始潑灑到**暫存目標**，再混合進去，而不是以 1/n 權重直接潑灑到累積器中（[累積](accumulation.md#why-each)）。若直接潑灑，每個 sprite 的貢獻會只有它所加入的運行總和的 1/n，而半浮點會把這些數字捨入掉——像素越密集，情況越糟。從零開始，每個加數都與它所加入的總和相當，這和單一影格本來就在做的算術相同。

### 實測效果 {#measured-effect}

在一個密集的合成場景上，以相同單位讀取場的數值：

| | p50 | p90 | p99 | 最大值 |
|---|---|---|---|---|
| 32 位元（參考） | 6051 | 60742 | 121199 | 232744 |
| 16 位元，修正前 | 1372 | 6972 | 7840 | 7840 |
| 16 位元，修正後 | 5996 | 59666 | 118824 | 210357 |

峰值從低了 30 倍，變成 0.90 倍；合成後的影格與 32 位元的影格相比，平均亮度的差距在 0.1% 以內。

### 測試方法 {#testing-it}

`?heat=f16` 會在任一後端上強制使用這條路徑——沒有這個開關，只有較弱 GPU 才會執行的算術，就只會由那些實際在執行它的人來測試。`npm run smoke:f16` 會用它執行整個瀏覽器測試套件。

讀回會抵消增益：自動曝光會把讀到的場除以它，而 `engine.readHeatProbe()` 會把它傳給渲染器——[量尺的即時熱度讀數](measure.md#notes)也是這樣讀取的。

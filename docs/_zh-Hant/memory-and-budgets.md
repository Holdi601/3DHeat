# 記憶體、預算與容量檢查

你的電腦記憶體有限。3DHeat 會加總你的檔案所需的記憶體，並在你按**載入**之前告訴你它們是否放得下。

![記憶體估計顯示「放不下」，並預先填入「每 [N] 列載入一列」，載入按鈕顯示「太大——請減少或抽稀」](../assets/img/en/memory-and-budgets-wont-fit.webp)

*對這台電腦來說太大？3DHeat 會建議改為每隔 N 列載入一列。*

瀏覽器分頁若在載入途中耗盡記憶體，就會當機並失去數分鐘的工作；而 GPU 若被要求超出其所能提供的量，不是會失去其環境，就是會慢到幾乎停止。因此在載入開始之前，來源面板會說明需要多少記憶體，與為這台電腦偵測到的預算比較；若放不下，它會拒絕載入，並提供出路。模型位於 [`src/data/memory.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/data/memory.ts)。

## 記憶體估計 {#the-memory-estimate}

資料列計數完成後，會顯示在**載入**按鈕上方。

| 行 | 意義 |
|---|---|
| **記憶體估計**——*放得下* / *吃緊* / *放不下* | 判定結果，分別為綠色、琥珀色或紅色。 |
| `N rows · B B/row` | 將被載入的資料列數（經過抽稀後），以及每列的穩定位元組數。 |
| `RAM X resident, Y peak while loading` | 載入完成後常駐的記憶體，以及載入期間的最高用量。 |
| `GPU Z · est. load T` | 資料列所需的 GPU 記憶體，以及以每秒 120 萬列計算的預估載入時間。 |
| GPU 名稱 | 驅動程式有回報時，顯示渲染器的名稱。 |
| 訊息 | 為什麼放不下或吃緊，以及該怎麼做。 |
| **每 [N] 列載入一列** | 抽稀的步距（見下文）。 |
| `Budget: X RAM, Y GPU. Adjust under Performance → Resource budgets.` | 此檢查所用的預算。 |

### 每列的位元組數 {#bytes-per-row}

| 欄位 | 穩定（RAM） | 備註 |
|---|---|---|
| 位置 | 12 | 三個 32 位元浮點數，一律如此（即使是平坦的軸，仍是一個陣列） |
| 時間 | 4 | 已對應時 |
| 生命期 | 4 | 時間與人員都已對應時 |
| 人員 | 4 | 已對應時 |
| 群組 | 2 | 已對應時 |
| 工作階段 | 4 | 已對應時 |
| `Source file` | 4 | 載入超過一個檔案時 |
| 每個篩選欄位 | 4 | 每個勾選了*保留以供篩選*的欄位 |

**峰值**會加上載入時僅短暫需要的部分——合併時 64 位元時間的 8 位元組、排序鍵與索引的 12 位元組、排列暫存的 4 位元組（若時間已對應，則三者皆需），以及群組欄位仍為 32 位元時的 4 位元組——並將總和乘以 **2.0**。這個係數是經過測量的（一次真實的多檔案載入，其峰值為逐項列出之陣列的 1.9 倍，來源是 Parquet 解碼器的工作集、把每欄修剪至長度的複本，以及已釋放但尚未歸還的記憶體），並向上取整，因為估計過低會導致分頁當機，而估計過高只會造成不必要的步距。

在 **GPU** 上，每列耗用 8 位元組（位置與群組，各為 16 位元），若時間與人員都已對應，再加上 4 位元組（時間與生命期，各為 16 位元）。見 [GPU 記憶體駐留](gpu-memory.md)。篩選貼圖（每個作用中篩選器每列 4 位元組）與線條熱量的片段起點（開啟線條模式時每列 8 位元組）不包含在此估計中。

## 容量檢查 {#the-fit-check}

會比較三項限制（[`checkFit`](https://github.com/Holdi601/3DHeat/blob/main/src/data/memory.ts)）：

- 峰值 RAM 與 **RAM 預算**相比，
- GPU 位元組與 **GPU 預算**相比，
- 資料列數與 **排序上限**（4 億列）相比，前提是已對應時間欄位。

三個比值中最差的那個決定結果：達 70% 以內為*放得下*，達 100% 以內為*吃緊*（應該能載入，但會很慢），超過則為*放不下*。若放不下，面板會指出起決定作用的限制，並建議：

- 每隔 *N* 列載入一列，其中 *N* = ⌈資料列數 / 能放下的列數⌉，並預先填入步距方塊；
- 移除篩選欄位、取消時間欄位的對應（這會移除排序及其上限，代價是失去時間軸），或提高預算。

當預算本身並非硬體的事實時——瀏覽器限制了 RAM 數值、預設值因目前可用的記憶體而被壓低，或 GPU 數值只是猜測——訊息會說明這一點，以免你去使用一個並不需要的步距。

### 抽稀 {#decimation}

**每 [N] 列載入一列**會以每個檔案為單位，每 *N* 列保留一列。熱量是平均值，因此每隔 *N* 列取一列會得到相同的分布，只是雜訊較多——這與渲染器每一畫面已經做的取捨相同。方塊起始值為 1（*列（全部）*）；當所選資料放不下時，除非你已自行輸入，否則會預先填入建議的步距。載入按鈕隨後會顯示*載入 N 個檔案（每 K 列一列）*，而資料集的名稱會記錄 `every Kth row`。

### 排序上限 {#the-sort-ceiling}

渲染器需要依時間遞增排序的資料列，因此對應的時間欄位意味著要對每一列排序，並以 32 位元鍵的基數排序進行（[`sort.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/data/sort.ts)）。超過 **4 億**列時，會直接拒絕，而不是嘗試在分頁中執行。這項檢查在載入前進行，因此超過上限的選取會被拒絕並給出步距建議，而不是完整讀入後在最後一步失敗。接近上限（*吃緊*）時，面板會警告排序是一個沒有自身進度顯示的長時間過程。沒有時間欄位時，不會進行排序，也不會套用上限。

## 資源預算 {#resource-budgets}

**效能 → 資源預算**（位於效能面板底部的一行可收合文字，顯示為 `Resource budgets - RAM, GPU, cores`）。預算會被自動偵測；偵測到的數值即為預設值；而滑桿最高只能到**上限**，上限即為偵測到的數值，除非偵測已知並非實測值。

| 控制項 | 範圍 | 意義 |
|---|---|---|
| **資料列使用的 RAM** | 256 MiB 至 RAM 上限，對數刻度 | 容量檢查所用的 RAM 預算。超過偵測預設值時標示為*（高於偵測值）*，達到上限時標示為*（最大）*。 |
| **資料列使用的 GPU 記憶體** | 128 MiB 至 GPU 上限，對數刻度 | 容量檢查與上傳資料列所用的 GPU 預算。超過偵測預設值時標示為*（高於偵測值）*，達到上限時標示為*（最大）*。 |
| **剖析執行緒** | 1 到邏輯核心數 | 一次載入時同時剖析的檔案數，每個檔案各自在一個工作執行緒中執行。預設為核心數 − 2（四核或以下為核心數 − 1）。見[剖析執行緒](#parser-threads)（位於給開發者一節）。 |
| 來源行 | | 每個數值的來源（`RAM: …. GPU: …. CPU: ….`）。 |
| **重新偵測** | | 要求開發伺服器重新讀取記憶體，並重新計算所有預算。 |
| GPU 名稱 | | 轉接器的簡稱；完整的渲染器字串為工具提示。 |

### 提高 GPU 預算 {#raising-the-gpu-budget}

高於偵測值的 GPU 預算會依設定值生效：容量檢查與上傳會從同一個函式取得相同的數值（[`effectiveGpuBudget`](https://github.com/Holdi601/3DHeat/blob/main/src/render/budget.ts)），而該函式只會將其限制在滑桿停止的 GPU 上限。因此，通過檢查的載入會被完整上傳。超過偵測值後，滑桿會顯示*（高於偵測值）*：此時該數字是你對顯示卡的判斷，而不是實測值；將其設定得高於顯示卡所能負荷，可能會導致環境遺失或運作極慢。

## 超大型資料集：可用的手段 {#huge-datasets-the-levers}

由最省事到最激烈：

1. **減少篩選欄位。** 每個欄位每列耗用 4 位元組，並多一次解碼。
2. **步距。** 每隔 *N* 列取一列。
3. **沒有時間欄位。** 不需排序，沒有排序上限，也不需要時間與生命期每列 4–8 位元組——但也沒有時間軸。
4. **提高預算**，前提是你知道記憶體確實足夠。

在渲染時，大型資料集是透過取樣與漸進式累積來處理的，而不是靠縮減資料；見[取樣與預算](sampling-and-budgets.md)。

## 給開發者 {#for-developers}

### 剖析執行緒 {#parser-threads}

載入多個檔案時，會同時剖析最多 **剖析執行緒** 數量的檔案，每個檔案在由該次載入的匯入工作執行緒啟動的剖析工作執行緒中執行（[`ingestFiles.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/data/ingestFiles.ts)，`parseInOrder`）。當數值為 1，或只有一個檔案時，檔案會在匯入工作執行緒本身中依序一個接一個地剖析。

同時執行多個並不會放寬容量檢查：

- **先計算建構器。** 合併後的欄位會在讀取第一個檔案之前，就為整個選取範圍配置完成，因此執行中的檔案只能取得 RAM 預算在它們旁邊剩下的部分（`parseHeadroom`）：位置、64 位元時間、視角、人員、32 位元群組、工作階段、篩選欄位與 `Source file`，每個待載入的資料列——若資料列數是 CSV 的估計值，則再乘以 2.6，以容納成長為較大欄位的情況。
- **每個檔案在開始前先保留其成本**（`fileParseBytes`）：其資料列（來自 Parquet 結尾；CSV 則依大小取估計值的一部分）乘以相同的欄位，再乘以 **8**——區塊本身、在捨棄沒有位置的資料列時旁邊的複本，以及解碼器的工作集（對於文字欄位，其工作集遠大於其 ID）。抽稀不會降低此數值，因為檔案是完整讀取後才抽稀的。這個 8 是經由測量設定的：使用 3 或 5 時，三十個剖析執行緒在一個擁有 8,600 萬列、含人員與工作階段名稱的資料上，會讓分頁超過其上限；使用 8 時則不會。
- **另一個檔案只有在其保留量能放進剩餘空間時才會開始。** 已完成但仍在等待較早的檔案合併的檔案，會保留其保留量直到合併完成。
- **一個檔案一定會執行。** 當沒有任何保留時，下一個檔案無論成本如何都會開始——這就是容量檢查所允許的逐一載入，因此緊張的預算會退回到它，而不是拒絕。

*載入時的峰值*數字，是逐一載入的峰值，它發生在排序時，也就是所有檔案都已讀完之後。並排剖析的檔案在被讀取時，可能會使用超過該數字的記憶體；只要上述估計正確，保留量就會將其控制在 RAM 預算之內。

合併順序是選取範圍的順序，與檔案完成的順序無關，因此人員、群組與工作階段的編號、資料列以及 `Source file` 的值，都與逐一載入完全相同。無法讀取的檔案會被略過，並與以前一樣列出。剖析工作執行緒若當機，會結束整個載入，就像匯入工作執行緒當機時一樣；無論載入如何結束，每個剖析工作執行緒都會在載入結束時被終止。若完全無法啟動剖析工作執行緒，則檔案會改在匯入工作執行緒中剖析。

### 數字如何偵測 {#how-the-figures-are-detected}

[`detectBudgets`](https://github.com/Holdi601/3DHeat/blob/main/src/data/memory.ts) 會在啟動時執行，在渲染器建立後再執行一次，以及按下**重新偵測**時執行。

**RAM，使用開發伺服器時。** `start.bat` 與 `npm run dev` 會由一個能讀取這台電腦記憶體的程序提供頁面，路徑為 `/__host/memory`（若在 1.5 秒內未回應則忽略）。預設值為已安裝 RAM 的 60% 與目前可用 RAM 的 80% 兩者中較小者；上限為已安裝 RAM 的 60%。當可用記憶體是把預設值壓低的原因時，面板會說明這一點，並建議關閉程式後按下**重新偵測**。

**RAM，沒有開發伺服器時**（靜態部署）：沒有任何瀏覽器 API 會回報可用記憶體，而 Chrome 與 Edge 會把 `navigator.deviceMemory` 向下取整為 2 的冪次，並上限為 8 GiB。預設值為 `deviceMemory` 的 60%，若瀏覽器有回報分頁可用的 JS 堆積，則再進一步上限為其 4 倍；若沒有任何回報，則為 4 GiB。當 `deviceMemory` 恰好讀到 8（上限值）時，該數字會被標記為*已限制*，上限為預設值的 4 倍，並附註說明超過預設值的數字是你的假設，而不是實測值。

**無論哪種情況**，RAM 的預設值與上限都會限制在 **12 GiB**——無論機器有多少記憶體，一個 Chrome 分頁所能容納的型別化陣列記憶體上限（有一個頁面曾達到 15.75 GB 而失敗；12 GiB 為其他一切留出空間），且絕不低於 256 MiB。

**GPU 記憶體。** 沒有任何網路 API 會回報它。

- 使用開發伺服器時，顯示卡的記憶體由 `nvidia-smi` 讀取（取最大的轉接器），或在 Windows 上從顯示轉接器的登錄值 `HardwareInformation.qwMemorySize` 讀取。預設值為其 70%，上限為 90%。
- 沒有讀數時，則會推定：預設為 2 GiB；當最大紋理為 16,384 px 或以上時（獨立顯示卡）為 4 GiB，較小時為 1 GiB；或當 WebGPU 的 `maxBufferSize` 較大時為其 8 倍。此時上限為推定值的 8 倍，因為推定只能分辨整合式與獨立式晶片，無法更精細。面板會說明此數值為推定。
- 絕不低於 128 MiB。

**CPU。** `navigator.hardwareConcurrency`（未回報時為 4）。

# Запісы Tacview (ACMI)

Tacview — гэта праграма, якая запісвае палёты ў авіясімулятарах; яе файлы маюць суфікс `.acmi`. 3DHeat адкрывае іх, каб вы маглі бачыць, дзе лётаў кожны самалёт.

Запісы палётаў Tacview загружаюцца, як любая табліца: выберыце або перацягніце `.acmi` (тэкставы, `.txt.acmi`, або спакаваны, `.zip.acmi`) і націсніце **Загрузіць**. Пасля гэтага вы атрымліваеце цеплыню ўсіх палётаў, а на ўкладцы **Match** — прайграванне з фігурамі, трэкамі і спісам падзей ([Прайграванне матчу](match-replay.md)). ACMI — публічны фармат файлаў Tacview ([дакументацыя](https://www.tacview.net/documentation/acmi/)); DCS (праз экспарцёр Tacview), IL-2 Great Battles, Falcon BMS, X-Plane, MSFS і іншыя пішуць яго, таму гэта чытае любы з іх.

## Што становіцца з запісу {#what-a-recording-becomes}

Адзін радок кожны раз, калі запісваецца пазіцыя аб'екта, адзін радок на кожную падзею ў месцы аб'екта і адзін радок, калі аб'ект знікае (`Removed`, там, дзе ён быў апошні раз). Падзея пра аб'ект, які яшчэ не бачылі, — закладка, паведамленне для ўсіх — становіцца радком аб'екта `(recording)` у апорнай кропцы. Запіс мае ўласныя інструкцыі чытання, таму крок супастаўлення запаўняецца сам. Чытач піша такія слупкі: `Time`, `X`, `Y`, `Altitude`, `Object`, `Coalition`, `Heading`, `Pitch`, `Roll`, `Type`, `Name`, `Pilot`, `Group`, `Country`, `Color`, `Event`, `Latitude`, `Longitude`, `Recording`, `EventObjects`, `RecordingInfo`, а потым любыя іншыя ўласцівасці, якія ёсць у запісе. Іх ролі:

| Слупок | Роля | Значэнне |
|---|---|---|
| Time | час | Секунды пасля ReferenceTime запісу; Unix-секунды, калі ён ёсць, таму гадзіннік паказвае сапраўдны час. |
| X, Y | пазіцыя | Усход і поўнач, метры, на плоскасці, што дакранаецца зямлі ў апорнай кропцы запісу: адлегласці і азімуты дакладныя побач з ёй, а на 100 км дрэйфуюць менш чым на адну тысячную. Поўнач становіцца -Z свету. |
| Altitude | пазіцыя (уверх) | Метры. |
| Object | асоба | Пілот і назва аб'екта з id, напрыклад, `Viper 1 (F-16C_50) #a01`; аб'ект без пілота `(T-90A) #401`. |
| Coalition | каманда | Бок (або колер, калі кааліцыі няма). |
| Heading, Pitch | погляд | Градусы; курс 0 — поўнач. |
| Recording | сесія | Title запісу або назва файла: некалькі запісаў загружаюцца побач, не злучаючы свае трэкі. |
| Type, Name, Pilot, Group, Country, Color, Event, Roll, Latitude, Longitude | фільтры | Захоўваюцца для фільтравання; Type і Name выбіраюць [фігуру](figures.md) кожнага аб'екта, Event падае спіс падзей разбору, Roll нахіляе самалёт. |
| U, V | | Уласныя плоскія метры свету гульні, калі ў кожнага ўзору яны ёсць (DCS іх піша). |
| EventObjects | фільтры | Кожны аб'ект, які называе падзея (`Message|a01|b02|...`), па id. |
| RecordingInfo | | Уласныя ўласцівасці запісу такімі, якімі яны былі ў той момант — DataSource, DataRecorder, Author, Category, Briefing, Comments, ... — як JSON. |
| IAS, Mach, AOA, FuelWeight, ... | фільтры | Любая іншая лікавая ўласцівасць, якую нясе запіс. |
| Parent, CallSign, LockedTarget, Label, Shape, ... | фільтры | Любая іншая тэкставая ўласцівасць запісу; уласцівасць з любым значэннем, якое не лік, з'яўляецца тэкстам. |

Усе чатыры формы пазіцыі Tacview (`lon|lat|alt`, з `u|v`, з `roll|pitch|yaw` і з усімі імі і курсам) чытаюцца; пустыя палі захоўваюць апошняе значэнне; `-id` выдаляе аб'ект, а id, які выкарыстоўваецца зноў пасля гэтага, — гэта новы аб'ект. Экранаваныя коскі і працягнутыя радкі апрацоўваюцца.

Пазіцыі заўсёды праецыруюцца з шыраты і даўгаты, ніколі не браюцца з U/V, таму запісы з усіх гульняў дзеляць адну праекцыю з фонам сапраўднага свету.

## Серверы DCS: хто перамог і як скончыўся кожны вылет {#dcs-servers-who-won-and-how-each-sortie-ended}

Шматкарыстальніцкі сервер DCS кругласутачна запісвае свае місіі праз Tacview. Пастаянны PvP-сервер вядзе кампанію праз многа такіх місій: бок перамагае, калі захоплівае кожны аэрадром, FARP і зону іншага боку. Гэта займае дні і многа перазапускаў місіі. Запісы ўтрымліваюць палёты, а не кампанію: ніводнае паведамленне не кажа, хто што захапіў, аэрадромы запісаны адзін раз на пачатку, і нішто не кажа, хто перамог. Канвертар Tacview (`node tools/acmi-to-parquet.mjs`, [`data/dcsOutcome.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/data/dcsOutcome.ts)) дадае да кожнага радка тое, што можна ведаць, а тое, чаго ведаць нельга, пакідае пустым. Ён ніколі не адгадвае.

| Слупок | Значэнне |
|---|---|
| `server` | сервер або кампанія, з загалоўка запісу (яго Title, Author і Comments называюць вядомыя публічныя серверы - Blue Flag, SPS Contention, Growling Sidewinder; інакш Author, які называе кагосьці); `--server Name` дае назву для цэлай папкі. Запіс, чый загаловак не называе сервера - Author накшталт `Admin`, Title і Comments, якіх не піша ніводны вядомы сервер, - застаецца без прывязкі: `server` пусты, нават калі яго спампавалі са старонкі запісаў сервера, бо гэтая старонка можа мець і місіі іншых супольнасцяў |
| `mission` | Title запісу без яго версіі ці месяца кампаніі: `Operation_Example_V7.7.99` становіцца `Operation Example` |
| `campaign` | раўнд кампаніі, да якога належыць запіс, па серверы, мапе і нумары: `Example Server North 3`. Адзін запіс - гэта адна сесія (ад перазапуску да перазапуску); раўнд ідзе праз многа сесій, дні або тыдні |
| `round` | нумар гэтага раўнда: уласны нумар сервера, калі ён яго публікуе, інакш n-ы раўнд, бачны на гэтым серверы і мапе; з файла раўндаў (ніжэй), без яго пусты |
| `session` | месца запісу сярод сесій раўнда, 1, 2, ...; `sessionStart` - яго сапраўдны пачатак (секунды Unix) |
| `heldRed`, `heldBlue` | спрэчныя месцы, якія кожны бок утрымліваў на пачатку сесіі, з ланцуговага файла раўндаў (ніжэй) |
| `won`, `matchWon` | 1, калі бок радка (яго Color, Red або Blue) выйграў гэтую кампанію, 0, калі прайграў; пустыя, дзе ніводны файл раўндаў не называе пераможцу, і ў нейтральных радках. Кампанія - гэта адначасова раўнд і матч, таму абодва слупкі маюць аднолькавае значэнне |
| `roundEndReason` | `capture` для кампаніі, выйгранай захопам усяго |
| `won`, `matchWon` у кожнай сесіі раўнда | вынік раўнда, запісаны ў кожным яго запісе, як толькі вядомы яго канец |
| `sortie` | у радках самалёта: яго палёт, 1, 2, ... ад узлёту да ўзлёту; час на зямлі да першага ўзлёту і пасля пасадкі адносіцца да палёту, да якога ён належыць |
| `sortieResult` | як скончыўся гэты палёт: `landed`, `landed damaged` (пасля трапляння ў паветры), `ejected`, `shot down`, `destroyed` (на зямлі), `crashed`, `despawned` (знік у паветры без бачнай прычыны - гулец выйшаў), `airborne at end`, `no takeoff` |
| `sortieKills` | знішчэнні, залічаныя самалёту ў гэтым палёце |

На пастаянным серверы менавіта вылет мае значэнне. Фільтруйце па `sortieResult` = `shot down`, каб убачыць, дзе губляліся палёты, або разбіце цяпло па `sortieResult` ці `server` у [разбіўцы](breakdown.md). Узлёты, пасадкі, катапультаванні, знішчэнні і аварыі, з якіх складаецца вылет, - гэта падзеі, якія канвертар вызначае з таго, як рухаецца самалёт (вышэй).

Месцы, захопленыя паміж дзвюма сесіямі раўнда (іх відаць з файла раўндаў, ніжэй), становяцца падзеямі `capture` на пачатку пазнейшага запісу: `Object` `(campaign)`, на гэтым месцы, `Detail` `Red to Blue, between missions`, `Inferred` `between missions`.

Аэрадром або FARP, які мяняе бок там, дзе гэта відаць у запісе (запісаны зноў у колеры іншага боку, або выдалены і запісаны зноў на сваім месцы ў колеры іншага на працягу пяці хвілін), становіцца падзеяй `capture` на гэтай пляцоўцы: `Event` = `capture`, `Airfield` - яго назва, `Detail` `Red to Blue`, `Coalition` - яго новы бок. Пляцоўка, упершыню запісаная ў нейкім колеры, - гэта не захоп. Серверы, якія мы дагэтуль праглядзелі, запісваюць свае пляцоўкі адзін раз, таму ў іх запісах захопаў няма.

### Файлы раўндаў {#rounds-files}

Файл раўндаў для кожнага сервера кажа, якія ў яго раўнды кампаніі, хто іх выйграў і якія сесіі мае кожны раўнд. Ён бярэцца з таго, што публікуе сервер, або з саміх запісаў (ніжэй).

Хто выйграў кампанію - гэта тое, што публікуе сервер (журнал кампаніі на яго вэб-старонцы), а не нешта ў запісе. Файл раўндаў нясе гэтую інфармацыю, і канвертар чытае яго з `--rounds file.json` (можна даць некалькі):

```json
{
  "format": "heat3d-dcs-rounds",
  "version": 1,
  "server": "Example Server",
  "source": "Example Server's public campaign log, read 2026-11-15",
  "rounds": [
    { "id": 41, "title": "^Example-Campaign-North$", "start": "2026-11-01T08:00:00Z", "end": "2026-11-04T19:30:00Z", "winner": "Blue", "endReason": "capture", "state": "won" },
    { "id": 42, "title": "^Example-Campaign-North$", "start": "2026-11-04T19:30:00Z", "end": null, "winner": null, "state": "in progress" }
  ]
}
```

Запіс належыць да тых раўндаў свайго `server`, чый `title` (рэгулярны выраз) супадае з яго Title. Кожны радок належыць да раўнда, у які трапляе яго сапраўдны час: RecordingTime запісу плюс секунды радка, а не гульнявая дата місіі. Час - у UTC. Раўнд без пераможцы (зменены, яшчэ ідзе) дае сваім радкам нумар раўнда і пусты вынік.

Адпаведнік дакумента матчу, ніжні блок `acmi`, кажа, адкуль узяўся вынік, як гэта робіць `result.source` матчу War Thunder: `outcome.result` - гэта `{ winner, round, endReason, source }`, дзе `source` - гэта `source` файла раўндаў, або `null`, калі нішто не назвала пераможцу. `outcome` таксама пералічвае раўнды запісу, яго захопы і яго вылеты па тым, як яны скончыліся:

```json
"outcome": {
  "server": "Example Server", "mission": "Example-Campaign-North", "kind": null,
  "result": { "winner": "Blue", "round": 41, "endReason": "capture", "source": "Example Server's public campaign log, read 2026-11-15" },
  "rounds": [{ "id": 41, "start": "2026-11-01T08:00:00.000Z", "end": "2026-11-04T19:30:00.000Z", "winner": "Blue", "endReason": "capture", "state": "won" }],
  "captures": 0,
  "sorties": { "landed": 31, "shot down": 12, "ejected": 3, "crashed": 2, "despawned": 9, "no takeoff": 4 }
}
```

Радок пілота `Viper 1 (F-16C_50) #a01` на сінім баку ў гэтай кампаніі тады мае: `server` Example Server, `round` 41, `won` 1, `roundEndReason` capture, `sortie` 2, `sortieResult` landed, `sortieKills` 1.

### Раўнды з саміх запісаў {#rounds-from-the-recordings-themselves}

Пастаянны сервер захоўвае сваю кампанію паміж перазапускамі, і кожны запіс пачынаецца з наземных падраздзяленняў і статычных аб'ектаў абодвух бакоў там, дзе іх пакінула кампанія. `node tools/dcs-campaign-rounds.mjs <out-folder> <folder>...` чытае першыя хвіліны кожнага запісу ([`data/dcsCampaign.ts`](https://github.com/Holdi601/3DHeat/blob/main/src/data/dcsCampaign.ts)), ставіць запісы кожнага сервера на адной мапе па часе і злучае іх у ланцуг:

- **Месцы**: зямля, падзеленая на клеткі прыблізна па 2 km; клетка належыць боку, калі тры чвэрці падраздзяленняў у ёй на пачатку сесіі - яго. *Спрэчныя* месцы - гэта тыя, якія бачылі ў руках абодвух бакоў.
- **Захопы**: месца, якое на пачатку наступнай сесіі ўтрымлівае іншы бок - захопленае паміж місіямі або падчас папярэдняй.
- **Новы раўнд**: сесія, чые месцы адрозніваюцца ад месцаў папярэдняй больш чым на 60% - гэта пачатковае размяшчэнне новага раўнда, а не крок старога. Раўнд таксама заканчваецца, калі сервер пераходзіць на іншую мапу (яго сесіі пачынаюцца пасля апошняй і ідуць далей).
- **Хто перамог**: у раўндзе, які скончыўся, - бок, які ўтрымліваў кожнае месца на пачатку яго апошняй сесіі (`capture`, упэўненасць высокая), інакш бок, які ўтрымліваў больш спрэчных месцаў (сярэдняя, калі ўдвая больш, чым іншы, інакш нізкая; нізкая, калі раўнд скончыўся зменай мапы). Адкрыты раўнд не мае пераможцы, але кожная сесія кажа, колькі месцаў утрымліваў кожны бок на яе пачатку, таму відаць, хто быў наперадзе.
- Сервер, чые сесіі ўсе пачынаюцца аднолькава, не захоўвае стан паміж імі: яго не злучаюць у ланцуг.

Пачатак апошняй сесіі можа быць за гадзіны да канца раўнда, таму ўпэўненасць важная. Праверка на серверы, які публікуе сваіх пераможцаў: ланцуг знайшоў кожны новы раўнд у той сесіі, з якой пачаўся апублікаваны раўнд, а бок, які быў наперадзе на апошнім пачатку, быў апублікаваным пераможцам у кожным з 9 раўндаў, якія можна было праверыць. `--official file.json` захоўвае апублікаваныя раўнды такога сервера і дадае да іх сесіі з ланцуга; поле `validation` у файле кажа, наколькі ланцуг супаў. У выдуманай кампаніі:

```json
{ "id": 2, "campaign": "Example Server North 2", "title": "^(?:Example_North_V1\.0)$",
  "start": "2026-11-02T06:00:00.000Z", "end": "2026-11-06T12:00:00.000Z", "winner": "Red", "endReason": null,
  "state": "won (reset)", "confidence": "medium", "ahead": "Red",
  "sessions": [
    { "start": "2026-11-02T06:00:00.000Z", "red": 12, "blue": 11, "redAll": 30, "blueAll": 28, "captures": [] },
    { "start": "2026-11-02T12:00:00.000Z", "red": 14, "blue": 9, "redAll": 32, "blueAll": 26,
      "captures": [{ "lat": 42.36, "lon": 42.02, "from": "Blue", "to": "Red" }, { "lat": 42.4, "lon": 41.98, "from": "Blue", "to": "Red" }] }
  ] }
```

### Прагляд раўнда кампаніі як серыі {#watching-a-campaign-round-as-a-series}

Загрузіце запісы аднаго раўнда разам (файлы з аднолькавым `campaign`), і праглядальнік прайграе іх як адну серыю: сесія за сесіяй у іх сапраўдным парадку, а гадзіны ці дні паміж дзвюма сесіямі скарочаны да перапынку ў адну хвіліну. Шкала часу пазначае пачатак кожнай сесіі жоўтым, а перапынкі - цёмнымі палосамі. Гадзіннік кажа, якая сесія грае, і яе сапраўдную дату (`session 4/12 · 2026-11-02 12:38 UTC`). Цяпло, паўтор, фільтры і Insights працуюць на ўсёй серыі, як на любых загружаных даных. Раздзел **Раўнд кампаніі** на ўкладцы **Матч** пералічвае сесіі з іх датамі, колькі спрэчных месцаў кожны бок утрымліваў на кожным пачатку (таксама як графік за ўвесь раўнд) і колькі з іх захапілі перад ім; клік пераходзіць да пачатку сесіі. Запіс, загружаны асобна, кажа там, які гэта раўнд і якая сесія. Запісы розных раўндаў, загружаныя разам, - гэта не серыя: кожны пачынаецца з нуля, як асобныя матчы. Загрузчык многіх матчаў (**Шмат матчаў адразу**) таксама прайграе раўнд як серыю, патокава і з памерам пад GPU, для раўндаў на многа гігабайтаў.

Месцы, якія мянялі ўладальніка падчас раўнда, намаляваны на мапе як зоны захопу. Кожная зона мае колер боку, які ўтрымліваў яе на пачатку сесіі, што грае, і колер мяняецца на межах сесій; кожная змена - гэта захоп у спісе падзей паўтору. Іх вызначаюць з загружаных радкоў (наземныя падраздзяленні і статычныя аб'екты кожнай сесіі ў яе першыя хвіліны, у клетках прыблізна па 2 km, як гэта робіць ланцуг), таму ім патрэбны поўны загрузчык (загрузчык многіх матчаў захоўвае занадта мала з кожнага радка).

**Загрузка ўсяго раўнда з аднаго яго запісу.** У звычайным браўзеры праглядальнік не можа адкрываць файлы, якіх вы не выбралі: загрузіце файлы раўнда разам. Калі яго абслугоўвае лакальны сервер праглядальніка (`npm run dev` або `npm run preview`), ён можа: дадайце ў ігнараваны git файл `tools/local-data.json` запіс `campaigns`, які называе папку файлаў раўндаў і папкі канвертаваных запісаў. Тады раздзел «Раўнд кампаніі» асобнага запісу прапануе **Загрузіць увесь раўнд**: ён атрымлівае знойдзеныя там сесіі раўнда і загружае іх загрузчыкам многіх матчаў:

```json
"campaigns": { "rounds": "D:/dcs/rounds", "recordings": ["D:/dcs/converted"] }
```

Абслугоўваюцца толькі запісы, якія называе файл раўндаў (`tools/campaign-files.mjs`); сесію, не знойдзеную ў гэтых папках, улічваюць, але не загружаюць.

Што публікуюць вядомыя серверы:

| Сервер | Раўнд | Як бок перамагае | Дзе можна прачытаць пераможцу |
|---|---|---|---|
| SPS Contention | кампанія на адной мапе і ў адной эпосе (дні), праз многа перазапускаў | захоплены кожны аэрадром, FARP і апорны пункт; кампанію, якая скончылася без пераможцы, змянілі | публічны журнал кампаній сервера (пераможца, пачатак, канец кожнай кампаніі) |
| Blue Flag | раўнд кампаніі праз многа 5-гадзінных місій; `_YYYY_MM` у Title з кожным перазапускам рухаецца на адзін месяц | захоплена кожная пазіцыя ворага; старэйшыя раўнды называлі бок, які ўтрымліваў больш пасля пэўнага часу | дагэтуль не знойдзены ў апублікаваным выглядзе; ланцуг запісаў сочыць за кожным раўндам і за тым, хто колькі ўтрымлівае на кожным пачатку |
| Growling Sidewinder | запуск місіі (6 гадзін) місіі адкрытага канфлікту | захоплены зоны і аэрадромы | яго старонка статыстыкі паказвае пілотаў, а не вынікі; кожная сесія пачынаецца аднолькава, таму ніводны раўнд не ахоплівае некалькі сесій: пуста |
| Місіі супраць ШІ (місіі з захопам зон) | запуск місіі | бок гульцоў супраць ШІ місіі: няма выніку PvP | пуста |
| Без прывязкі (загаловак не называе сервера) | - | - | пуста, `server` таксама пусты |
